## 1. 方向与结论

本版方向是：**先把 Iceberg FDW 的"上半层 routine"在 GaussVector extension 形态下接通——注册 `FdwRoutine`、实现规划三回调与扫描生命周期骨架，并把它与控制面 SQL 接口的接入关系厘清——把 `arrow → tuple/vectorbatch` 的转换内核和 namespace/table 控制面的详细设计留到后续版本。**

结论先行：

- **"FDW 的 routine"与"namespace/table 的 SQL 接口"是两条互不调用的路径，只通过 Catalog 状态相连，不通过调用链相连。** routine 是数据面（执行器在查询外表时自动回调 `FdwRoutine`）；namespace/table 的 SQL 接口是控制面（用户显式调用扩展导出的 SQL 函数）。doc 2 说的"6 个接口"指数据面的 6 个 `FdwRoutine` 扫描回调；上一轮设计里 namespace 的"6 个接口"指控制面的 6 个 catalog 操作——两者同名易混，但分属两个平面，本文统一以"数据面 / 控制面"指代，不再混用"6 个接口"这一计数。

- **openGauss 的 `FdwRoutine` 里没有 `ImportForeignSchema`**（已核对拉取源码，§2.1）。这意味着 namespace/table 的目录操作**在 openGauss 上根本没有对应的 FDW 回调**，只能实现为扩展导出的 SQL 函数 + C(++) handler——这比在社区 PG 上的结论更硬。openGauss 提供的 DDL 期钩子是 `ValidateTableDef` 与 `PartitionTblProcess`，用于外表定义校验和分区外表处理，可作为未来 table create 路径的挂载点，但它们不是 namespace 管理接口。

- **tuple 路径与 vectorbatch 路径在 openGauss 里是两个并列的回调**：行式 `IterateForeignScan` 返回 `TupleTableSlot*`，向量化 `VecIterateForeignScan` 返回 `VectorBatch*`（入参为 `VecForeignScanState*`）。这修正了 doc 2 §6.4 里假设的 `IterateForeignScanBatch` 命名——真实 API 名为 `VecIterateForeignScan`。上半层需要把**两个迭代入口都注册进 `FdwRoutine`**，共享同一套规划与扫描态。

- **上半层先用桩数据打通，不依赖 Arrow**。把规划三回调产出的 `FileScanTask` 先写死、`Iterate/VecIterate` 先返回 mock 行/批，目标是验证"`SELECT 外表` 能走完整条 routine 接线"；随后把规划接进 Catalog 解析（namespace.table → metadata_location），最后才在下一版把 mock 换成真实 Arrow 读取。这样 routine 接线与 Arrow 转换解耦，可分别验证。

本版明确不做：完整 Arrow→tuple/vectorbatch 转换、namespace/table 控制面 SQL 详细设计、写路径（Modify）、join/upper 下推、并行/异步扫描。

## 2. openGauss FDW 接口现状（以拉取源码为准）

### 2.1 `FdwRoutine` 全量回调清单

下表来自拉取的 `src/include/foreign/fdwapi.h`（openGauss master）。注意该头文件本身 `#include "vecexecutor/vectorbatch.h"` 与 `vecexecutor/vecnodes.h`——**向量化是 FDW API 的内建部分**，不是外挂。

|---|---|---|---|
| **扫描规划** | `GetForeignRelSize` | `(PlannerInfo*, RelOptInfo*, Oid)` | ✅ |
| | `GetForeignPaths` | `(PlannerInfo*, RelOptInfo*, Oid)` | ✅ |
| | `GetForeignPlan` | `(…, ForeignPath*, List* tlist, List* scan_clauses, Plan* outer_plan)` → `ForeignScan*` ⚠️比社区 PG 多 `outer_plan` 参数 | ✅ |

### 2.2 与社区 PostgreSQL FDW 的关键差异

- **多 `VecIterateForeignScan`**：社区 PG 无此项；openGauss 把向量化扫描作为一等回调。tuple 与 vectorbatch 两条路在此分叉。
- **无 `ImportForeignSchema`**：社区 PG 有；此 openGauss 版本的 `FdwRoutine` 不含——目录/schema 导入没有 FDW 回调位。
- **无并行/异步扫描回调**：无 `IsForeignScanParallelSafe`、无 `ForeignAsyncRequest` 一族。
- **无 DirectModify**：无 `PlanDirectModify` 一族，写路径只有逐行 Modify。
- **`GetForeignPlan` 多 `outer_plan` 参数**、**`GetForeignUpperPaths` 用 `FDWUpperRelCxt*`**：签名细节与社区 PG 不同，移植回调实现时必须对齐。
- **MOT / `@hdfs` 扩展回调**：`ValidateTableDef`、`PartitionTblProcess`、`BuildRuntimePredicate`、内存统计等是 openGauss 为 MOT 和 HDFS/DFS 外表引入的，多数对 Iceberg 只读扫描不必需。

### 2.3 handler / validator 注册（extension 形态）

openGauss FDW 是 **C++**（`.cpp`、`extern "C"` 导出、`PG_FUNCTION_INFO_V1`）。以 `contrib/file_fdw/file_fdw.cpp` 为模板，handler 即"`makeNode(FdwRoutine)` + 逐字段赋指针"：

```cpp
extern "C" Datum iceberg_fdw_handler(PG_FUNCTION_ARGS);
extern "C" Datum iceberg_fdw_validator(PG_FUNCTION_ARGS);
PG_FUNCTION_INFO_V1(iceberg_fdw_handler);
PG_FUNCTION_INFO_V1(iceberg_fdw_validator);

Datum iceberg_fdw_handler(PG_FUNCTION_ARGS)
{
    FdwRoutine *r = makeNode(FdwRoutine);          /* 未赋值字段全为 NULL */
    /* 规划三回调 */
    r->GetForeignRelSize = icebergGetForeignRelSize;
    r->GetForeignPaths   = icebergGetForeignPaths;
    r->GetForeignPlan    = icebergGetForeignPlan;
    /* 行式执行 */
    r->BeginForeignScan  = icebergBeginForeignScan;
    r->IterateForeignScan = icebergIterateForeignScan;
    r->ReScanForeignScan = icebergReScanForeignScan;
    r->EndForeignScan    = icebergEndForeignScan;
    /* 向量化执行（tuple/vectorbatch 双路并列） */
    r->VecIterateForeignScan = icebergVecIterateForeignScan;
    /* EXPLAIN / DDL 校验 */
    r->ExplainForeignScan = icebergExplainForeignScan;
    r->ValidateTableDef  = icebergValidateTableDef;   /* table create 接入点，namespace 不经此 */
    PG_RETURN_POINTER(r);
}
```

extension 安装侧（`iceberg_fdw--1.0.sql`）声明 handler/validator 并建 FDW：

```sql
CREATE FUNCTION iceberg_fdw_handler()   RETURNS fdw_handler   AS 'MODULE_PATHNAME' LANGUAGE C;
CREATE FUNCTION iceberg_fdw_validator(text[], oid) RETURNS void AS 'MODULE_PATHNAME' LANGUAGE C;
CREATE FOREIGN DATA WRAPPER iceberg_fdw
    HANDLER iceberg_fdw_handler VALIDATOR iceberg_fdw_validator;
```

### 2.4 落地到 GaussVector 时需复核的差异点

GaussVector 与社区 openGauss 不完全一致，定稿前需对 GaussVector 内核头文件复核：① `FdwRoutine` 字段集与本节是否一致（尤其 `VecIterateForeignScan` 是否同名同签名）；② `VecForeignScanState` / `VectorBatch` 结构（向量批容量、`ScalarVector` 布局，关系下半层）；③ `GetForeignPlan` 的 `outer_plan` 等签名细节；④ extension 构建是否走 PGXS/CMake、是否允许 `.cpp`。这些差异不改变本文的 routine 结构设计，只影响具体签名与构建。

## 3. 上半层 routine 的范围切分

把 `FdwRoutine` 按"是否触及 Arrow 转换"切成上下半，本版只做上半：

```
FdwRoutine（handler 里 makeNode + 赋指针）
├─ 注册层        handler / validator                              ← 上半层
├─ 规划三回调    GetForeignRelSize → GetForeignPaths → GetForeignPlan  ← 上半层（重点）
│                    └─ GetForeignPlan 内调 Catalog 解析，编码 fdw_private
├─ 行式执行      BeginForeignScan → IterateForeignScan → End/ReScan    ← 骨架属上半层
│                    └─ Iterate 内"Arrow 批 → tuple"内核              ← 下半层（下一版）
└─ 向量化执行    VecIterateForeignScan                                ← 骨架属上半层
                     └─ "Arrow 批 → VectorBatch"内核                  ← 下半层（下一版）
```

上半层的交付边界：**6 个扫描回调（+ ReScan、+ VecIterate）作为能跑通的骨架**，规划阶段真实解析 Catalog 得到文件列表，执行阶段先返回桩数据。下半层只剩"把桩数据换成 `ArrowColumnToDatums` / `ArrowColumnToScalarVector`"（doc 2 §6.3/§6.4），不再改动 routine 接线。

tuple 与 vectorbatch 两路共享 `BeginForeignScan` 建立的扫描态与文件快照；执行器按计划节点类型（`ForeignScan` vs `VecForeignScan`）决定调 `IterateForeignScan` 还是 `VecIterateForeignScan`。上半层必须让两个入口都能返回正确形状的空/桩结果并正常收尾。

## 4. 控制面 SQL 接口与 routine 的接入关系

这一节回答"上层 SQL 与 FDW 内部怎么连"。核心是：**控制面写 Catalog，数据面读 Catalog，二者无直接调用**。

**接触点一：OPTIONS 是绑定锚点。** 一张外表（`pg_class` + `pg_foreign_table`）通过 OPTIONS 指明它对应哪个 namespace、哪张 Iceberg 表；server 级 OPTIONS 指明 Catalog 后端（系统表 / REST）。这些 OPTIONS 的合法性由 `validator` 回调把关，DDL 期由 `ValidateTableDef` 进一步校验外表定义。OPTIONS 是 SQL 侧与 routine 侧唯一的静态契约。

**接触点二：规划期的 Catalog 解析（routine 在此消费控制面产出的状态）。** `GetForeignPlan`（必要时 `GetForeignRelSize`）从外表 OPTIONS 取 `namespace.table`，调 Catalog 抽象解析出 `metadata_location → schema → FileScanTask 列表`，编码进 `fdw_private`。也就是说：未来的 `iceberg_create_table(...)` 往 Catalog 写一行表身份，之后 `SELECT` 这张外表时，规划回调读同一份 Catalog 把它取出来——**两条路径在 Catalog 抽象（§7）上汇合，而非互相调用**。

**接触点三：namespace 与 table 在 routine 里的出场程度不同。**
- **namespace 对 routine 完全不出场**：不存在"`SELECT` 一个 namespace"，所以 namespace 的目录操作（list/create/load/exists/drop/update properties）是纯 Catalog 操作，零 routine 接触面。**[接入点]** 支持 namespace 时，此处只需在 Catalog 抽象上增加 namespace 操作集并新增对应 SQL 函数，无需改动任何 `FdwRoutine` 回调；详见 §11。
- **table 间接出场**：`iceberg_create_table` 除了写 Catalog，还要让表"可被查询"——即对应一个外表对象。建表既可走原生 `CREATE FOREIGN TABLE ... OPTIONS(namespace, table)`（FDW 只用 `validator`/`ValidateTableDef` 校验），也可由 SQL 函数托管创建外表对象并把 `relid` 回写 Catalog（对应 GaussVector 设计 §6.2 的 `tables.relid REGCLASS`，及 pg_lake `tables_internal`(带 Oid) / `tables_external`(无 Oid) 之分）。**[接入点]** 支持 table create 时，此处需把 `ValidateTableDef` 实现为校验 Iceberg 外表 OPTIONS，并决定建表走"纯 DDL"还是"函数托管"模型；详见 §11。

因此本版上半层只需保证：规划回调能从 OPTIONS + Catalog 解析出文件列表；至于 Catalog 里的表身份是手工 `INSERT` 进去，还是未来由控制面 SQL 写进去，对 routine 透明。

## 5. 上半层各回调详细设计

各回调以 §2.3 的命名为准。"骨架阶段"指本版用桩数据打通，"接 Catalog"指接入 §7 抽象。

### 5.1 注册层：handler / validator

- `iceberg_fdw_handler`：见 §2.3，赋齐 6 个扫描回调 + `VecIterateForeignScan` + `ExplainForeignScan` + `ValidateTableDef`，其余 NULL。
- `iceberg_fdw_validator`：校验 server/table OPTIONS。server 级：`catalog_kind`(pg_native/rest)、`uri`/`prefix`/`warehouse`（rest 时）、`catalog_schema`（pg_native 时）。table 级：`namespace`、`table_name`。非法 key 报 `ERRCODE_FDW_INVALID_OPTION_NAME`。

### 5.2 `GetForeignRelSize`

- 职责：填 `baserel->rows / width`；`classifyConditions` 把 `baserel->baserestrictinfo` 拆成可下推（remote）与不可下推（local）。
- 骨架阶段：行数/宽度给固定估算，谓词分类可先全部归 local（不下推），保证正确性优先。
- 接 Catalog：从 OPTIONS 取 `namespace.table`，可顺带做一次轻量 Catalog 查询取 `record_count` 累加估行（doc 1 §4.1）。

### 5.3 `GetForeignPaths`

- 职责：`create_foreignscan_path(...)` 生成一条基础 ForeignPath，`add_path()`。
- 骨架阶段：单一全表扫描路径即可；参数化路径/有序路径本版不做。

### 5.4 `GetForeignPlan`（上半层重点）

- 职责：固化计划节点，**调 Catalog 解析文件列表并编码 `fdw_private`**。注意 openGauss 签名含 `Plan* outer_plan`。
- 流程：
  1. 从外表 OPTIONS 取 `namespace.table`；
  2. `IcebergCatalogResolveTable(cat, ns, table)` → `metadata_location` + 当前 schema（§7）；
  3. 调 SDK/桩 `PlanFiles()` 得 `FileScanTask` 列表（骨架阶段写死 1~2 个 mock task）；
  4. 计算投影列（retrieved_attrs）、残差谓词、`field_id → 属性号`映射；
  5. 编码 `fdw_private = list_make4(SerializeFileScanTasks(tasks), retrieved_attrs, residual, field_id_map)`（§6），`make_foreignscan(...)`。
- 与 pg_lake 的差异：去掉 DuckDB SQL 模板那一项（doc 2 §3.2），换成 FileScanTask 列表。

### 5.5 `BeginForeignScan`

- 职责：从 `fdw_private` 解码；建 `batch_cxt`/`temp_cxt`；打开（或桩开）reader；初始化批游标（`tuples/num_tuples/next_tuple/eof_reached`）。
- 骨架阶段：reader 用桩对象，`MemoryContext` 照建（生命周期管理本版就要正确）。
- 注意 `eflags & EXEC_FLAG_EXPLAIN_ONLY` 时不开真实资源。

### 5.6 `IterateForeignScan`（行式骨架）

- 职责："批缓存 + 逐行吐 slot"控制流（doc 2 §4.2.2）：批内 `next_tuple++`；耗尽则 `fetch_more_data`；`fetch_more_data` 返回 EOF 则 `ExecClearTuple`。
- 骨架阶段：`fetch_more_data` 造 N 行 mock `HeapTuple`（按外表 `tupdesc` 填常量），验证逐行返回与 EOF。
- 下半层：把 mock 换成 `IcebergReaderNextBatch → ArrowColumnToDatums`（doc 2 §6.3）。

### 5.7 `VecIterateForeignScan`（向量化骨架）

- 职责：返回一个 `VectorBatch*`（入参 `VecForeignScanState*`）；耗尽返回空批/NULL（按 GaussVector 向量执行器约定，§2.4 复核）。
- 骨架阶段：构造一个 `m_rows = N` 的 mock `VectorBatch`，每列填常量、`m_flag` 全 NOTNULL，验证向量算子能消费。
- 下半层：`ArrowColumnToScalarVector`（doc 2 §6.4），定长 64 位列整列 memcpy。

### 5.8 `EndForeignScan` / `ReScanForeignScan`

- `EndForeignScan`：关 reader、`MemoryContextDelete(batch_cxt)`；桩阶段同样要释放，避免泄漏被后续误判。
- `ReScanForeignScan`：重置 task 游标与批游标，重开第一个 reader；本版做最小实现以支持子计划重扫。

### 5.9 `ValidateTableDef`（table DDL 接入点）

- 本版只放空实现或最小校验占位。**[接入点]** 支持 table create 时，在此校验 Iceberg 外表的 OPTIONS 组合（namespace 必须存在、location 合法等），并与控制面 `iceberg_create_table` 协同。namespace 不经此回调。

## 6. fdw_private 与扫描状态结构

### 6.1 `fdw_private` 编码（规划→执行的桥）

沿用 pg_lake `FdwScanPrivateIndex` 模式（doc 2 §3.2），但替换 DuckDB SQL 项：

```c
enum IcebergScanPrivateIndex {
    IcebergPrivFileScanTasks,   /* FileScanTask 列表：文件路径 + 投影 field_id + 残差谓词 */
    IcebergPrivRetrievedAttrs,  /* 投影列属性号 List<int> */
    IcebergPrivResidualQuals,   /* 执行期重过滤的 local 谓词 */
    IcebergPrivFieldIdMap       /* field_id → 外表属性号映射（schema evolution 对齐） */
};
```

### 6.2 扫描状态结构（行式 + 向量化共用主体）

精简 pg_lake `PgLakeScanState`（doc 2 §3.3），去掉 DuckDB 连接与文本回填字段，新增 SDK reader 与 Arrow 批字段：

```c
typedef struct IcebergScanState {
    Relation        rel;
    TupleDesc       tupdesc;
    List           *fileScanTasks;   /* 解码自 fdw_private */
    List           *retrievedAttrs;
    int            *fieldIdMap;

    void           *reader;          /* SDK Parquet reader 句柄（骨架阶段为桩） */
    /* 批缓存游标（行式） */
    HeapTuple      *tuples;
    int             num_tuples;
    int             next_tuple;
    bool            eof_reached;

    MemoryContext   batch_cxt;       /* 每批 reset 一次性回收 */
    MemoryContext   temp_cxt;
} IcebergScanState;
```

向量化路径复用同结构，`VecIterateForeignScan` 直接产出 `VectorBatch`（不经 `tuples[]`）。`reader`/`fileScanTasks`/`fieldIdMap` 两路共用，故 `BeginForeignScan` 一次初始化即可服务两个迭代入口。

## 7. Catalog 接入抽象（数据面↔控制面边界）

routine 上半层只需要一个**只读解析入口**；控制面（未来）在同一抽象上加写操作。本版先定义读侧，写侧留接入点。

```c
typedef enum { ICEBERG_CATALOG_PG_NATIVE, ICEBERG_CATALOG_REST } IcebergCatalogKind;

typedef struct IcebergCatalog {
    IcebergCatalogKind kind;
    void *backendCtx;            /* pg_native: schema 名；rest: host/prefix/token */
} IcebergCatalog;

/* 数据面（本版需要）：外表 → metadata_location + schema */
IcebergResolved *IcebergCatalogResolveTable(IcebergCatalog *cat,
                                            const char *ns, const char *table);

/* 控制面（接入点，本版不实现）：
 *   [接入点] 支持 namespace 时增加：ListNamespaces/CreateNamespace/LoadNamespace/
 *            NamespaceExists/DropNamespace/UpdateNamespaceProperties
 *   [接入点] 支持 table 时增加：ListTables/CreateTable/LoadTable/TableExists/
 *            DropTable/CommitTable（CAS on metadata_location）
 */
```

- **pg_native 后端**：`IcebergCatalogResolveTable` 走 SPI 查 `iceberg_catalog.tables`（GaussVector 设计 §6.2）取 `metadata_location`、`current_schema_id` 等；schema 从 `table_schemas` 缓存取。骨架阶段允许先手工 `INSERT` 一行喂它。
- **rest 后端**：HTTP 调 `GET /v1/{prefix}/namespaces/{ns}/tables/{table}`（移植 pg_lake `rest_catalog`），解析 `metadata-location`。
- 后端由 server OPTIONS `catalog_kind` 选择，validator 校验。

这一抽象是数据面与控制面的唯一边界：上半层 routine 只调 `ResolveTable`；namespace/table 控制面 SQL 在同一结构上挂写操作，互不穿透。

## 8. Iceberg ↔ PG 类型映射（下半层边界，参考）

> 类型映射属数据面**下半层**（`arrow → tuple/vectorbatch` 转换时消费），本版不实现转换内核，仅保留映射表作为上半层 `tupdesc`/投影对齐与下一版落地的参考基准。读路径明细见 doc 1 §4.2、doc 2 §6.3.3；此处给双向静态映射，详细转换算法（`ArrowColumnToDatums` / `ArrowColumnToScalarVector`、纪元偏移、varlena 包装）留待下半层版本。

**读路径 Iceberg → Arrow → PG**（权威映射，合并 doc 1/2）：

| Iceberg | Arrow format | PG / OID | 要点 |
|---|---|---|---|
| boolean | `b` | bool | bit-packed |
| int / long | `i` / `l` | int4 / int8 | 零拷贝 |
| float / double | `f` / `g` | float4 / float8 | 直读 |
| decimal(P,S) | `d:P,S` | numeric | `ToString(S)`→`numeric_in`，typmod=`((P<<16)|S)+VARHDRSZ` |
| date | `tdD` | date | 天偏移 **−10957** |
| time | `ttu:` | time | µs since midnight |
| timestamp / timestamptz | `tsu:` / `tsU:` | timestamp(tz) | µs 偏移 **−946684800000000** |
| string / binary | `u`/`z` | text / bytea | 切片拷入 `batch_cxt` |
| uuid | `w:16` | uuid | 16B 直拷 |
| list / map·struct | `+l` / `+m`·`+s` | array / jsonb | 递归 |

**写/DDL 路径 PG → Iceberg**（未来 table create 用，新增）：要点是 `numeric` 必须有 typmod 才能映射 `decimal(P,S)`，无 typmod 报错；`int2→int`、`varchar→string`（丢长度）；`jsonb`/复合类型首期拒绝自动推断。遵循"无法无损映射就报错，不静默近似"（doc 2 §6.3.4 同款原则）。

## 11. 扩展空间

本版刻意只做数据面上半层骨架。后续在本文续写时，按以下接入点扩展，**不改动已定的 routine 接线**：

- **下半层（arrow→tuple/vectorbatch 转换）**：只替换 §5.6/§5.7 的 `fetch_more_data` 内核与 `VecIterate` 内核，落地 §8 类型映射的转换算法。routine 注册、`fdw_private`、扫描态不变。
- **namespace 控制面**：在 §7 `IcebergCatalog` 上增加 namespace 操作集（List/Create/Load/Exists/Drop/UpdateProperties），并新增 6 个 `CREATE FUNCTION ... LANGUAGE C` SQL 函数。**对 routine 零接触**（namespace 不被扫描）。底座为 GaussVector 设计的 `namespaces` 表与 `iceberg_namespace_properties` 兼容视图。
- **table 控制面**：在 §7 增加 table 操作集（list/create/load/exists/drop/commit，commit 走 `metadata_location` CAS，对应 GaussVector §8.4）；`iceberg_create_table` 决定"纯 DDL"或"函数托管建外表"模型，并实现 §5.9 `ValidateTableDef`。table create 依赖 §8 的 PG→Iceberg 类型映射。
- **下推与写路径**：`GetForeignPaths` 增参数化/有序路径；`classifyConditions` 真正下推谓词到 SDK `Scan().Filter()`；写路径按需补 Modify 回调（openGauss 逐行模型）。

每个接入点都对应本文已标注的 **[接入点]** 位置，可在对应小节就地补充，保持单文档可断点继续。
