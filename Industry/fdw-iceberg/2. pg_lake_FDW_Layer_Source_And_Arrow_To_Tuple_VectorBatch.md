## 1. 通路辨析与文档定位

### 1.1 三条通路对比

理解本文的前提是把三条数据通路区分清楚。

**通路 A：pg_lake 的真实执行通路（文本路径）**

pg_lake FDW 进程把扫描翻译成 SQL，交给独立进程 `pgduck_server`（DuckDB）执行，结果经 **PostgreSQL wire protocol 以文本行** 传回，再用 `PQgetvalue()` + `InputFunctionCall()` 逐列解析为 `Datum`：

```
DuckDB DataChunk（列式）
  → 逐行逐列 to_text()
  → wire protocol（行式文本）
  → FDW: PQgetvalue → InputFunctionCall → Datum
  → heap_form_tuple → HeapTuple
```

证据：`pg_lake_table.c:5462–5619`（`make_tuple_from_result_row`，`PQgetvalue` / `InputFunctionCall` / `heap_form_tuple`）、`:3377–3440`（`fetch_more_data`，消费 `PGresult`）。

**通路 B：本项目选取的通路（Arrow 直读）**

GaussVector 进程内直接调用 Iceberg SDK，读 Parquet 后以 Arrow 批次返回，FDW 直接读 buffer 指针转换为执行器所需格式：

```
Iceberg SDK 读 Parquet
  → Arrow C Data Interface（ArrowArray + ArrowSchema，进程内传指针）
  → FDW 直接读 buffer
  → 行式：tuples[]（HeapTuple）→ TupleTableSlot
    列式：VectorBatch（ScalarVector[]）
```

**通路 C：向量化 FDW 理想形态（参考）**

若 GaussDB 已有向量化执行引擎，FDW 直接输出 VectorBatch，上层向量算子零转换消费（见《arrow-c-data-interface-and-iceberg-sdk.md》§4）。本项目的通路 B 列式路径是这条路的工程实现。

### 1.2 各章对应关系

```
第 2 章  ── 通用 FDW 机制 + 接口全景（general FDW 视角）
第 3–5 章 ── pg_lake 的具体实现（pg_lake 视角，含特殊结构）
第 6 章  ── 本项目设计（GaussVector 视角，通路 B）
```

## 2. FDW 接口体系

### 2.1 通用 FDW 机制

**通用 FDW（Foreign Data Wrapper）** 是 PostgreSQL/GaussDB 的标准扩展机制，允许把外部数据源以"外表（foreign table）"的方式暴露给 SQL 引擎。核心是实现 `FdwRoutine` 结构体中的若干回调函数，由执行器在对应阶段调用。

FDW 开发者需要在 handler 函数中注册各回调指针，未使用的回调置 `NULL`。对于只读 Foreign Scan，核心是 Scan 类的 6 个回调（规划 3 个 + 执行 3 个）；写路径、下推、并行、异步等各有对应的扩展回调组。

### 2.3 本项目实现范围

本项目第一阶段为**只读 Foreign Scan**，实现以下 **6 个接口**（P0 核心路径，表中粗体 ✅）：

## 3. pg_lake FDW 层：源码结构与关键数据结构

### 3.1 扩展模块组织

pg_lake 的 FDW 层位于 `pg_lake_table` 扩展。与 FDW 回调及扫描/写执行直接相关的源码：

```
pg_lake_table/src/fdw/
├── pg_lake_table.c          # FdwRoutine 注册 + 全部 scan/modify 回调（~5900 行，核心）
├── snapshot.c               # CreatePgLakeScanSnapshot：relation → 文件级快照
├── data_file_pruning.c      # 文件级谓词裁剪（分区/统计）
├── partition_transform.c    # identity/bucket/truncate/year/month/day/hour 分区变换
├── deparse.c                # PG plan → SQL 字符串（下推给 DuckDB 执行引擎）
├── writable_table.c         # INSERT/UPDATE/DELETE 写路径
├── position_delete_dest.c   # position delete 写出
├── row_ids.c                # (filename, file_row_number) 行定位编解码
├── shippable.c              # 表达式是否可下推到远端判定
└── schema_operations/       # field_id 映射注册（schema evolution）

pg_lake_table/src/planner/
├── query_pushdown.c         # LakeTablePlanner：full query pushdown → CustomScan
└── restriction_collector.c  # 收集 restriction 供执行期文件裁剪

pg_lake_table/src/transaction/
├── transaction_hooks.c                 # XACT_EVENT_PRE_COMMIT / COMMIT 钩子
└── track_iceberg_metadata_changes.c    # 事务内累计 metadata 变化

pg_lake_table/include/pg_lake/fdw/snapshot.h   # 文件快照结构定义
```

`FdwRoutine` 在 `pg_lake_table_handler()` 中注册（`pg_lake_table.c:536–598`）。以接口全景表的视角看 pg_lake 的注册情况：Scan 类全部实现；Modify 类全部实现；DirectModify 全部 NULL；`ExecForeignBatchInsert` / `GetForeignModifyBatchSize` NULL（无 FDW 批量写接口）；Join / Upper 下推已实现；异步执行全部 NULL。

### 3.2 `fdw_private` 编码（规划 → 执行的桥）

**通用 FDW 规范** 规定：规划阶段可将执行期所需的任意信息序列化为 `List *fdw_private`，挂在 `ForeignScan` 节点上，执行阶段的 `BeginForeignScan` 从中解码。编码格式完全由 FDW 自定义。

**pg_lake 的实现**（`pg_lake_table.c:122–140, 1504–1511`）：

```c
enum FdwScanPrivateIndex {
    FdwScanPrivateSelectSql,       /* 下推给 DuckDB 的 SQL 模板（String 节点） */
    FdwScanPrivateRetrievedAttrs,  /* SELECT 取回的列属性号 List<int> */
    FdwScanPrivateRteList,         /* relation RTE 列表 */
    FdwScanPrivateRestrictions,    /* relation 上的 restriction（谓词），供执行期裁文件 */
    FdwScanPrivateRelations        /* join 描述（仅 join/upper 时追加） */
};

/* GetForeignPlan 编码 */
fdw_private = list_make4(makeString(sql.data),  /* SQL 模板 */
                         retrieved_attrs,        /* 取回列 */
                         rteList,               /* RTE */
                         restrictionList);      /* 谓词 */

/* BeginForeignScan 解码 */
fsstate->query = strVal(list_nth(fsplan->fdw_private, FdwScanPrivateSelectSql));
```

pg_lake 把"下推 SQL 模板"作为核心载体——这是 DuckDB 路径的特有设计，SQL 在执行期会经 `ReplaceReadTableFunctionCalls()` 把 `read_table()` 占位替换为实际文件路径列表后发往 pgduck_server。

**本项目改造点**：`FdwScanPrivateSelectSql`（DuckDB SQL）在无 DuckDB 方案中无意义，应替换为 **FileScanTask 列表（文件路径集合）+ 投影 field_id 列表 + 残差谓词**。`RetrievedAttrs` 和 `Restrictions` 仍保留（投影列号 + 文件裁剪谓词）。

### 3.3 `PgLakeScanState`（扫描执行态）

**通用 FDW 规范** 要求 `BeginForeignScan` 将执行期状态挂在 `node->fdw_state`，后续 `IterateForeignScan` / `EndForeignScan` 通过它访问。状态结构完全由 FDW 自定义。

**pg_lake 的实现**（`pg_lake_table.c:145–200`）：

```c
typedef struct PgLakeScanState {
    Relation       rel;            /* 外表 relcache */
    TupleDesc      tupdesc;        /* 扫描元组描述 */
    AttInMetadata *attinmeta;      /* 列输入函数元数据（文本→Datum 用） */

    char          *query;          /* 下推 SQL 文本 */
    List          *retrieved_attrs;/* 取回列属性号 */

    PGDuckConnection *conn;        /* 与 pgduck_server 的连接 ← pg_lake 特有 */
    bool           prepared_statement_sent;

    /* 结果元组批次缓存 */
    HeapTuple     *tuples;         /* 当前批次元组数组 */
    int            num_tuples;     /* 批内元组数 */
    int            next_tuple;     /* 下一个返回的下标 */
    bool           eof_reached;

    MemoryContext  batch_cxt;      /* 批次内存（每批 MemoryContextReset） */
    MemoryContext  temp_cxt;       /* 每元组临时内存 */

    PgLakeScanSnapshot *scanSnapshot;  /* relation → 文件集合快照 */

    /* UPDATE/DELETE 行定位（只读场景不需要） */
    Oid            resultRelationId;
    HTAB          *resultFileIndexes;  /* filename → 文件索引 */
    FmgrInfo       recordInFunction;
    int            rowLocationTypeMod;
    int            fileRowNumberBits;
} PgLakeScanState;
```

**本项目可直接借用的设计**：`tuples[] / num_tuples / next_tuple / eof_reached` 这套"按批缓存、逐行吐出"的游标结构，以及 `batch_cxt`（批次内存，每 fetch 批 `MemoryContextReset` 一次性回收）。本项目把"一个 fetch 批"换成"一个 Arrow RecordBatch"即可。

**本项目去掉的字段**：`conn`（pgduck_server 连接）、`prepared_statement_sent`、`attinmeta`（文本回填用，Arrow 直读不需要），以及 UPDATE/DELETE 相关字段（只读阶段）。**新增的字段**：SDK Parquet reader 句柄、当前 ArrowArray/ArrowSchema 批次、field_id → 属性号映射表。

### 3.4 文件快照三层结构

**通用 FDW** 通常需要在 `BeginForeignScan` 阶段把"外表扫描"落实为"具体文件集合"。pg_lake 为此定义了三层快照结构（`snapshot.h:26–71`）：

```c
/* 单个待扫描文件 */
typedef struct PgLakeFileScan {
    char  *path;            /* 文件路径（S3/OBS URI） */
    int64  rowCount;        /* 行数（-1 = 未知） */
    uint64 deletedRowCount; /* position delete 删掉的行数 */
    bool   allRowsMatch;    /* 整文件均命中（可整体跳过/全收） */
} PgLakeFileScan;

/* 单表的所有待扫描文件 */
typedef struct PgLakeTableScan {
    Oid    relationId;
    int    uniqueRelationIdentifier;
    List  *fileScans;             /* List<PgLakeFileScan> 数据文件 */
    List  *positionDeleteScans;   /* List<PgLakeFileScan> position delete 文件 */
    List  *childScans;
    bool   isUpdateDelete;
} PgLakeTableScan;

/* 整个查询涉及的全部表 */
typedef struct PgLakeScanSnapshot {
    List  *tableScans;            /* List<PgLakeTableScan> */
} PgLakeScanSnapshot;
```

`PgLakeFileScan` 中的 `rowCount / deletedRowCount / allRowsMatch` 正好对应 Iceberg manifest 中每个数据文件条目的 `record_count`、关联 delete 文件信息和谓词全匹配标志，对本项目**完全适用**，不依赖 DuckDB。

## 4. pg_lake FDW 层：读路径实现

### 4.1 规划阶段（`GetForeignRelSize / Paths / Plan`）

**通用 FDW 规范** 的规划三步：`GetForeignRelSize` 估算代价 → `GetForeignPaths` 生成路径 → `GetForeignPlan` 固化计划。

**pg_lake 的实现**（行号均指 `pg_lake_table.c`）：

| Hook | 实现函数 | 行号 | pg_lake 做了什么 |
|------|---------|------|----------------|
| `GetForeignRelSize` | `postgresGetForeignRelSize` | 608 | `classifyConditions` 拆 remote/local 谓词；统计属性号；估算行宽；禁用系统列 / `FOR UPDATE` |
| `GetForeignPaths` | `postgresGetForeignPaths` | 1042 | `create_foreignscan_path` 加基础路径；按 EClass 生成参数化路径；`add_paths_with_pathkeys_for_rel` 有序路径 |
| `GetForeignPlan` | `postgresGetForeignPlan` | 1265 | deparse 出 SQL；`ReplacePgLakeTableWithReadTableFunc` 把表换为 `read_table()` 占位；`PreparePGDuckSQLTemplate` 生成 SQL 模板；编码 `fdw_private`（4 项） |

pg_lake 在 `GetForeignPlan` 中把所有下推逻辑收束为一段 SQL 字符串，这是 DuckDB 路径的核心工件。本项目规划阶段同样保留 `GetForeignRelSize`（代价估算 + 谓词分类）和 `GetForeignPaths`（基础路径生成），但 `GetForeignPlan` 中不再生成 SQL 字符串，改为调 Iceberg SDK 的 `PlanFiles()` 获取 `FileScanTask` 列表并编码进 `fdw_private`。

### 4.2 执行阶段（`Begin / Iterate / End`）

#### 4.2.1 `BeginForeignScan`

**通用 FDW** 在 `BeginForeignScan` 中完成：从 `fdw_private` 解码信息、建立与数据源的连接/打开 reader、分配内存上下文。

**pg_lake 的实现**（`pg_lake_table.c:1640–1839`，关键步骤）：

```c
postgresBeginForeignScan(ForeignScanState *node, int eflags)
{
    fsstate->conn = GetPGDuckConnection();          /* ① 取 pgduck_server 连接 */
    fsstate->query = strVal(...FdwScanPrivateSelectSql...);  /* ② 解码 SQL 模板 */

    fsstate->scanSnapshot =
        CreatePgLakeScanSnapshot(rteList, restrictionList, ...); /* ③ 构造文件快照 */
                                                                 /*   relation → FileScanTask 列表 + 裁剪 */
    /* ④ 建内存上下文 */
    fsstate->batch_cxt = AllocSetContextCreate(...);
    fsstate->temp_cxt  = AllocSetContextCreate(...);

    /* ⑤ 解码 TupleDesc、准备 attinmeta（文本→Datum 转换用） */
    fsstate->tupdesc   = RelationGetDescr(fsstate->rel);
    fsstate->attinmeta = TupleDescGetAttInMetadata(fsstate->tupdesc);
}
```

③ 的核心是 `CreatePgLakeScanSnapshot` → `CreateTableScanForRelation`：对 internal 表走本地 catalog，对 external 表解析 `metadata.json` / manifest，再经 `PruneDataFiles` 按谓词/分区/统计裁剪，最终产出 `fileScans` 列表。

**本项目的改造**：去掉①（无连接），②改为解码 FileScanTask 列表；③保留（文件快照逻辑不变）；④保留；⑤去掉 `attinmeta`，改为准备 SDK reader 句柄 + field_id 映射表。

#### 4.2.2 `IterateForeignScan` 骨架

**通用 FDW 规范** 要求 `IterateForeignScan` 每次返回一行（填好 `TupleTableSlot`）或 NULL（EOF）。pg_lake 采用"批缓存 + 逐行吐出"的经典模式（`pg_lake_table.c:1848–1881`）：

```c
static TupleTableSlot *
postgresIterateForeignScan(ForeignScanState *node)
{
    PgLakeScanState *fsstate = node->fdw_state;
    TupleTableSlot  *slot = node->ss.ss_ScanTupleSlot;

    if (!fsstate->prepared_statement_sent)   /* 首次：向 pgduck_server 发 SQL */
        send_prepared_statement(node);

    if (fsstate->next_tuple >= fsstate->num_tuples) {
        if (!fsstate->eof_reached)
            fetch_more_data(node);           /* 取下一批结果 */
        if (fsstate->next_tuple >= fsstate->num_tuples)
            return ExecClearTuple(slot);     /* EOF */
    }

    ExecStoreHeapTuple(fsstate->tuples[fsstate->next_tuple++], slot, false);
    return slot;
}
```

这个"上层逐行拉取 / 底层按批补给"的控制流是 PostgreSQL 行执行器的标准节奏。**本项目完整保留该骨架**，只把 `send_prepared_statement`（发 SQL）替换为"打开/推进 Iceberg SDK reader"，`fetch_more_data` 的内核替换为"读一个 Arrow RecordBatch 并整批转为 `tuples[]`"。

#### 4.2.3 `fetch_more_data` 与 `make_tuple_from_result_row`（文本路径）

这是 pg_lake 的 DuckDB 路径特有实现，本项目要整体替换的部分。

**pg_lake 现状**（`pg_lake_table.c:3377–3440, 5462–5619`）：

```c
/* fetch_more_data：从 pgduck_server 获取一批结果 */
fetch_more_data:
    MemoryContextReset(batch_cxt);
    res = WaitForResult(conn);           /* 阻塞等 PGresult */
    numrows = PQntuples(res);
    tuples = palloc0(numrows * sizeof(HeapTuple));
    for (i = 0; i < numrows; i++)
        tuples[i] = make_tuple_from_result_row(res, i, ...);

/* make_tuple_from_result_row：把一行文本结果转为 HeapTuple */
make_tuple_from_result_row:
    for each retrieved_attr j:
        valstr = PQgetvalue(res, row, j);                   /* 取文本值 */
        values[i-1] = InputFunctionCall(&attinfuncs[i-1],   /* 文本 → Datum */
                                        valstr, ...);
    tuple = heap_form_tuple(tupdesc, values, nulls);
```

**关键性能问题**：每一列每一行都走一次 `InputFunctionCall`（文本解析），这是 DuckDB + wire protocol 路径无法避免的代价。本项目用 Arrow 直读消灭这一层。

### 4.3 谓词下推与文件裁剪

**通用 FDW** 的谓词下推分两层：规划期把可下推的谓词标记为 `remote_conds`，执行期把不可下推的 `local_conds` 在 PG 侧重新过滤。

**pg_lake 在文件级额外增加了两层裁剪**（见《1.》§4.3）：
- **manifest list 层**：`GetForeignPaths` 阶段，用分区摘要（partition_summary 的 lower/upper bound）裁剪整个 manifest 文件（`partition_transform.c`）。
- **manifest 层**：`GetForeignPlan` 阶段，用每个数据文件的列 min/max statistics 裁剪单个 Parquet 文件（`data_file_pruning.c`）。

**本项目保留这两层**，直接移植 pg_lake 的 `data_file_pruning.c` + `partition_transform.c`；投影/残差谓词额外下推到 Iceberg SDK 的 `Scan().Select().Filter()`，由 Arrow Parquet reader 处理行组级过滤（Parquet row group statistics，第三层）。

### 4.4 pg_lake 特殊设计：pgduck_server 交互

这部分是 pg_lake 独有的、本项目不复用的设计，列出以说明两套方案的结构差异。

pg_lake 在 `GetForeignPlan` 中把 Iceberg 表替换为 DuckDB `read_table()` 函数占位（`ReplacePgLakeTableWithReadTableFunc`），然后在 `BeginForeignScan` 执行时用实际文件路径列表填充（`ReplaceReadTableFunctionCalls`），再通过 `SendQueryWithParams(conn, query, ...)` 发往 pgduck_server（`pg_lake_table.c:3322–3371`）。pgduck_server 是独立进程，实现了 PostgreSQL wire protocol，所以结果以 `PGresult` 行式文本返回。

**双进程原因**：PG 多进程架构（每连接一 worker）使多线程 DuckDB 嵌入不安全，故将 DuckDB 拆为独立进程（详见架构报告 §2.1.1）。本项目进程内直接调用 SDK，不存在这个问题。

## 5. pg_lake FDW 层：写路径（简述）

本篇以只读 Foreign Scan 为主，写路径给出定位坐标供参考。

pg_lake 写路径：逐行 `ExecForeignInsert/Update/Delete`（`writable_table.c`）→ 写出 data/delete file 到对象存储 → `track_iceberg_metadata_changes.c` 在事务内累积变化 → `transaction_hooks.c` 在 `XACT_EVENT_PRE_COMMIT` 统一生成 manifest / snapshot / `metadata.json` 并切换 metadata pointer。

`equality delete` 明确不支持（`external_heavy_asserts.c:736` 直接报错）；`position delete` + `copy-on-write` 支持。事务语义详见架构报告 §5。

## 6. 本项目设计：Iceberg → Arrow → tuple / VectorBatch

### 6.1 整体通路与依赖

```
GaussVector 后端进程（FDW 扩展，进程内）
  ┌─ GetForeignRelSize / Paths / Plan（规划）
  │    → classifyConditions：谓词分类
  │    → SDK PlanFiles()：FileScanTask 列表
  │    → 文件裁剪（data_file_pruning.c 移植）
  │    → fdw_private：FileScanTask + field_id 映射 + 残差谓词
  │
  ├─ BeginForeignScan（初始化）
  │    → 解码 fdw_private
  │    → IcebergReaderOpen()：打开 Parquet reader（Arrow C++ parquet 模块）
  │    → 分配 batch_cxt / temp_cxt
  │
  ├─ IterateForeignScan（逐行返回）
  │    → 批内 next_tuple++ 直到耗尽
  │    → fetch_more_data：IcebergReaderNextBatch() → ArrowArray
  │    → Arrow → tuples[]（行式，见 6.3）
  │       或 Arrow → VectorBatch（列式，见 6.4）
  │
  └─ EndForeignScan（释放）
       → IcebergReaderClose()
       → MemoryContextDelete(batch_cxt)

对象存储（OBS / S3）── Arrow S3FileSystem 或 S3RandomAccessFile 适配
```

SDK 选型要点（详见《1.》§4.5）：元数据解析移植 pg_lake C 代码（C99，低风险）；Parquet 读取用 Arrow C++ parquet 模块（C++17）；**输出首选 Arrow C Data Interface（`ArrowArray` + `ArrowSchema`），避免 `libarrow.so` 进入 GaussVector 内核 ABI**。

### 6.2 规划阶段改造点

**`GetForeignRelSize / Paths`**：与 pg_lake 基本相同——`classifyConditions` 拆谓词、`set_baserel_size_estimates` 估代价、`create_foreignscan_path` 生成基础路径。不需要改动。

**`GetForeignPlan`**：核心改造点。去掉 deparse SQL 和 `read_table()` 占位替换，改为：

```c
/* 调 SDK 规划，获取文件列表（manifest list + manifest 两层裁剪后） */
FileScanTask *tasks = IcebergScanPlanFiles(catalog, scan_spec, remote_exprs);

/* 编码进 fdw_private */
fdw_private = list_make4(

    retrieved_attrs,                 /* 投影列属性号 */
    residual_filter,                 /* 残差谓词（下推到 reader 的行组过滤） */
    field_id_mapping                 /* field_id → 外表属性号映射 */
);
```

### 6.3 Arrow → tuple（行式路径）

#### 6.3.1 Arrow C Data Interface 内存布局

一个标量列的 `ArrowArray`：

- `buffers[0]`：validity bitmap，**1 bit / 行**，`1` = valid（`NULL` 时整个指针可为 `NULL`）
- `buffers[1]`：定长值连续数组（int32/int64/float/double 直接存放）
- `offset`：逻辑切片起点，**读任何 buffer 都必须 `+ array->offset`**

变长列（utf8/binary）：`buffers[1]` = offsets（int32，n+1 个），`buffers[2]` = 连续 data 字节；第 r 行的值范围 = `data[offsets[r]..offsets[r+1])`。

（完整结构见《arrow-c-data-interface-and-iceberg-sdk.md》§2。）

#### 6.3.2 `fetch_more_data` 替换骨架

替换 pg_lake 的 `WaitForResult` + `make_tuple_from_result_row`：

```c
static void
fetch_more_data_arrow(ForeignScanState *node)
{
    PgLakeScanState *fsstate = node->fdw_state;
    MemoryContextReset(fsstate->batch_cxt);
    MemoryContext old = MemoryContextSwitchTo(fsstate->batch_cxt);

    ArrowArray  carr;
    ArrowSchema cschema;

    if (!IcebergReaderNextBatch(fsstate->reader, &carr, &cschema)) {
        fsstate->eof_reached = true;
        fsstate->num_tuples  = 0;
        fsstate->next_tuple  = 0;
    } else {
        int nrows = (int)carr.length;
        fsstate->tuples     = palloc0(nrows * sizeof(HeapTuple));
        fsstate->num_tuples = nrows;
        fsstate->next_tuple = 0;

        /*
         * 列优先：每列整批转为 Datum[]，再逐行 heap_form_tuple。
         * 相比逐行逐列调 Arrow API，减少类型分发次数（参考 parquet_fdw CachingParquetReader）。
         */
        Datum **colvals = palloc(ncols * sizeof(Datum *));
        bool  **colnull = palloc(ncols * sizeof(bool  *));
        for (int c = 0; c < ncols; c++)
            ArrowColumnToDatums(carr.children[proj[c]],
                                cschema.children[proj[c]],
                                typinfo[c], nrows,
                                &colvals[c], &colnull[c]);   /* 见 6.3.3 */

        Datum values[MaxTupleAttributeNumber];
        bool  nulls [MaxTupleAttributeNumber];
        memset(nulls, true, sizeof(nulls));

        for (int r = 0; r < nrows; r++) {
            for (int c = 0; c < ncols; c++) {
                int att = retrieved_attno[c] - 1;
                values[att] = colvals[c][r];
                nulls[att]  = colnull[c][r];
            }
            fsstate->tuples[r] = heap_form_tuple(fsstate->tupdesc, values, nulls);
        }
        carr.release(&carr);   /* 归还 SDK 内存 */
    }
    MemoryContextSwitchTo(old);
}
```

与 pg_lake 的 `make_tuple_from_result_row` 对应，差别只在于把 `PQgetvalue + InputFunctionCall` 换成 `ArrowColumnToDatums`（直读 buffer）。

#### 6.3.3 单列转换：类型分发要点

```c
/* validity bitmap：bit-per-row → bool nulls[] */
const uint8_t *valid = arr->buffers[0];
int off = arr->offset;
for (int r = 0; r < nrows; r++)
    nulls[r] = valid ? !((valid[(off+r)/8] >> ((off+r)&7)) & 1) : false;

/* 按 cschema->format 分发 */
switch (format[0]) {
case 'b': /* bool：值也是 bit-packed */
    for (r) vals[r] = BoolGetDatum((((uint8_t*)arr->buffers[1])[(off+r)/8]
                                     >> ((off+r)&7)) & 1);  break;
case 'i': /* int32 */
    { const int32_t *v = arr->buffers[1];
      for (r) vals[r] = Int32GetDatum(v[off+r]); }          break;
case 'l': /* int64 */
    { const int64_t *v = arr->buffers[1];
      for (r) vals[r] = Int64GetDatum(v[off+r]); }          break;
case 'f': /* float32 */
    { const float *v = arr->buffers[1];
      for (r) vals[r] = Float4GetDatum(v[off+r]); }         break;
case 'g': /* float64 */
    { const double *v = arr->buffers[1];
      for (r) vals[r] = Float8GetDatum(v[off+r]); }         break;
case 'u': /* utf8（字符串） */
    { const int32_t *o = arr->buffers[1];
      const char *data  = arr->buffers[2];
      for (r) { int s=o[off+r], e=o[off+r+1];
                vals[r] = PointerGetDatum(
                    cstring_to_text_with_len(data+s, e-s)); } } break;
/* date32/timestamp/decimal128 见类型映射表 */
}
```

完整类型映射（延续《1.》§4.2）：

| Arrow format | Iceberg 类型 | PG Datum | 注意 |
|---|---|---|---|
| `b` | boolean | `BoolGetDatum` | 值与 null 均为 bit-packed |
| `i` | integer | `Int32GetDatum` | 直读，零拷贝 |
| `l` | long | `Int64GetDatum` | 直读，零拷贝 |
| `f` / `g` | float / double | `Float4/8GetDatum` | 直读 |
| `u` / `z` | string / binary | `cstring_to_text_with_len` / `bytea` | 按 offsets 切片，在 `batch_cxt` 中拷出 |
| `tdD` | date | `DateADTGetDatum(days - 10957)` | 纪元偏移：Unix 1970 → PG 2000，差 10957 天 |
| `ttu:` | time | `TimeADTGetDatum(us)` | 午夜起始微秒，直接使用 |
| `tsu:` | timestamp | `TimestampGetDatum(us - 946684800000000LL)` | 微秒纪元偏移（946684800×10⁶） |
| `tsU:` | timestamptz | 同上（已含 UTC） | 同上 |
| `d:P,S` | decimal(P,S) | `numeric_in(Decimal128::ToString(S))` | 需逐值字符串转换 |
| `w:16` | uuid | 16 字节直拷 → `UUIDGetDatum` | fixed_size_binary(16) |
| `+l` | list\<T\> | `construct_md_array` | 递归处理子 ArrowArray |
| `+s` | struct | `pushJsonbValue` | 映射为 jsonb |

#### 6.3.4 易错点

1. **`array->offset` 必须偏移**：Arrow 批次可能是零拷贝切片，所有 buffer 索引（包括 validity bit）都要加 `array->offset`，忘加导致偏移读错。

2. **变长类型必须拷贝进 `batch_cxt`**：utf8/binary 的 data buffer 属于 SDK，调 `carr.release()` 后立即失效；必须在 `batch_cxt` 中用 `cstring_to_text_with_len` 拷出，生命周期跟随当前 fetch 批。

3. **纪元偏移与精度**：date（10957 天）、timestamp（946684800000000 微秒）的纪元偏移，以及 decimal128 → `numeric` 的 scale 处理，在 pg_lake 里被 DuckDB 文本输出 + `InputFunctionCall` 隐藏，本项目必须显式处理。

4. **field_id 投影对齐**：Iceberg 按 field_id（不是列名/列序）做 schema evolution；`ArrowSchema` 的列序需经 field_id → 外表属性号映射对齐，否则值会写到错列。参考 pg_lake `schema_operations/field_id_mapping_catalog.c`。

5. **批次内存归属**：`tuples[]` 与拷出的变长值都建在 `batch_cxt`；下批 `MemoryContextReset` 一次性回收，不要逐行 `pfree`（代价高且易出错）。

### 6.4 Arrow → VectorBatch（列式路径）

如果 GaussVector 的上层是**向量化执行器**，把 Arrow 批次再"拆成行 HeapTuple"是浪费——应直接产出 **VectorBatch**，让向量算子消费。这是本项目相对 pg_lake（只有行式接口）的核心增量。

#### 6.4.1 VectorBatch / ScalarVector 结构

GaussVector（openGauss 系向量化引擎）的列批核心结构（概念形态）：

```
VectorBatch
  int           m_rows;      // 本批行数（典型 1000~2048）
  int           m_cols;      // 列数
  ScalarVector *m_arr;       // 每列一个 ScalarVector

ScalarVector
  ScalarValue  *m_vals;      // 值数组，ScalarValue == Datum（统一 8 字节槽）
  uint8        *m_flag;      // 每行一个 flag 字节（NULL / 非空，byte-per-row）
  /* 变长值的实际字节缓冲区（类 m_buf） */
  int           m_rows;
  ScalarDesc    m_desc;      // 类型描述（typid、是否定长等）
```

与 Arrow 的关键差异（决定了转换的"对齐成本"）：

| 维度 | Arrow | VectorBatch (ScalarVector) | 转换动作 |
|---|---|---|---|
| **null 表示** | validity bitmap（**bit / 行**） | `m_flag`（**byte / 行**，`SET_NULL/SET_NOTNULL`） | bit → byte 展开（不可省） |
| **值宽度** | 原生宽度（int32 = 4B，bool = bit） | `ScalarValue` 统一 **8B 槽** | 32 位及以下需加宽写入 |
| **定长 64 位** | int64/double 连续数组 | `m_vals` 连续 8B 数组 | 可整列 **memcpy**（最快） |
| **变长值** | offsets 数组 + 连续 data | 每行一个 varlena 指针（指向 buffer） | 切片 + 加 varlena 头拷入 buffer |

#### 6.4.2 转换骨架：列对列

向量化路径新增一个迭代入口（`IterateForeignScanBatch`，对应 openGauss `VecForeignScan` 体系）：

```c
static bool
IterateForeignScanBatch(ForeignScanState *node, VectorBatch *batch)
{
    PgLakeScanState *fsstate = node->fdw_state;
    ArrowArray  carr;
    ArrowSchema cschema;

    if (!IcebergReaderNextBatch(fsstate->reader, &carr, &cschema))
        return false;               /* EOF */

    int nrows = (int)carr.length;
    batch->m_rows = nrows;

    for (int c = 0; c < batch->m_cols; c++) {
        ArrowArray  *acol = carr.children[proj[c]];
        ScalarVector *vec = &batch->m_arr[c];
        vec->m_rows = nrows;
        ArrowColumnToScalarVector(acol, cschema.children[proj[c]],
                                  typinfo[c], nrows, vec);
    }

    /* position delete：转为 selection mask，标记被删行 */
    if (fsstate->hasDeletes)
        ApplyDeletesToBatch(batch, fsstate->deleteBitmap, carr.offset);

    carr.release(&carr);
    return true;
}
```

`ArrowColumnToScalarVector` 按类型分三类处理：

```c
/* 1) null 展开：bit → byte（所有列均需） */
const uint8_t *valid = acol->buffers[0];
int off = acol->offset;
for (int r = 0; r < nrows; r++) {
    if (valid && !((valid[(off+r)/8] >> ((off+r)&7)) & 1))
        SET_NULL(vec->m_flag[r]);
    else
        SET_NOTNULL(vec->m_flag[r]);
}

/* 2a) 64 位定长（int64/double/timestamp）：整列 memcpy */
memcpy(vec->m_vals, (int64_t*)acol->buffers[1] + off, nrows * sizeof(int64_t));
/* timestamp 在此之后逐值减去纪元偏移（或在拷贝循环中顺手做） */

/* 2b) 32 位定长（int32/float/date）：逐行加宽到 8B 槽 */
const int32_t *v = acol->buffers[1];
for (int r = 0; r < nrows; r++)
    vec->m_vals[r] = Int32GetDatum(v[off+r]);   /* date 还要 -10957 */

/* 3) 变长（utf8/binary）：切片 + varlena 头写入 buffer */
const int32_t *o    = acol->buffers[1];
const char    *data = acol->buffers[2];
for (int r = 0; r < nrows; r++) {
    int s = o[off+r], e = o[off+r+1];
    text *t = (text *) ScalarVectorAlloc(vec, VARHDRSZ + (e - s));
    SET_VARSIZE(t, VARHDRSZ + (e - s));
    memcpy(VARDATA(t), data + s, e - s);
    vec->m_vals[r] = PointerGetDatum(t);
}
```

#### 6.4.3 设计要点与权衡

1. **批大小对齐**：Iceberg SDK 支持设置 `with_batch_size`，应对齐到 VectorBatch 的 `BatchMaxSize`（典型 1000/2048），使一个 Arrow batch 直接等于一个 VectorBatch，省去切批逻辑。

2. **定长 64 位列接近零拷贝**：int64/double/timestamptz 与 `ScalarValue` 同宽，整列 `memcpy` 即可（若 Arrow buffer 与 `m_vals` 内存对齐，理论上可让 `m_vals` 直接指向 Arrow buffer，但 Arrow 内存归属 SDK，安全做法是 memcpy 进 batch 自己的内存）。这是向量路径相对 tuple 路径的主要收益。

3. **null 展开不可省**：Arrow bit-per-row 与 VectorBatch byte-per-row 不兼容，必须展开；可用查表（8 bit → 8 byte 的 256 条表项）或 SIMD 加速。

4. **变长列仍需逐值包装**：openGauss text/bytea 是 varlena（带 4B/1B 头），Arrow 是裸 offset+data，必须逐值包装；批量预估 buffer 大小（= `offsets[last] - offsets[first]` + n × VARHDRSZ）一次性分配，减少 malloc 次数。

5. **position delete → selection mask**：Iceberg merge-on-read 的 position delete 最适合表达为 VectorBatch 的 selection mask / 行有效位，不要物理删行，符合向量算子的惯例（参考 §3.4 `deletedRowCount`、《1.》§3.2 iceberg-cxx 的 `first_row_number`）。

6. **decimal128**：openGauss numeric 不是定长，需逐值转换（与 tuple 路径相同），是向量路径里最贵的列类型；若性能敏感，可考虑用 int128 物理列 + scale 元数据延迟物化为 numeric。

7. **两套迭代接口共存**：行式 `IterateForeignScan` 返回 `TupleTableSlot`；向量化 `IterateForeignScanBatch` 返回 `VectorBatch`。两者共享 `BeginForeignScan` 建立的 reader 和文件快照，执行器按自身类型选择调哪个入口。

### 6.5 两条路径对比与落地建议

| 维度 | Arrow → tuple（行式，§6.3） | Arrow → VectorBatch（列式，§6.4） |
|---|---|---|
| 上层执行器 | 行式（标准 `ForeignScan`） | 向量化（`VecForeignScan`） |
| 每批产物 | `HeapTuple[]` → 逐行 `TupleTableSlot` | 一个 `VectorBatch`（列对列） |
| 定长 64 位列 | 逐行 `Int64GetDatum` | 整列 `memcpy`（最优） |
| 定长 32 位列 | 逐行 `Int32GetDatum` | 逐行加宽到 8B 槽 |
| null 处理 | 逐行写 `nulls[]` bool | bit → byte 展开 `m_flag` |
| 变长列 | 逐值 `cstring_to_text_with_len` | 逐值 varlena 包装到 buffer |
| 与 pg_lake 关系 | 替换 `fetch_more_data` 内核 | pg_lake 无此路径，本项目新增 |
| 实现复杂度 | 低（骨架直接复用 pg_lake） | 中（需新增向量迭代接口） |
| 性能收益 | 去文本化，消除 `InputFunctionCall` | 定长列整列 memcpy，向量算子端到端收益 |

**落地建议**：

- **P0：先做 Arrow → tuple**。替换 `fetch_more_data`/`make_tuple_from_result_row` 的文本内核为 Arrow 直读，保留 pg_lake FDW 骨架（回调注册、`fdw_private`、文件快照、`batch_cxt` 游标、`IterateForeignScan` 控制流）。这一步消灭 DuckDB sidecar 和 wire protocol 文本开销，改动面最小，可优先验证正确性。

- **P1：再做 Arrow → VectorBatch**。在 GaussVector 向量化执行器存在的前提下，新增向量迭代回调，定长列走整列 memcpy，position delete 走 selection mask。这是相对 pg_lake 最核心的增量价值。

- **复用 pg_lake C 资产**：metadata.json / manifest Avro 解析（`pg_lake_iceberg/src/iceberg/`、`src/avro/`）、文件裁剪（`data_file_pruning.c`）、field_id 映射（`schema_operations/`）、`PgLakeScanSnapshot` 文件快照结构——均与执行引擎无关，可直接移植。

- **统一 Arrow 输出接口**：无论 SDK 是 iceberg-cpp（C Data Interface 原生）还是基于 Arrow C++ 的 reader，FDW 侧统一收 `ArrowArray`/`ArrowSchema`，使 §6.3/§6.4 的转换层与 SDK 选型解耦（与《1.》§3 结论一致）。
