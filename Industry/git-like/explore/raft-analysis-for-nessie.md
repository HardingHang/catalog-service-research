# Nessie 引入 Raft 的可行性分析：OCC vs Raft 的理论边界与工程实践

> 分析视角：在职数据库架构师
> 目标读者：对分布式一致性有基础认知、但不确定 Raft 是否适用于 Catalog 场景的工程师
> 生成日期：2026-05-15

---

## 1. 核心问题

Nessie 用 OCC + CAS（乐观锁）保证一致性。另一条路线是基于 Raft/Paxos 的共识机制。两条路线的性能边界（何时该选哪条）没有研究。

本报告不仅回答"Catalog 该选 OCC 还是 Raft"，更系统梳理 Raft 的基础原理、适用边界，以及在 Nessie 中的合理用法。

---

## 2. Raft 基础原理

### 2.1 核心角色

Raft 将节点分为三种角色：

```
用户A ──┐
用户B ──┼──→ Leader 节点 ──→ Follower A
用户C ──┘      （3个节点组成一个 Raft group）
                     Follower B
```

- **Leader**：唯一接收写请求的节点，负责将日志复制到 Follower。
- **Follower**：被动接收 Leader 的日志复制，不处理客户端写请求。
- **Candidate**：Leader 失联时，Follower 变为 Candidate 发起选举。

客户端（用户）**不是** Raft 成员，只是向 Leader 发送请求的外部调用方。

### 2.2 日志复制流程

Raft 保证一致性的核心机制：

1. **Leader 接收请求**：客户端的写请求必须发送到 Leader。
2. **追加本地日志**：Leader 将请求作为新日志条目追加到自己的日志末尾，分配递增的 `logIndex`。
3. **并行复制到 Follower**：Leader 通过 AppendEntries RPC 将日志并发发送给所有 Follower。
4. **多数派确认**：当 Leader 收到超过半数节点（含自己）的确认后，该日志被标记为 **committed**。
5. **应用到状态机**：所有节点按 `logIndex` 顺序将 committed 日志应用到本地状态机。
6. **返回客户端**：Leader 通知客户端操作成功。

由于所有节点按相同的 `logIndex` 顺序执行，天然保证强一致性。

### 2.3 Leader 选举与故障恢复

- Leader 周期性发送心跳（heartbeat）给 Follower。
- 如果 Follower 在超时时间内（通常 150–300ms）未收到心跳，则变为 Candidate，发起新一轮选举。
- Candidate 需要获得**超过半数**的投票才能成为新 Leader。
- 选举期间（通常 1–10 秒），集群不可用写服务。

### 2.4 适用前提

Raft 只在**多节点独立存储**场景下才有意义：

| 部署模式 | 是否需要 Raft | 一致性由谁保证 |
|---------|-------------|--------------|
| 单节点 + PostgreSQL | **不需要** | PostgreSQL 的单机事务（ACID） |
| 多节点 + 共享 PostgreSQL | **不需要** | 数据库事务 + 应用层 CAS |
| 多节点 + 每个节点独立存储 | **需要** | Raft 保证多副本日志一致 |

Nessie 当前属于第二行：多个 Nessie 实例共享一个 PostgreSQL/MongoDB。**引入 Raft 意味着要从"共享存储"架构改为"每个节点独立存数据"的架构**，改动量巨大。

### 2.5 Leader 瓶颈

Raft 的 Leader 是**硬瓶颈**，所有写请求都必须经过它：

| 客户端并发数 | Leader 的行为 | 平均 commit latency（经验估算） |
|-------------|-------------|-------------------------------|
| 10 | 直接处理，几乎无排队 | ~1ms |
| 100 | 轻微排队，CPU 满载 | ~5ms |
| 1,000 | 严重排队，Follower 复制跟不上 | ~50ms |
| 10,000 | 队列溢出，大量超时 | 超时/失败 |

> 注：以上数据为基于 Raft 论文和 etcd 工程实践的经验估算，非 Nessie 实测数据。实际延迟还受网络带宽、磁盘 I/O、日志大小等因素影响。

Raft 无法通过加机器水平扩展写吞吐——写永远只能走 Leader。真正支持高并发的系统（如 TiKV、Kafka）靠的是**将数据分片，每个分片独立的 Raft group/Partition**，从而把负载分散到多个 Leader。

**Raft 适合的是"需要强一致复制的元数据场景"（如配置中心、服务发现），不是"高并发写场景"。**

## 3. OCC 与 Raft 的本质分野

要正确回答"Catalog 该选 OCC 还是 Raft"，首先需要厘清两者的本质分工：

| 维度 | OCC（乐观并发控制） | Raft（复制协议） |
|------|-------------------|----------------|
| **核心问题** | 多个事务并发修改同一数据时如何协调 | 多个副本如何就日志顺序达成一致 |
| **写频率** | 低（每分钟几次） | 中低（Raft 本身不限制频率，但 Leader 是瓶颈） |
| **读写比** | 读占 99%+ | 读写均衡 |
| **冲突分布** | 集中在少数 key | 分散在多 key/多表 |
| **网络延迟** | 单集群，RTT <1ms | 跨地域，RTT >50ms |
| **故障恢复要求** | 依赖底层数据库 HA | 需要应用层自动切换（RTO <5s） |
| **数据量/次** | 极小（KB 级元数据） | 大（业务数据） |

**OCC 的适用场景**：写频率极低、读占绝对主导、冲突概率低（通过分片或 striped lock 将冲突分散）、本地操作低延迟优先、冲突后可廉价重试。典型系统：Nessie Catalog（靠 151-way striped lock 将 reference pointer 的冲突概率降到极低）、Redis 乐观锁、MongoDB CAS 更新。

**Raft 的适用场景**：多副本强一致、需要自动故障转移、写操作需要全局顺序、跨地域多主写入、数据需要多副本冗余。典型系统：etcd、TiKV、Consul、ZooKeeper。

**两者并非互斥**：TiDB 用 Raft 做副本复制 + MVCC/2PC 做并发控制；Minerva (SIGMOD 2026) 用 OCC 做并发控制 + 异步 Raft 做跨地域复制。Catalog 的问题不是"二选一"，而是判断当前工作负载落在哪个象限。

## 4. Catalog（Nessie）场景下的理论边界

### 4.1 工作负载特征：Catalog 与通用数据库的根本差异

| 特征 | Catalog (Nessie) | 通用数据库 (TPC-C) |
|------|-----------------|-------------------|
| 写频率 | 每分钟几次 | 每秒数万次 |
| 单次写数据量 | 几 KB 元数据 | 数十 KB 业务数据 |
| 冲突集中度 | 99% 在 reference pointer CAS | 广泛分布在多表多行 |
| 读写比 | 读占 99.9% | 读写均衡 |

在这个模型下：
- **OCC 的优点**：无 leader 瓶颈，本地操作延迟低（<1ms），Nessie 的 151-way striped lock 已将冲突概率降到极低。
- **Raft 的缺点**：所有写经过 leader，leader 成为瓶颈；leader 选举期间写中断（1–10秒）；对于低频写场景，这些 overhead 完全是浪费。

### 4.2 直接结论：Catalog 场景下，OCC 比 Raft 更合适

**原因不是"OCC 比 Raft 更好"，而是"Catalog 的工作负载特征与 Raft 的设计假设不匹配"**：

- Raft 假设"写操作需要全局顺序、多副本强一致"。Catalog 的写（commit）虽然需要顺序，但底层数据库的单机事务已经保证了这一点，不需要跨节点共识。
- Raft 假设"系统需要自动故障转移"。Nessie 的故障转移由底层数据库（PostgreSQL HA / MongoDB ReplicaSet）保证，应用层不需要再实现一套。
- Raft 假设"数据需要冗余在多个节点"。Nessie 的数据存在共享数据库中，Nessie 服务器本身是无状态的，挂一个实例不会影响数据。

### 4.3 唯一可能 Raft 更优的场景

跨地域多主数据中心（纽约/伦敦/新加坡同时可写）。此时 OCC 的跨地域 RTT（~100ms）会让重试代价变得可感知。

但即使在这个场景，Minerva (arXiv:2602.21566, 投稿至 SIGMOD 2026) 的"OCC + 异步共识"混合架构也比纯 Raft 更优。

## 5. 混合架构探索

### 5.1 已被否定的方案：branch 内 Raft，跨 branch OCC

一种直觉上的混合思路是"branch 内用 Raft 保证顺序，branch 间用 OCC 处理独立操作"。但深入分析后，这个方案在理论和工程上都不成立：

**不成立的原因**：
1. **Raft 只保证日志顺序，不解决语义冲突**。如果两个客户端同时修改同一个 `ContentKey`，Raft 会按 logIndex 顺序执行两个 commit，可能导致第二个覆盖第一个（lost update）。数据库中 Raft 只复制事务日志，冲突检测由上层（MVCC / 2PL / OCC）负责。"branch 内 Raft"仍需叠加并发控制，复杂度翻倍。
2. **Leader 瓶颈无法绕过**。`main` branch 只有一个 Leader，所有对 `main` 的 commit 都需经过它。而 `main` 是高频操作目标，这个 Leader 会成为全局瓶颈。
3. **branch 数量不可控**。Nessie 的 branch 可能成千上万，每个 branch 一个 Raft group 的心跳、选举、日志复制开销不可接受。TiKV 的 Region 是系统内部分片（通常 96MB 一个），而 Nessie 的 branch 是用户创建的，数量无上限。
4. **单集群下无收益**。Nessie 当前共享数据库架构已经能保证 commit 的顺序和持久化，引入 Raft 没有解决任何实际问题。

**结论**："branch 内 Raft"不是"待验证的假设"，而是"理论上就有明显缺陷的方案"，不应被采纳。

### 5.2 方案一：跨地域多活复制（Minerva 模式）——最现实

**场景**：Nessie 在纽约、伦敦、新加坡各部署一个实例（三地共享底层数据库的跨地域复制，或各自拥有独立数据库但需要数据同步），三地数据工程师都需要在本地执行写入。

**问题**：纯 OCC 下，新加坡工程师修改 `main` branch，伦敦工程师几乎同时修改同一 `ContentKey`，冲突后需要跨地域重试（RTT ~150ms），体验极差。注意：Nessie 当前架构不支持真正的"多主写入"，此场景假设的是改造后的跨地域部署。

**架构**：

```
┌─────────────┐      Raft 日志复制      ┌─────────────┐
│  纽约集群    │  ════════════════════  │  伦敦集群    │
│  OCC + CAS   │  （异步，容忍秒级延迟）  │  OCC + CAS   │
│  本地 Leader │◄──────────────────────►│  本地 Leader │
└──────┬──────┘                        └──────┬──────┘
       │                                      │
       │         ┌─────────────┐             │
       └────────►│  新加坡集群  │◄────────────┘
                 │  OCC + CAS   │
                 │  本地 Leader │
                 └─────────────┘
```

- **本地层**：每个地域保留现有 OCC + CAS，P99 commit latency 仍 <10ms。
- **复制层**：本地 commit 成功后，异步写入跨地域 Raft 日志（单 Raft group 管理三地副本）。
- **冲突处理**：异地副本间的冲突用 MWIS 算法（Minerva）选择非冲突事务子集，确定性重执行。
- **一致性保证**：异地副本是最终一致（异步复制），但 Raft 保证三地最终会收敛到相同状态。

**为什么合理**：Raft 不负责本地高并发的 commit 排序（本地 OCC 已足够），只负责**跨地域的日志收敛**——这是 Raft 的强项。

### 5.3 方案二：全局配置与策略的强一致存储

**场景**：Nessie 的全局配置（如访问控制策略、存储后端路由、Feature Flag）变更很少，但一旦变更，所有节点必须立即看到一致状态。

**当前问题**：这些配置存在共享数据库中，依赖数据库的同步复制。如果数据库主从延迟，不同 Nessie 节点可能看到不同的配置。

**架构**：

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│ Nessie 节点A │     │ Nessie 节点B │     │ Nessie 节点C │
│  业务数据    │     │  业务数据    │     │  业务数据    │
│  (OCC+DB)   │     │  (OCC+DB)   │     │  (OCC+DB)   │
└──────┬──────┘     └──────┬──────┘     └──────┬──────┘
       │                   │                   │
       └───────────────────┼───────────────────┘
                           ▼
                  ┌─────────────────┐
                  │  独立 Raft group │  ◄── 仅存储全局配置
                  │  (3–5 节点)     │      如 ACL、路由策略
                  └─────────────────┘
```

- **业务数据路径**：仍走现有 OCC + 共享数据库，不受 Raft 影响。
- **配置路径**：全局配置存储在独立的 Raft group（类似内嵌 etcd）中。
- **读配置**：每个 Nessie 节点本地缓存配置，从本地 Raft Follower 读取（强一致，无跨网络）。
- **写配置**：发送到 Raft Leader，多数派确认后立即生效。

**为什么合理**：配置变更频率极低（每天几次），不会触发 Raft Leader 瓶颈；同时全局配置需要强一致，Raft 恰好满足。

### 5.4 方案三：审计日志的不可篡改存储

**场景**：金融、医疗等合规场景要求 Nessie 的所有操作（谁、何时、修改了什么）必须不可篡改、可审计。

**架构**：

```
用户 commit ──→ Nessie OCC + DB ──→ 业务成功返回
                      │
                      ▼
              ┌──────────────┐
              │  Raft 审计链  │  ◄── 仅追加，不可删除
              │  (专用节点)   │      每条操作一个 log entry
              └──────────────┘
```

- Nessie 的每次 commit/merge/transplant 操作，除了写入业务数据库，还追加一条记录到独立的 Raft 审计链。
- Raft 的日志不可变性保证审计记录无法被后续修改或删除。
- 审计链的节点可以与业务节点分离，由合规团队独立运维。

**为什么合理**：审计日志是 append-only、低频、不可变的，完美契合 Raft 的日志语义。且与业务路径解耦，不影响性能。

### 5.5 核心原则与总结

| 方案 | Raft 的使用位置 | 是否影响业务路径 | 适用场景 |
|------|---------------|---------------|---------|
| **Minerva 跨地域复制** | 异地日志收敛层 | **否**（本地仍走 OCC） | 跨地域多活 |
| **全局配置存储** | 独立配置子系统 | **否**（业务数据仍走 DB） | 强一致全局策略 |
| **审计日志链** | 独立审计子系统 | **否**（异步追加） | 合规审计 |

**核心原则**：Raft 在 Nessie 中的合理用法是**作为辅助子系统**（跨地域复制、配置中心、审计链），**永远不要进入高频业务数据路径**（commit/merge/reference update）。业务数据路径上，OCC + 共享数据库是当前最优解。

## 6. 与 Catalog 场景相关的研究进展

**直接针对 Catalog/元数据一致性协议的学术研究极少**。现有分布式事务论文几乎全部使用 YCSB/TPC-C 等通用数据库 workload，与 Nessie 的 Catalog 工作负载（低频写、单 Key 冲突、读占 99.9%）完全不匹配。以下仅列出思路上有参考价值的进展，并明确标注其与 Catalog 场景的适配度：

| 论文/系统 | 核心贡献 | 与 Catalog 的适配度 | 说明 |
|-----------|---------|-------------------|------|
| **Minerva (arXiv:2602.21566)** | OCC + 异步 Raft 混合架构，MWIS 冲突解决 | **中** | 架构思路（分层使用 OCC 和 Raft）可直接借鉴，但其 benchmark 基于 TPC-C，吞吐数据不适用于 Catalog |
| **etcd / Consul 工程实践** | Raft 用于配置元数据的强一致存储 | **高** | 配置中心的工作负载（低频写、读主导、小数据量）与 Catalog 高度相似，验证了 Raft 在元数据场景的边界条件 |
| **TiKV / CockroachDB** | 多 Raft group 实现水平扩展 | **低** | 数据可分片，但 Catalog 的 branch 是不可分片的单 Key 空间，其分片策略无法复用 |
| **CRDT 版本控制（Evo, Loro）** | 无冲突复制数据类型用于版本控制 | **低** | CRDT 的"无冲突"假设与 Catalog 的"前置条件语义"（不能创建已存在的表）互斥，Evo 项目已于 2025 年 discontinued |

**结论**：学术界目前**没有**针对 Catalog（Git-like 元数据管理）一致性协议的专门研究。本文提出的分析框架——Catalog 专用 workload 定义、Raft 作为辅助子系统而非业务路径——正是为了填补这一空白。后续研究应优先定义 Catalog 标准化 benchmark，而非套用 TPC-C/YCSB。

## 7. 可行性评估

### 7.1 验证路径

这个方向的核心是回答"Catalog 场景下 OCC 是否足够"，而不是重写整个存储层。推荐采用"理论分析 + 轻量 benchmark 验证"的混合路径：

| 阶段 | 内容 | 人力 | 时间 | 产出 |
|------|------|------|------|------|
| 阶段一 | 工作负载特征分析 | 0.5 FTE | 2 周 | 负载特征报告 |
| 阶段二 | 压力测试验证（JMH） | 1 FTE | 4 周 | Benchmark 工具 + 性能报告 |
| 阶段三 | Raft 原型对比（可选） | 1 FTE | 6 周 | 对比白皮书 |
| **总计（最小）** | | **1 FTE** | **6 周** | **技术白皮书** |

### 7.2 关键发现预判

基于 Catalog 工作负载的固有特征，以下结论大概率成立：

| 场景 | OCC 表现 | Raft 表现 | 结论 |
|------|---------|----------|------|
| 单集群，<100 并发（分散多 branch） | P99 <50ms，abort <1% | Leader 瓶颈不明显，但选举中断 1–3s | **OCC 更优** |
| 单集群，>500 并发（集中在同一 branch） | P99 可能 >200ms，abort 率飙升（冲突集中） | Leader 成为明显瓶颈 | **OCC 仍更优**（但需 branch 拆分或 striped lock 优化） |
| 跨地域（RTT 100ms），多写入点 | 重试代价高（每次冲突 +100ms） | 异步复制，本地 leader 提交 | **Raft 可能更优，但 Minerva 混合架构更优** |
| 灾难恢复（RTO/RPO） | 依赖数据库自身 HA（RTO 分钟级） | 自动 leader 选举，RTO <5s | **Raft 更优** |

> 注：以上数据为基于理论分析的估算，非 Nessie 实测。实际表现取决于具体部署配置、网络环境和负载特征。

### 7.3 主要风险

1. **无生产数据**：如果没有 Nessie 生产环境的操作日志，模拟负载可能与真实场景偏差大。缓解：与 Nessie 社区合作，获取匿名化日志。
2. **Benchmark 设计陷阱**：如果用 TPC-C/YCSB 代替 Catalog 专用负载，结论将失去意义。缓解：严格定义 Catalog workload（branch/commit/merge/tag 的混合比例）。
3. **结论价值有限**：即使证明 OCC 更优，对现有 Nessie 用户也是"已知结论"，不会产生产品改动。缓解：将产出定位为技术白皮书，用于售前说服和学术发表。

### 7.4 维度评分

| 维度 | 评分 | 理由 |
|------|------|------|
| 技术可行性 | 6/10 | 负载分析和压力测试路径清晰；Raft 原型投入大且可能不必要 |
| 创新价值 | 5/10 | "范畴错误"的提法有启发性 |
| 商用价值 | 3/10 | 间接价值（技术影响力），对终端用户无直接增益 |

## 8. 结论与建议

### 8.1 核心结论

1. **Raft 只在多节点独立存储场景下有意义**。Nessie 当前是"多节点 + 共享数据库"架构，不需要 Raft。
2. **Raft 不适合高并发写**。Raft 的 Leader 是硬瓶颈，高并发下请求串行化排队，延迟飙升。
3. **Catalog 场景下 OCC 更合适**。低频写、单 Key 冲突、读占 99.9% 的特征与 OCC 完美匹配，与 Raft 的设计假设错位。
4. **跨地域是唯一值得考虑 Raft 的场景**，但 Minerva 式的"OCC + 异步共识"混合架构比纯 Raft 更优。
5. **Raft 在 Nessie 中的合理边界已明确**：单集群业务路径不需要 Raft；跨地域场景用 Minerva 混合架构；配置中心/审计链可用独立 Raft 子系统。

### 8.2 建议

**优先级：P3（长期观察）**

如果要做，建议：
1. 不要重复通用 DB 的 benchmark，先定义 Catalog 专用 workload。
2. 核心指标应是 **P99 commit latency** 而非吞吐。
3. 产出一份技术白皮书，澄清"Raft 在 Catalog 场景下的适用边界"，为社区提供选型参考。
4. 不要作为产品研发方向——Nessie 的当前 OCC 架构在单集群场景下是最优解。
5. 如果跨地域延迟是实际痛点，优先探索 Minerva 式的"OCC + 异步共识"混合架构，而非纯 Raft。

## 参考资料

- **Minerva (arXiv:2602.21566)**：投稿至 PACMMOD/SIGMOD 2026。OCC + 异步 Raft 混合架构，MWIS 冲突解决。
- **etcd / Consul 工程实践**：Raft 用于配置元数据的强一致存储，工作负载特征（低频写、读主导）与 Catalog 高度相似。
- **TiKV / CockroachDB**：多 Raft group 架构实现水平扩展。数据可分片，但 Catalog 的 branch 是不可分片的单 Key 空间，其分片策略无法复用。
- **CRDT 版本控制（Evo, Loro）**：Evo 项目基于 RGA CRDT，已于 2025 年 discontinued，说明纯 CRDT 路线在版本控制领域遇到根本性障碍。
