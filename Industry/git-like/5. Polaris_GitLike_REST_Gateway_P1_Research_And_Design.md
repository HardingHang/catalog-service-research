# Polaris Git-like REST Gateway P1 调研验证与实现设计

> 调研与设计日期：2026-05-20。本文基于 `3. Lakehouse_GitLike_Evolution_Roadmap_And_Design_Options.md` 与 `4. Polaris_Branch_Overlay_Demo_Research_And_Design.md`，分析 P0 branch overlay demo 是否能迁移到真实 LakeHouse 数据规模，并给出 P1 可分阶段实现的方案。P1 选择 Apache Polaris 作为主流 Catalog 基线，但不再放大 P0 manifest 模型，而是引入 branch-aware Iceberg REST Gateway 与外置权威 Version Store。

## 1. 方向选择与结论

本轮选择的方向是：**基于 Apache Polaris 1.4.1 做 branch-aware Iceberg REST Gateway，使用 PostgreSQL Version Store 保存 catalog-wide refs、commits、content values 与 indexes，把 P0 的流程验证升级为可迁移到实际数据规模的 P1 架构**。

结论先行：

- P0 demo 的整体工作流有研究价值，但不能直接迁移到实际 LakeHouse 数据规模。
- P0 的核心限制不是 Python 或 PowerShell 本身，而是架构语义：它把 catalog-wide branch 降级成“多张表同名 Iceberg table branch 的外部清单”。
- P1 不能只是把 `branches.json` 换成数据库；P1 必须引入独立权威 Version Store、ref HEAD、catalog commit、索引、幂等、锁、审计和可恢复物化链路。
- P1 继续选择 Polaris，因为它是 Iceberg REST-first 的主流 Catalog，能复用权限、存储配置、credential vending、管理 API 和 P0 已验证的运行基线。
- P1 不修改 Polaris core。所有 branch-aware 读写先收敛到 Gateway，Polaris 只作为 main 的兼容物化视图、权限/凭证基线和后续 P2 内置化参照。

P1 的最低功能目标是：

- 支持 `branch`：从 `main` 或指定 ref 创建 branch，创建成本与 catalog 表数量无关。
- 支持 `commit`：通过 Gateway 对某个 branch 提交 Iceberg 表更新，生成 catalog commit，main 不受 branch 写入污染。
- 支持 `publish-plan` 与 fast-forward `publish`：main 未漂移时用一次 ref HEAD CAS 发布，main 已漂移时拒绝。
- 支持基本可靠性：幂等键、CAS 冲突处理、branch lock / merge queue、审计、outbox、失败恢复。
- 支持基本性能：list/load/diff 走索引，不逐表采集 metadata table，不回放完整历史。

P1 明确不做完整 semantic merge，不承诺 Git 双父 merge graph，不做 P2 级 Polaris 内置版本层，不把 branch 维度硬塞进 Polaris 现有 table row。

## 2. P0 demo 现实性分析

P0 的实现目录是 `Demo/branch_on_polaris`。它由三部分组成：`controller/branch_controller.py` 维护本地 logical branch manifest，`runtime/workflows/run-p0-overlay.ps1` 串联 Polaris、RustFS、Spark SQL 和 state 采集，`runtime/tools/collect_iceberg_ref_state.py` 读取 Iceberg metadata tables 中的 ref snapshot。这个 demo 已经证明：在不改 Polaris 的情况下，可以用 Iceberg 表级 branch 编排出最小 logical branch 工作流。

但 P0 不能直接放大到实际 LakeHouse 数据规模，原因如下。

### 2.1 状态模型会随 branch 与 table 相乘膨胀

`branch_controller.py create` 在 manifest 中记录每个 logical branch 管理的表集合，以及这些表创建 branch 时的 base snapshot：

```text
branch dev_a
  sales.orders    -> branch_ref=dev_a, base=snapshot_x
  sales.customers -> branch_ref=dev_a, base=snapshot_y
```

这个模型在两张表、两个 branch 上很清楚，但在生产 catalog 中会出现结构性问题：

- branch 创建成本随工作集表数量线性增长；如果想表达全 catalog branch，就会随 catalog 表数量线性增长。
- manifest 体积随 `branch_count × table_count` 增长。
- 新增表、删除表、rename、namespace 变更都需要同步到每个 branch 的 manifest。
- diff 与 publish preflight 需要外部采集每张表状态，无法自然支持大 catalog 的低延迟列表、过滤和分页。

真实 catalog-wide branch 应该是一个 ref HEAD 指向一个 commit/index。branch 创建只复制 HEAD 指针，不复制全量表集合。

### 2.2 P0 没有服务端权威写入口

P0 的 branch 创建、diff、publish 都依赖本地脚本串行执行：

```text
Spark SQL -> collect state JSON -> Python controller -> generate SQL -> Spark SQL
```

这适合演示，但不是生产控制面。它缺少：

- 服务端 API 和认证上下文。
- 幂等请求处理。
- 并发写入冲突处理。
- 失败重试与恢复。
- 权限、审计、metrics 和 tracing。
- 对所有读写接口的统一 ref 解析。

在实际环境中，Spark、Trino、Flink、PyIceberg、维护任务和平台服务可能并发访问同一 catalog。只靠本地脚本无法成为一致性边界。

### 2.3 P0 publish 是逐表 fast-forward，不是 catalog-wide commit

P0 的 `publish-ff` 只做以下判断：

```text
for each table:
  if main_snapshot != base_snapshot:
    reject
  else:
    emit CALL catalog.system.fast_forward(table, 'main', branch)
```

这个保护能避免明显覆盖 main，但仍不是 catalog-wide 原子发布：

- 逐表 SQL 执行到一半失败时，main 可能只发布了一部分表。
- 多表 publish 没有统一 commit id。
- 不能表达“这次发布同时修改了哪些表、为什么这些表必须一起发布”。
- 不能对 publish 请求做幂等重放。
- 不能把 publish 失败恢复为确定状态。

P1 必须把 publish 变成 Version Store 中的一次 ref HEAD CAS。Polaris main 物化可以异步补齐，但 Gateway 读写语义必须以 Version Store 为准。

### 2.4 Polaris 不理解 P0 logical branch

P0 的 branch 存在于外置 manifest 中，Polaris 仍只看到普通 Iceberg 表和表级 refs。因此以下路径都不是 branch-aware：

- `listTables`
- `loadTable`
- `commitTable`
- `renameTable`
- `dropTable`
- `transactions/commit`
- `loadCredentials`
- cache key / ETag / endpoint discovery
- policy / audit / GC

这意味着 P0 只能控制演示脚本覆盖到的路径。只要客户端绕过脚本直接访问 Polaris，logical branch 语义就会失真。P1 必须把引擎读写入口收敛到 Gateway，并让 Gateway 对 Iceberg REST 读写路径统一解析 ref。

### 2.5 P0 工程栈只适合 demo

P0 使用 Python controller、PowerShell workflow、本地 JSON、in-memory Polaris runtime 和临时 Spark SQL 容器。这些选择对 2 人日 demo 是合理的，但生产级 P1 需要：

- JVM 服务端框架，例如 Java/Kotlin + Quarkus 或 Spring Boot。
- Iceberg Java API 处理 metadata、requirements、updates 和 FileIO。
- PostgreSQL 持久化 refs、commits、indexes 和幂等记录。
- Flyway/Liquibase 管理 schema。
- Testcontainers 做真实集成测试。
- OpenTelemetry/Micrometer 做可观测性。
- Docker Compose/Helm 部署 Gateway、DB、Polaris 和 object storage。

因此，P0 的可迁移内容是语义样本和验收样例，不是实现架构。

## 3. 产品与路线选择

P1 继续选择 Apache Polaris，方案选择 `3.md` 第二章中的 **REST/API 代理转换层 + 外置版本层**。更准确地说，P1 是一个 branch-aware Iceberg REST Gateway，内部持有外置 Version Store，外部对引擎表现为 Iceberg REST Catalog。

### 3.1 Catalog 选择

| 产品 / 路线 | 是否作为 P1 基线 | 判断 |
|---|---:|---|
| Apache Polaris | 是 | 与 P0 连续，代表 Iceberg REST-first 主流 Catalog。Polaris 1.4.1 是当前稳定基线，适合复用权限、存储配置、credential vending 和管理 API，同时作为 P2 内置版本层参照。 |
| Project Nessie | 否，作为语义标尺 | Nessie 已经原生 Git-like，适合借鉴 ref、commit、content value、merge、GC 和 Iceberg REST 接入方式，但本课题目标是增强主流非 Git-like Catalog。 |
| Apache Gravitino | 否 | 适合 catalog-of-catalogs、治理和 federation，但当前 Iceberg REST service 文档仍列出 multi table transaction 未实现，不适合作为 P1 branch/commit 基线。 |
| Unity Catalog OSS | 暂不选 | Delta Catalog-Managed Tables 很有价值，但 Delta CMT 和 UC managed table 的协议、客户端和存储入口侵入更深，不适合作为 P0 Iceberg/Polaris 的直接 P1。 |
| Lakekeeper | 可替代参照 | Rust Iceberg REST Catalog 与 credential vending 很强，但 P0 已选择 Polaris，P1 需要优先保持验证连续性。 |

选择 Polaris 的原因不是它天然支持 Git-like，而是它已经具备主流 Iceberg REST Catalog 的关键基础：

- Catalog / namespace / table 管理。
- 表名到 metadata pointer 的当前态管理。
- 原子更新 table metadata pointer 的基础。
- REST-compatible 多引擎入口。
- RBAC、storage configuration、credential vending 与管理 API。
- Docker image、Helm、PostgreSQL 等生产部署路径。

P1 在 Polaris 外部补 branch-aware Gateway，能先验证产品语义和性能模型；如果成立，P2 再把 Version Store 下沉到 Polaris core。

### 3.2 路线选择

`3.md` 第二章列出四类实现架构：Catalog 内置版本层、Catalog 外置版本层、REST/API 代理转换层、先做多表事务再扩展版本能力。P1 选择其中两者的组合：

```text
Spark / Trino / Flink / PyIceberg
  -> P1 branch-aware Iceberg REST Gateway
       -> PostgreSQL Version Store
       -> Polaris REST / Management API
       -> Object Storage
```

选择这个组合的原因：

- 只做外置版本层但不代理写入口，会被直接写 Polaris 绕过，不能保证 branch 隔离。
- 只做 REST 代理但没有完整 per-ref content value，会丢失历史分支的权威状态。
- 直接改 Polaris core 是 P2 范围，P1 成本过高。
- 先做多表事务再补 branch 会遇到历史模型不足；P1 已经要求至少具备 branch 和 commit，所以需要从一开始建立 refs/commits/content values。

P1 的架构原则是：**Gateway 是 Git-like 读写入口，Version Store 是 branch/commit 权威状态，Polaris 是 main 兼容物化视图与治理基线**。

## 4. P1 总体方案

### 4.1 架构图

```text
                     +--------------------+
Spark / Trino        |                    |
Flink / PyIceberg -> | P1 REST Gateway    |
Iceberg Java API     | branch-aware IRC   |
                     +---------+----------+
                               |
       +-----------------------+-----------------------+
       |                       |                       |
+------+-------+        +------+-------+        +------+-------+
| Version Store|        | Apache       |        | Object       |
| PostgreSQL   |        | Polaris      |        | Storage      |
| refs/commits |        | main view    |        | metadata/data|
| content/index|        | auth/cred    |        | S3/ADLS/GCS  |
+--------------+        +--------------+        +--------------+
```

P1 Gateway 对外暴露两组 API：

- Iceberg REST Catalog API 子集，供 Spark、Trino、Flink、PyIceberg 等引擎读写。
- P1 管理 API，供平台、CLI、UI 和 Agent 创建 branch、查看 diff、生成 publish-plan、执行 publish。

P1 Gateway 内部由六个模块组成：

| 模块 | 职责 |
|---|---|
| Ref Resolver | 从 header、path 或默认配置解析 `ref`，校验 branch/tag/hash 是否存在，生成 request context。 |
| Iceberg REST Adapter | 实现 P1 必需的 Iceberg REST 子集，处理 table load、commit、transaction commit、namespace/list、drop/rename 和 credentials pass-through。 |
| Version Store | PostgreSQL 持久化 refs、commits、content values、commit ops、indexes、幂等和审计。 |
| Commit Coordinator | 校验 requirements，写 Iceberg metadata，生成 catalog commit，通过 ref HEAD CAS 完成提交。 |
| Publish Coordinator | 生成 fast-forward plan，执行 branch lock / merge queue，CAS 推进 main，并写 outbox。 |
| Polaris Materializer | 将 main 的新状态物化到 Polaris，支持 outbox 重试、对账和诊断。 |

### 4.2 Ref 选择方式

P1 默认使用 HTTP header 选择 ref：

```http
X-Catalog-Ref: dev_a
```

选择 header 的原因是它不污染 namespace/table 名称，也不强行改变 Iceberg REST `prefix` 的含义。对无法稳定注入 header 的客户端，保留 path fallback：

```text
/iceberg/dev_a/v1/{prefix}/namespaces/...
```

约定如下：

- 未提供 ref 时默认使用 `main`。
- `main` 可读写，但生产部署建议用 branch protection 禁止普通用户直写 main。
- tag 和 commit hash 只读。
- 所有 cache key、ETag、credential scope、audit event 必须包含 ref 或 resolved commit id。
- 禁止 namespace 编码 branch，例如 `dev_a.sales.orders`，避免污染业务 namespace。

### 4.3 Gateway 覆盖的 Iceberg REST 子集

P1 不需要一次覆盖全部 Iceberg REST OpenAPI，但必须覆盖能形成 branch/commit 闭环的路径。

| Iceberg REST 路径 | P1 行为 |
|---|---|
| `GET /v1/config` | 返回 Gateway 支持的 endpoint、warehouse 与必要 overrides。 |
| `GET /v1/{prefix}/namespaces` | 从 Version Store ref index 解析 namespace，可叠加 Polaris main 物化视图做 bootstrap。 |
| `GET /v1/{prefix}/namespaces/{namespace}` | 读取 namespace 元信息；P1 可先支持最小属性集。 |
| `GET /v1/{prefix}/namespaces/{namespace}/tables` | 从 ref index 按 namespace 列表返回表，不逐表加载 metadata。 |
| `GET /v1/{prefix}/namespaces/{namespace}/tables/{table}` | 从 ref HEAD index 解析 content value，返回该 ref 上的 Iceberg metadata 与 config。 |
| `POST /v1/{prefix}/namespaces/{namespace}/tables` | 支持创建表或 stage-create，生成 branch 上的新 content value。 |
| `POST /v1/{prefix}/namespaces/{namespace}/tables/{table}` | 支持单表 commit，校验 requirements，写 metadata，生成 catalog commit。 |
| `DELETE /v1/{prefix}/namespaces/{namespace}/tables/{table}` | 在目标 ref 上写 tombstone commit，不立即删除物理文件。 |
| `POST /v1/{prefix}/tables/rename` | 在目标 ref 上写 key rename commit，保留 content id。 |
| `POST /v1/{prefix}/transactions/commit` | 支持多表一次 catalog commit。 |
| `GET /v1/{prefix}/namespaces/{namespace}/tables/{table}/credentials` | 透传或委托 Polaris credential vending，但 scope 必须绑定 resolved ref/content。 |

如果某条路径暂不支持，Gateway 必须返回明确的 `UnsupportedOperationException`，不能静默转发到 Polaris，因为静默转发会绕过 ref 语义。

### 4.4 Polaris 的定位

P1 中 Polaris 不再是 branch 的事实源。它承担三类职责：

1. **治理基线**：继续管理 catalog、principal、role、storage config、credential vending 和现有管理 API。
2. **main 兼容物化视图**：给未接入 Gateway 的只读旧客户端提供当前 main 状态。
3. **P2 迁移参照**：P1 Version Store 的 refs/commits/content values 模型未来可映射到 Polaris 内置 persistence。

为了保证 P1 语义成立，生产部署必须限制直写 Polaris：

- 引擎写入只能访问 Gateway 的 Iceberg REST endpoint。
- Polaris REST endpoint 只允许 Gateway 和受控运维账号访问。
- 如果允许客户端直接写 Polaris，则 P1 只能承诺 Gateway 内部一致性，不能承诺全平台 branch 隔离。

## 5. 数据模型详细设计

P1 使用 PostgreSQL 16 作为 Version Store。数据库结构需要支持 O(1) branch 创建、CAS commit、按 ref 快速 list/load、diff、审计、幂等和 outbox。

### 5.1 核心表

#### `catalog_refs`

```text
catalog_refs(
  catalog_id,
  ref_name,
  ref_type,              -- BRANCH / TAG
  head_commit_id,
  policy_id,
  deleted,
  created_by,
  created_at,
  updated_at,
  version
)
```

关键约束：

- `(catalog_id, ref_name)` 唯一。
- `main` 是系统 branch，初始化时创建。
- 更新 `head_commit_id` 必须带 expected head，例如 `WHERE head_commit_id = :expected_head`。
- tag 默认不可变；如果需要移动 tag，必须有显式管理权限。

#### `catalog_commits`

```text
catalog_commits(
  commit_id,
  catalog_id,
  parent_commit_id,
  author,
  message,
  created_at,
  operation_summary,
  index_id,
  source_ref,
  request_id
)
```

P1 commit 采用单父模型。fast-forward publish 可以把 source branch head 直接赋给 main；如果后续要记录 publish 审计，可在 `operation_summary` 中记录 source ref 与 publish plan。P1 不实现 Git 双父 merge commit。

#### `catalog_content_values`

```text
catalog_content_values(
  value_id,
  catalog_id,
  content_id,
  content_key,           -- namespace.table
  content_type,          -- ICEBERG_TABLE / VIEW / NAMESPACE / TOMBSTONE
  metadata_location,
  snapshot_id,
  schema_id,
  spec_id,
  sort_order_id,
  table_uuid,
  table_location,
  format_version,
  last_sequence_number,
  metadata_fingerprint,
  serialized_payload,
  created_at
)
```

`content_id` 用于维持逻辑对象身份，尤其是 rename 场景。`content_key` 是某个 ref 上的可见路径。`metadata_location` 是 Iceberg 表在该 ref 上的权威 metadata JSON。

#### `catalog_commit_ops`

```text
catalog_commit_ops(
  commit_id,
  content_key,
  op_type,               -- PUT / DELETE / RENAME / UNCHANGED
  expected_value_id,
  new_value_id,
  old_content_key,
  new_content_key
)
```

用途：

- 支持 diff。
- 支持 publish-plan。
- 支持 read-set validation。
- 支持审计和后续 revert。

P1 至少支持 `PUT`、`DELETE`、`RENAME`。`UNCHANGED` 可作为多表 transaction 的 read-set validation 扩展。

### 5.2 索引表

只保存 refs 与 commits 不足以支撑大规模读取。P1 需要显式索引。

```text
catalog_ref_indexes(
  index_id,
  catalog_id,
  commit_id,
  parent_index_id,
  index_kind,            -- FULL / INCREMENTAL
  object_count,
  stripe_count,
  created_at
)
```

```text
catalog_content_index(
  index_id,
  namespace,
  content_key,
  content_id,
  value_id,
  content_type,
  deleted
)
```

实现原则：

- 小 commit 生成 incremental index。
- 定期或达到阈值后生成 full compacted index。
- `listTables(namespace)` 必须通过 `catalog_content_index` 的 `(index_id, namespace)` 查找。
- `loadTable(key)` 必须通过 `(index_id, content_key)` 查找。
- `diff(base, head)` 优先使用 commit ops；跨很多 commits 时使用 index 对比。

### 5.3 可靠性表

```text
idempotency_keys(
  key,
  request_hash,
  status,
  response_payload,
  created_at,
  expires_at
)
```

```text
branch_locks(
  catalog_id,
  ref_name,
  lock_type,
  owner,
  expires_at,
  fencing_token
)
```

```text
outbox_materializations(
  event_id,
  catalog_id,
  target_ref,
  commit_id,
  status,
  attempts,
  next_attempt_at,
  last_error,
  created_at,
  updated_at
)
```

```text
audit_events(
  event_id,
  catalog_id,
  ref_name,
  actor,
  action,
  commit_id,
  request_id,
  payload,
  created_at
)
```

这些表不是附加功能，而是 P1 能否从 demo 进入真实环境的分水岭。没有幂等、锁、审计和 outbox，P1 在失败重试、并发 publish 和物化失败时无法给出确定语义。

## 6. 核心流程设计

### 6.1 Bootstrap main

P1 初始化时需要从 Polaris 当前 main 状态生成 Version Store 的初始 commit。

```text
1. Gateway 用 Polaris REST / Iceberg REST 列出 namespace 与 table。
2. 对每张表 loadTable，读取 metadata_location、snapshot_id、schema_id、table_uuid 等。
3. 写入 catalog_content_values。
4. 生成 initial commit c0 与 full index i0。
5. 创建 catalog_refs(main -> c0)。
6. 写 audit event: BOOTSTRAP_MAIN。
```

这个过程可以离线执行。生产首次接入时，应在 bootstrap 窗口禁止对 Polaris 直接写入，避免初始快照不一致。

### 6.2 Create branch

创建 branch 只复制 source ref 的 HEAD 指针：

```text
POST /api/v1/catalogs/{catalog}/branches
{
  "name": "dev_a",
  "sourceRef": "main",
  "message": "create dev_a"
}
```

流程：

```text
1. resolve sourceRef -> head_commit_id
2. insert catalog_refs(dev_a -> source_head)
3. write audit event
4. return branch metadata
```

这一步不扫描全 catalog，不复制表集合，不创建 Iceberg table branch。因此 branch 创建是 O(1)，可以迁移到真实 catalog 规模。

### 6.3 Load table on ref

引擎读取某张表：

```http
GET /iceberg/v1/prod/namespaces/sales/tables/orders
X-Catalog-Ref: dev_a
```

流程：

```text
1. Ref Resolver 得到 ref=dev_a。
2. 读取 catalog_refs.head_commit_id。
3. 读取 commit.index_id。
4. 从 catalog_content_index 查 sales.orders -> value_id。
5. 从 catalog_content_values 读取 metadata_location 与 cached metadata summary。
6. 加载 Iceberg metadata JSON，返回 LoadTableResponse。
7. 返回的 config/credentials/cache metadata 必须绑定 ref 与 commit id。
```

如果表在该 ref 上是 tombstone，则返回 `NoSuchTableException`，即使 Polaris main 中仍能看到该表。

### 6.4 Commit table on branch

引擎提交单表更新：

```http
POST /iceberg/v1/prod/namespaces/sales/tables/orders
X-Catalog-Ref: dev_a
Idempotency-Key: ...
```

流程：

```text
1. 校验 ref 可写，tag/hash 只读。
2. 校验 idempotency key；重复请求直接返回已记录响应。
3. 读取 ref expected HEAD 与 table expected content value。
4. 用 Iceberg Java API 校验 REST requirements 与 updates。
5. 使用 FileIO 写新的 Iceberg metadata JSON 到 object storage。
6. 在 PostgreSQL 事务中：
   a. insert catalog_content_values(new value)
   b. insert catalog_commits(parent = expected HEAD)
   c. insert catalog_commit_ops
   d. build incremental index
   e. update catalog_refs set head_commit_id = new_commit where head_commit_id = expected_head
   f. insert audit event
   g. record idempotency response
7. 如果 CAS 更新行数为 0，返回 409 conflict；客户端或 Gateway 按配置重试。
```

这个流程把 ref HEAD CAS 作为最终提交边界。对象存储中的 metadata JSON 先写入，若 DB CAS 失败，该 metadata 变成未引用对象，后续由 orphan cleanup 或 GC dry-run 清理。

### 6.5 Multi-table transaction commit

P1 应支持 Iceberg REST `POST /v1/{prefix}/transactions/commit`，因为真实 LakeHouse 场景经常要求多张表在同一次发布中保持一致。

流程与单表 commit 类似，但一次处理多个 table commit：

```text
1. 解析 ref 与 expected HEAD。
2. 校验所有 table requirements。
3. 为每张表写新的 metadata JSON。
4. 在一个 DB 事务中插入多个 content values 与 commit ops。
5. 生成一个 catalog commit。
6. 对 ref HEAD 做一次 CAS。
```

P1 的多表原子性指 Version Store 中的 catalog commit 原子可见。Polaris main 的物化可以滞后，但 Gateway 读写始终以 Version Store 为准。

### 6.6 Diff

P1 管理 API：

```text
POST /api/v1/catalogs/{catalog}/branches/{branch}/diff
{
  "baseRef": "main"
}
```

输出至少包含：

- changed tables。
- added tables。
- deleted tables。
- renamed tables。
- 每张表的 base value、head value、snapshot_id、schema_id、metadata_location。
- 是否满足 fast-forward publish。

算法：

```text
1. resolve base head 与 branch head。
2. 如果 base 是 branch 创建点或已记录 merge base，优先扫描 commit_ops。
3. 如果历史跨度过大，读取两个 ref index 做 content_key/value_id 对比。
4. 对同一 content_key 两边都变化的情况标为 CONFLICT。
```

P1 不解析完整 Iceberg schema diff 作为必需能力，但保留 `schema_id`、`spec_id`、`sort_order_id` 和 `metadata_fingerprint`，便于 P2 或 semantic merge service 使用。

### 6.7 Publish plan 与 fast-forward publish

P1 的 publish 是受控 fast-forward，不是 semantic merge。

```text
POST /api/v1/catalogs/{catalog}/branches/{branch}/publish-plan
{
  "targetRef": "main"
}
```

判断：

```text
if target_head == branch_base_or_expected_target:
  publishable = true
else:
  publishable = false
  return conflicts
```

执行 publish：

```text
POST /api/v1/catalogs/{catalog}/branches/{branch}/publish
{
  "targetRef": "main",
  "expectedTargetHead": "c123",
  "expectedSourceHead": "c456"
}
```

流程：

```text
1. 获取 targetRef 的 branch lock 或进入 merge queue。
2. 重新校验 source head 与 target head。
3. update catalog_refs set head_commit_id = source_head where ref_name = target and head_commit_id = expectedTargetHead。
4. 写 audit event: PUBLISH_FAST_FORWARD。
5. 写 outbox_materializations，用于把 main 物化到 Polaris。
6. 释放 lock。
```

如果 CAS 失败，说明 main 漂移，返回 409，并要求重新生成 publish-plan。

### 6.8 Polaris main 物化

P1 的权威状态在 Version Store，但为了兼容旧客户端和已有治理工具，需要把 main 的最新状态物化到 Polaris。

物化策略：

- 首选使用 Polaris / Iceberg REST 支持的多表 transaction commit，如果目标版本和部署支持。
- 如果只能逐表物化，必须在 outbox 中记录非原子物化边界，并把 Gateway 读写继续绑定 Version Store。
- 物化 worker 必须可重试、可对账、可暂停。
- 物化失败不回滚 Version Store 的 main HEAD；它会让 Polaris 兼容视图滞后，需通过运维告警处理。

对账流程：

```text
1. 读取 Version Store main head 对应 index。
2. 读取 Polaris 当前表 metadata pointer。
3. 比较每张表 metadata_location / snapshot_id。
4. 生成 drift report。
5. 对可自动修复项写新的 outbox event。
```

## 7. 工程实现设计

### 7.1 技术栈

P1 不应继续以 Python/PowerShell 作为核心实现。建议技术栈：

| 层 | 建议 |
|---|---|
| 服务端语言 | Java 17 或 Kotlin 1.9+ |
| 服务框架 | Quarkus，优先与 Polaris / Nessie 的 JVM 生态保持接近 |
| Iceberg 能力 | Apache Iceberg Java API 1.10.x，使用 REST request/response model、TableMetadata、FileIO |
| 持久化 | PostgreSQL 16 + jOOQ 或 Hibernate Panache |
| schema migration | Flyway |
| 集成测试 | JUnit 5 + Testcontainers |
| API 文档 | OpenAPI / Swagger |
| 可观测性 | Micrometer + OpenTelemetry |
| 本地环境 | Docker Compose，包含 Gateway、PostgreSQL、Polaris、RustFS 或 MinIO、Spark SQL client |

PowerShell 可以保留为 Windows 本地 smoke workflow，但不进入核心控制面。Python 可以保留为 P0 oracle 或辅助脚本，但不承担 P1 branch/commit 权威逻辑。

### 7.2 代码模块建议

建议在 `Demo/branch_on_polaris` 平级或内部新增 P1 模块，例如：

```text
Demo/p1_polaris_gateway/
  gateway-service/
    src/main/java/...
    src/main/resources/db/migration/
    build.gradle.kts 或 pom.xml
  runtime/
    docker-compose.yml
    spark/
    smoke/
  docs/
    api/
```

模块边界：

| 模块 | 主要包 |
|---|---|
| API layer | `api.iceberg`, `api.management` |
| Ref context | `ref.RefResolver`, `ref.RefContext` |
| Version store | `store.RefRepository`, `store.CommitRepository`, `store.IndexRepository` |
| Commit coordinator | `commit.CommitService`, `commit.IcebergMetadataWriter` |
| Publish coordinator | `publish.PublishPlanner`, `publish.PublishService`, `publish.LockService` |
| Polaris integration | `polaris.PolarisClient`, `polaris.MaterializationWorker` |
| Observability | `audit.AuditService`, `metrics.GatewayMetrics` |

### 7.3 API 设计

P1 管理 API 最小集合：

| API | 作用 |
|---|---|
| `POST /api/v1/catalogs/{catalog}/branches` | 创建 branch |
| `GET /api/v1/catalogs/{catalog}/branches` | 列出 branch/tag |
| `GET /api/v1/catalogs/{catalog}/branches/{branch}` | 查看 branch 元信息与 head |
| `DELETE /api/v1/catalogs/{catalog}/branches/{branch}` | 删除 branch 名称，数据保留交给 retention |
| `POST /api/v1/catalogs/{catalog}/branches/{branch}/diff` | 计算 diff |
| `POST /api/v1/catalogs/{catalog}/branches/{branch}/publish-plan` | 生成 fast-forward 发布计划 |
| `POST /api/v1/catalogs/{catalog}/branches/{branch}/publish` | 执行 fast-forward publish |
| `GET /api/v1/catalogs/{catalog}/commits/{commit}` | 查看 commit |
| `GET /api/v1/catalogs/{catalog}/refs/{ref}/contents` | 调试用，分页列出某 ref 的 content index |

P1 管理 API 必须支持：

- `Idempotency-Key`。
- request id / trace id。
- 明确的 409 conflict。
- 结构化错误体。
- actor 透传或服务端认证主体。

### 7.4 权限与绕写控制

P1 的权限模型先保持保守：

- 读表权限复用 Polaris 对 catalog/namespace/table 的权限判断。
- branch 创建、删除、publish 使用 Gateway 自身的 branch policy。
- `main` 默认受保护，普通写入只能进入 feature branch。
- Gateway 访问 Polaris 使用受控 service principal。
- Polaris endpoint 在生产网络中不暴露给普通引擎写入。

P1 文档和验收必须明确：如果部署允许客户端直接写 Polaris，Gateway 无法感知该提交，Version Store 的 branch HEAD 会失真。此场景不属于 P1 强一致承诺范围，只能通过 drift detection 发现。

### 7.5 GC 与 retention 边界

P1 不实现自动物理删除，但必须记录足够的 GC root：

- refs 的 head commit。
- tag 指向的 commit。
- branch/tag retention 期内的历史 commit。
- tombstone 对应的 dropped table metadata root。
- outbox 未完成物化事件引用的 content value。

P1 可以提供 GC dry-run：

```text
POST /api/v1/catalogs/{catalog}/gc/dry-run
```

输出不可达 commit、不可达 metadata location、潜在可清理对象数量。实际删除留到 P2 或独立 GC service。

## 8. 分阶段执行计划

P1 可以拆成多个 Agent 可执行阶段，每阶段都有明确产物和验收。

### Phase 1：文档与接口冻结

产物：

- P1 API OpenAPI 草案。
- PostgreSQL schema 草案。
- Gateway 模块骨架。
- docker-compose runtime 草案。

验收：

- API 能表达 branch create、commit、diff、publish-plan、publish。
- schema 能表达 refs、commits、content values、indexes、idempotency、audit、outbox。
- 所有接口明确 ref 选择方式和错误语义。

### Phase 2：Version Store MVP

产物：

- PostgreSQL migration。
- RefRepository / CommitRepository / IndexRepository。
- CAS 更新实现。
- branch create/list/delete。

验收：

- branch 创建 O(1)，不扫描表。
- 并发创建同名 branch 正确冲突。
- ref HEAD CAS 失败能返回明确 conflict。

### Phase 3：Iceberg REST load/list

产物：

- `GET /config`。
- namespace/table list。
- load table on ref。
- bootstrap main 工具。

验收：

- 从 Polaris bootstrap 出 main。
- 创建 branch 后，branch 与 main 初始 load 一致。
- list/load 走 index，不逐表采集 state。

### Phase 4：Commit MVP

产物：

- 单表 commit。
- 基础 metadata 写入。
- idempotency key。
- audit event。

验收：

- branch 上 commit 后，branch load 返回新 snapshot，main load 不变。
- 重放相同 idempotency key 返回同一结果。
- 两个并发 commit 到同一 branch 至少一个 CAS 成功，另一个明确冲突或重试成功。

### Phase 5：Transaction commit 与 diff

产物：

- `transactions/commit`。
- 多表一个 catalog commit。
- diff API。

验收：

- 一次 transaction 修改两张表，只生成一个 catalog commit。
- diff 能列出 changed/added/deleted/renamed tables。
- 大工作集 diff 不依赖全表 metadata table 采集。

### Phase 6：Publish 与 Polaris 物化

产物：

- publish-plan。
- fast-forward publish。
- branch lock / merge queue。
- outbox materialization worker。
- drift report。

验收：

- main 未漂移时 publish 成功，main ref 一次 CAS 到 source head。
- main 漂移时 publish-plan 拒绝。
- 物化失败能留在 outbox 并重试。
- Gateway main 与 Polaris main 的 drift 能被报告。

## 9. 测试与验收

### 9.1 单元测试

必须覆盖：

- branch create/list/delete。
- ref resolve 默认值、header、path fallback。
- commit CAS conflict。
- idempotency replay。
- diff index。
- namespace/table lookup。
- publish-plan fast-forward 与 conflict。
- outbox retry 状态转换。

### 9.2 集成测试

使用 Testcontainers 启动：

- PostgreSQL 16。
- Polaris 1.4.1。
- RustFS 或 MinIO。
- Spark 3.5+ with Iceberg 1.10.x。

测试链路：

```text
bootstrap main
create dev_a/dev_b
load table on each ref
commit table on dev_a
multi-table commit on dev_b
diff dev_a/main
publish-plan dev_a
publish dev_a
verify dev_b publish conflict
```

### 9.3 端到端验收标准

P1 完成的最低标准：

- `dev_a` 与 `dev_b` 可以从 `main` O(1) 创建。
- 同一张表在不同 ref 上可以读到不同 snapshot。
- branch commit 后 main 不变化。
- 两张表一次 transaction commit 生成同一个 catalog commit。
- main 漂移时 publish-plan 拒绝 fast-forward。
- publish 成功后 Gateway main 立即可见；Polaris main 通过 outbox 最终物化。
- 直接绕过 Gateway 写 Polaris 的场景被明确标记为不受 P1 保证，并可被 drift report 检测。

### 9.4 性能验收

P1 需要做小规模基准，目标不是极限吞吐，而是证明架构不会随 catalog 表数量线性退化。

| 场景 | 验收目标 |
|---|---|
| branch create | O(1)，不扫描全表。 |
| table load | 通过 `(index_id, content_key)` 查找，单表 lookup 不回放历史。 |
| namespace list | 通过 `(index_id, namespace)` 分页列出，不逐表 load metadata。 |
| diff | 优先走 commit ops，必要时走 index 对比，不采集每张表 metadata table。 |
| publish | 一次 CAS 推进 target ref，不逐表 fast-forward 作为权威边界。 |

## 11. 与 P0/P2 的关系

P0、P1、P2 的边界如下：

| 阶段 | 权威状态 | 读写入口 | branch 成本 | publish 边界 | 适用性 |
|---|---|---|---|---|---|
| P0 | 本地 JSON manifest | 脚本 + Spark SQL + Polaris | O(branch × table) | 逐表 fast-forward SQL | workflow demo |
| P1 | 外置 PostgreSQL Version Store | Branch-aware Iceberg REST Gateway | O(1) ref pointer | ref HEAD CAS + outbox materialization | 可迁移架构验证 |
| P2 | Polaris 内置 Version Store | Polaris 原生 ref-aware API | O(1) ref pointer | Polaris 内部 catalog commit | 最终产品形态 |

P1 的价值是证明“在主流 Catalog 周围收敛写入口，并引入外置权威 version store”能否支撑真实规模。P1 成功后，P2 不应迁移 Python/PowerShell 或 P0 manifest，而应迁移 P1 的语义、schema、CAS、index、audit、outbox 与 API 行为。
