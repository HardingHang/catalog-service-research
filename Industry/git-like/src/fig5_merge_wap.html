图 5 · Merge Replay 与 WAP 发布流程

两个核心场景的可视化说明

共 5 步，点击开始
点击"下一步"查看 merge replay 的分步过程。
场景：experiment branch 在 c2 之后提交了 c3 和 c4，现将其 merge 进 main。
1
创建隔离 Branch（零成本）
从 main 拉出 qa branch。该操作仅在 Nessie 的 refs 表中写入一行，不复制任何数据文件。 main 上的读者完全感知不到 qa 的存在。
CREATE BRANCH qa FROM main; -- Nessie: refs.put("qa", refs["main"]) -- 耗时 < 1ms，无文件复制
2
ETL 向 qa Branch 写入数据
Spark / Flink 配置为写入 qa branch。写入期间 main 上的读者看到的仍是旧版本，两条历史线完全隔离。 可在 qa 上做多次提交，最终形成若干个新 commit。
# Spark 配置写入 qa branch spark.conf.set("spark.sql.catalog.nessie.ref", "qa") # 以下 DML 全部写入 qa，main 不受影响 spark.sql("INSERT INTO orders ...") spark.sql("UPDATE customers ...")
3
数据质量校验（Audit）
在 qa branch 上读取数据（对生产环境无影响），执行行数、空值率、业务规则等校验。 此阶段 qa branch 可反复修改并重新提交，直至通过校验。
# 读 qa branch 执行校验 df = spark.sql(""" SELECT COUNT(*) FROM orders VERSION AS OF 'qa' """) assert df.first()[0] > 0 # 校验失败 → 直接 DROP qa
4a
校验通过 → Merge（原子发布）
将 qa branch 的所有变更原子地 merge 进 main。Nessie replay 机制在 main 上逐 commit 重放并执行 OCC 校验。 merge 完成的瞬间，所有读 main 的用户同时看到新版本（多表同步切换）。
MERGE BRANCH qa INTO main; -- Nessie: replay qa 的所有 commit 到 main -- 单次 CAS 完成，多张表同时可见 DROP BRANCH qa;
4b
校验失败 → 丢弃（无代价回退）
直接删除 qa branch。main 的数据和读者完全未受影响。 由于 qa 的变更从未写入 main，此处"回退"无需 UNDO 操作。 S3 上 qa branch 写入的文件由 GC 异步清理。
# 校验失败，丢弃 qa branch DROP BRANCH qa; -- refs 表删除一行，操作完成 -- main 状态无任何变化

成功路径的关键性质

多表原子：merge 完成前，读者不会看到部分更新状态。
全程隔离：ETL 写入期间 main 读者无感知。
可重试：校验失败后修复数据，重新 merge，无副作用。

传统方式无法做到的原因

无 branch：ETL 直写 main，脏数据立即可见，无法安全回滚。
单表 branch：各表 fast-forward 顺序执行，存在中间不一致状态。
无 catalog-wide commit：无法保证多张表在同一时刻切换。
