从单表 Iceberg CAS 到 Nessie refs / objs 模型的完整原理

① 初始状态：Catalog 持有唯一的可变指针
表 sales.orders 在对象存储中存在多个历史版本的 metadata.json，但 Catalog 只记录"当前哪个版本有效"。引擎查询时向 Catalog 询问该表路径，Catalog 返回当前有效的 metadata.json 路径。

不可变对象：每个 metadata.json 一旦写入 S3 就不再修改。v1、v2 版本均持续保存，供 time travel 和 GC 使用。
可变指针：Catalog 中那一行 sales.orders → v2.json 是系统中唯一"会变"的部分。
② 写入发生：引擎先写文件，再请求翻指针
Spark 执行写操作。它先在 S3 生成新的 Parquet 文件及对应的新 metadata.json（v3），再向 Catalog 发起 CAS 请求："请将指针从 v2 替换为 v3"。顺序关键：先写文件，后翻指针。

指针（仍指向 v2）

→ v2-abc.json
等待中
Spark 正在请求
CAS: v2 → v3
→
对象存储 S3
v3-new.json（新写入）
snapshotId: 101 · schemaId: 2
→ manifest-list-3.avro → 新 Parquet 文件
v2-abc.json（当前有效）
snapshotId: 100
v1-def.json（历史）
snapshotId: 99
v3-new.json 已写入 S3，但在 CAS 成功之前，所有引擎查询 Catalog 仍得到 v2 路径。写操作对读者不可见，直到指针翻转完成——这是原子发布的基础。
③ 指针翻转（CAS）：原子地将新版本设为当前版本
Catalog 执行 compare-and-swap：若当前值等于 v2，则替换为 v3；否则拒绝。该操作要么完全成功，要么完全失败——没有中间状态。
CAS 操作
compare_and_swap(
  key      = "sales.orders",
  expected = v2-abc.json,
  new      = v3-new.json
)
→ 成功：指针已翻转
若此时另一 writer 已将指针改为 v3'，
则 CAS 返回失败，Spark 需重试
→
Catalog（翻转后）
指针（已更新）
sales.orders
→ v3-new.json
此后所有引擎读到的均为 v3 版本数据
为何称为"原子"：CAS 针对单条记录的条件更新，在任何 KV 存储中天然是原子的。无需锁、无需多行事务。
CAS 失败时的安全性：v3-new.json 已写入 S3 但无指针引用，成为孤儿文件，由 GC 异步清理。数据状态不受损坏。
④ Nessie 的版本：将多表指针打包进 CommitObj
Nessie 将"每张表的 metadata 指针"封装在一个 CommitObj 中，由 refs 表中的一行指向该 CommitObj。翻转 refs 中的这一行，等价于原子地变更整个 catalog 中多张表的状态。
refs 表（可变）
branch "main"
→ CommitObj(c3)
branch "experiment"
→ CommitObj(c5)
每行更新需要 single-key CAS
→
objs 表（不可变，内容寻址）
CommitObj(c3) — main 当前 HEAD
parent: c2
changes: {
  sales.orders     → v43.json,
  sales.customers → v17.json
}
ObjId = hash(内容)，写入后不可变
CommitObj(c2)
parent: c1 · changes: {...}
多表原子性的来源：CommitObj(c3) 同时包含 sales.orders 和 sales.customers 两张表的新指针。refs 表中"main → c3"这一次 CAS 成功后，两张表同时对所有读者可见——这即是"多表原子 commit"。
⑤ 幂等写的意义：CAS 失败无需回滚
内容寻址的核心性质：相同内容产生相同 ObjId。向 objs 表写入相同内容两次，第二次等同于空操作。这使得 CAS 失败时无需任何回滚逻辑。

普通数据库写入（需要回滚）

步骤 1
INSERT INTO table VALUES ...
步骤 2
UPDATE table SET ...
失败
必须 ROLLBACK
否则步骤 1 的数据残留，状态不一致

Nessie 内容寻址写入（天然幂等）

objs.put(commit_A)
hash(commit_A) = "abc123"
objs["abc123"] = commit_A
objs.put(commit_A)（重复写）
key 已存在，写入被忽略，无副作用
天然幂等
CAS 失败时
objs 中的孤儿对象不影响正确性
后台 GC 定期清理，无需 ROLLBACK
幂等：执行 N 次与执行 1 次效果相同。内容寻址使每次写入幂等，允许将全部重 IO 置于 CAS 之前，CAS 失败时直接重试而无需任何清理操作。
