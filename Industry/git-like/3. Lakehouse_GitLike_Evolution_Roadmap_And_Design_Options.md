# Lakehouse Git-like 演进、主流 Catalog 改造与创新方案讨论

> 基于《1. Catalog 层 Git-like 能力分析报告》和《2. Nessie Catalog 级 Git-Like 原理与实现流程》继续展开。
> 调研日期：2026-05-12。本文结合官方文档、社区 issue 与源码，重点回答四个问题：除 Catalog 级 Git-like 外还有哪些层级演进；Unity Catalog / Apache Polaris 等主流 catalog 若实现 Git-like 至少需要什么结构；Nessie 的 roadmap、已知不足与优化方向；以及除“把 Nessie 双逻辑表迁入/套在 catalog 外层”之外还有哪些创新空间。最后补充一个最小可运行 demo 方案，用于验证有限安全场景下的 semantic auto resolve conflict。

---

## 0. 结论先行

**第一，目前 Lakehouse 领域确实存在多个层级的版本化路线，但真正接近“跨表 Git-like”的仍主要在 Catalog/外置版本控制层。** Iceberg、Paimon 已经把 branch/tag 下沉到单表；Delta/Hudi 主要提供单表 transaction log、time travel、savepoint；lakeFS 把 Git-like 放在对象存储路径层；Delta Catalog-Managed Tables 与 Iceberg REST `/transactions/commit` 把提交协调上移到 catalog，但它们更像“多表事务协调”，还不是 branch/merge/log/diff/revert 完整 Git-like。

**第二，Unity Catalog / Polaris 要实现 Git-like，核心不是给每张表多加几个字段，而是引入一套 catalog-wide version store。** 最小结构包括：`refs`、`commits`、`content values`、`commit ops/index`、ref-scoped read/write API、merge/diff/revert 语义、branch/tag 权限与 GC roots。对 Iceberg 表格式本身可以做到低侵入：不必修改 Iceberg table metadata JSON；Catalog 的 on-reference content value 只需记录 `metadata_location`、`snapshot_id`、`schema_id`、`spec_id`、`sort_order_id`、`table_uuid/content_id` 等摘要。若采用 Delta Catalog-Managed Tables，则侵入更深，因为 Delta 协议要求启用 `catalogManaged` table feature 并禁止直接 path-based 访问。

**第三，Nessie 的可见 roadmap 更像“从 Git-like Catalog 向通用 Iceberg REST Catalog/湖仓控制面演进”。** 官方最新站点显示 0.107.5 已发布；源码中 `catalog/README.md` 仍标注 “In-development of Nessie Catalog”，并说明 Spark/Flink 已按 Iceberg REST 接入，Trino “coming soon”。Release notes 近期主要围绕 Spark 4.0、Java 17、Quarkus、认证/密钥管理、对象存储兼容等工程化演进。公开文档没有一个稳定的“roadmap 页面”，所以本文把 roadmap 分为官方已写明、release/source 推断、社区 issue 暴露三类。

**第四，“metadata of metadata” 是必要但不充分。** 真正有产品差异的地方在：自动/半自动 conflict resolution、数据质量门禁、branch protection、语义 diff、schema/data contract 合并、依赖感知的多表发布、GC 安全性、热点 ref 性能、审计/血缘/CI 一体化、以及面向不同引擎的渐进式接入。

## 1. 除 Catalog 级 Git-like 外，其他层级有哪些方案和演进路线？

Lakehouse 版本化可以按“版本边界”分成五层。

| 层级 | 代表 | 版本边界 | 是否 Git-like | 跨表能力 | 关键判断 |
|---|---|---|---|---|---|
| 表格式层 | Iceberg branch/tag、Paimon branch | 单表 snapshot lineage | 部分是 | 否 | 适合单表 WAP、单表回滚；无法表达“一次提交修改多张表” |
| 表事务日志层 | Delta log、Hudi timeline/savepoint | 单表 commit timeline | 不是 | 否 | 强在 ACID/time travel；不提供 catalog-wide branch |
| Catalog 事务协调层 | Iceberg REST `/transactions/commit`、Delta Catalog-Managed Tables | 多表提交边界 | 不是完整 Git-like | 是，多表原子提交 | 解决 all-or-nothing，但不天然提供 branch/merge/log/diff/revert |
| Catalog Git-like 层 | Nessie、Bauplan Data Branches | catalog/repository snapshot | 是 | 是 | 最接近 Git：branch、commit、merge、tag、log |
| 对象存储版本层 | lakeFS | repository 内对象路径集合 | 是 | 与文件集合一致 | 格式无关，但冲突粒度通常是文件/对象，不理解表格式语义 |

### 1.1 表格式层：Iceberg / Paimon 的单表 branch

Iceberg 官方文档定义 branch/tag 为“表 snapshot 的命名引用”。Branch 指向某条 snapshot lineage 的 head，tag 指向特定 snapshot；Audit branch 可用于 WAP，验证后通过 `fast_forward` 把 main 推进到 audit branch。这个能力非常适合单表，但边界仍是单表：`sales.orders` 和 `sales.customers` 的 branch 即使命名相同，也不是同一棵版本树。

Paimon 也提供单表 branch：可以从 tag 创建 branch、读写 `t$branch_branch1`、并 fast-forward 回 main。Paimon 文档特别提到 branch 可用于 streaming 场景的数据纠错和验证，避免复制数据。但它同样是表级，无法表达“多表同一次 commit”。

**结论**：表格式层 branch 是“单表 Git-like”，不是“Lakehouse/catalog Git-like”。它减少了 Catalog 层 Git-like 的一部分诉求，但替代不了跨表一致发布、catalog-wide audit log 和跨表 revert。

### 1.2 表事务日志层：Delta / Hudi 的时间线能力

Delta Lake 官方文档把 time travel 作为核心能力：表 transaction log 支持历史查询、审计、回滚和可复现实验。Hudi 的 timeline/savepoint 也能保留关键 commit 供 disaster recovery 使用。

这条路线的强项是表内事务和数据文件管理，弱项是跨表协调。多个 Delta/Hudi 表之间没有一个共享 commit 对象，因此“事实表和维表一起发布”只能由上层工作流补偿，或依赖新一代 catalog-managed commit 协议。

### 1.3 Catalog 事务协调层：多表原子提交正在标准化

Iceberg REST Catalog OpenAPI 已有 `/v1/{prefix}/transactions/commit`，summary 明确是 “Commit updates to multiple tables in an atomic operation”。Polaris 的 `polaris-catalog-service.yaml` 直接引用该 Iceberg REST endpoint；源码中的 `IcebergCatalogHandler.commitTransaction()` 用 `TransactionWorkspaceMetaStoreManager` 暂存每张表的变更，验证完成后把所有 entity update 作为单个原子单元提交。

Delta Lake 4.0.1+ 的 Catalog-Managed Tables 更进一步：官方文档说明 `catalogManaged` reader-writer table feature 会改变 Delta 表发现和访问方式，由 catalog 协调 commit atomicity，从而支持 multi-table transactions。它也明确限制：启用后不支持 filesystem-based direct access，所有 Delta client 必须通过 managing catalog 访问；新建表启用后 table protocol 会升级，且不能对已有表开启，也不能禁用。

**结论**：这是非常重要的行业演进。它说明主流 Lakehouse 正在把“提交协调权”从文件系统/对象存储 CAS 上移到 Catalog。但它与 Git-like 不是同一件事：它解决“多表一次事务提交”，不自动提供长期 branch、merge、tag、diff、revert 与跨版本审计体验。

### 1.4 对象存储层：lakeFS 的文件集合 Git-like

lakeFS 在对象存储前加一层 repository/branch/commit/tag/merge。官方文档说明 branch 是指向 commit 的 pointer，创建 branch 是 zero-copy；commit 是 repository 全部 contents 的不可变 checkpoint；merge 会生成以 destination/source 为父的提交。

它的优势是格式无关：Parquet、Iceberg、Delta、JSON、图片都能纳入同一对象版本空间。代价是它位于表格式下方，天然看到的是对象/路径，而不是“表 schema、snapshot、manifest 语义”。因此它更适合作为物理数据湖版本控制，若要服务 Iceberg/Delta 语义，还需要额外集成来避免表 metadata 与数据文件之间的不一致。

### 1.5 Pipeline / Data Product 层：把 branch 作为执行环境

Bauplan 文档把 data branch 定义为隔离开发环境：用户可以在 branch 中导入数据、删除表、创建 namespace、运行 pipeline，之后再 merge 到 main。它更强调“pipeline run = commit”的研发体验，而非只做 catalog API。

学术侧的 LakeVilla 也值得关注。论文摘要把问题描述为：现有 OTF（Iceberg/Delta/Hudi）主要提供单表事务，而缺少 multi-table transactions 和 abort recovery；LakeVilla 试图以非侵入方式为 Iceberg/Delta 引入长事务、隔离和恢复。这不是 Git-like，但说明另一条演进路线是“事务管理器/恢复层”，它可能与 Git-like Catalog 互补。

## 2. 基于 Unity / Polaris 等主流 Catalog 实现 Git-like：至少需要增加什么？

### 2.1 先看主流 Catalog 现状

**Unity Catalog OSS** 的 `TableInfo` 模型主要是当前表实体：`name`、`catalog_name`、`schema_name`、`table_type`、`data_source_format`、`columns`、`storage_location`、`properties`、`owner`、`table_id` 等。服务端 `TableInfoDAO` 落表为 `uc_tables`，核心字段包括 `schema_id`、`type`、`data_source_format`、`url`、columns、view_definition，以及 Delta UniForm Iceberg metadata 的三个字段。它天然是“当前状态 catalog”，没有 ref/commit 对象图。

**Apache Polaris** 的 `IcebergTableLikeEntity` 把 Iceberg 当前 `metadata-location` 放在 internal properties；`PolarisEntityCore` 有 `entityVersion`，`BasePersistence.writeEntity()` 通过 `originalEntity` 做 CAS，`writeEntities()` 支持一批 entity 原子写入。Polaris 已经具备“多实体条件提交”的基础，但它的 entity 仍表示当前 catalog tree，而不是 branch 上的 catalog snapshot。

这意味着：Unity/Polaris 已有的是“当前 metadata pointer + entity version/OCC”；Git-like 需要的是“每个 ref 都有自己的 metadata pointer 集合 + commit DAG/log”。

### 2.2 最小新增结构

若采用 Nessie-like 的 integrated version store，至少需要以下结构。

| 结构 | 作用 | 关键字段 |
|---|---|---|
| `catalog_refs` | branch/tag 的命名入口 | `repo_id/catalog_id`、`ref_name`、`ref_type`、`head_commit_id`、`created_at`、`owner`、`policy`、`deleted` |
| `catalog_commits` | catalog-wide commit 链 | `commit_id`、`parent_commit_id`、`secondary_parent_ids`、`author`、`timestamp`、`message`、`index_id`、`operation_summary` |
| `catalog_content_values` | 某个 catalog object 在某版本上的 on-reference state | `value_id`、`content_id`、`content_type`、`metadata_location`、`snapshot_id`、`schema_id`、`spec_id`、`sort_order_id`、`table_uuid`、`serialized_payload` |
| `catalog_commit_ops` 或 index object | commit 中的 key 级变更 | `commit_id`、`content_key`、`op_type`、`expected_value_id`、`new_value_id`、`payload_type` |
| `catalog_commit_indexes` | 从 HEAD 快速解析完整 catalog view | full index / incremental index / stripe index |
| `branch_policies` | branch/tag 权限与保护规则 | who can write/merge/delete、required checks、tag immutability |
| `gc_roots` / reachability index | 防止误删仍被历史/ref 引用的数据文件 | `ref_name`、`commit_id`、`content_value_id`、retention policy |

抽象读路径：

```text
ref_name = main
  -> catalog_refs.head_commit_id = c102
  -> catalog_commits.index_id
  -> lookup(ContentKey("sales.orders"))
  -> catalog_content_values(value_id=cv43)
  -> metadata_location = s3://.../orders/metadata/v43.metadata.json
```

抽象写路径：

```text
1. read target ref HEAD
2. resolve HEAD index and expected content values
3. write new Iceberg metadata.json to object store
4. create new content values / commit / index objects
5. CAS update catalog_refs.head_commit_id from old HEAD to new HEAD
```

### 2.3 是否需要修改表格式或表结构字段？

分三种情况。

**情况 A：Iceberg 表 + Catalog Git-like，低侵入。**

不需要修改 Iceberg table metadata JSON。Catalog 只保存不同 branch 上“表名 -> metadata_location”的不同值。为了加速 OCC、diff、merge 和 UI 展示，可在 `content_value` 中冗余保存：

| 字段 | 是否必须 | 说明 |
|---|---|---|
| `metadata_location` | 必须 | 当前 ref 上该表的 Iceberg metadata JSON |
| `table_uuid` / `content_id` | 强烈建议 | 识别 rename 前后是否同一逻辑表 |
| `snapshot_id` | 建议 | 快速展示和校验，不必每次解析 JSON |
| `schema_id`、`spec_id`、`sort_order_id` | 建议 | 支持 schema/spec 级 diff 与部分自动冲突判断 |
| `location` | 建议 | 支持 GC、storage policy 和安全校验 |
| `format_version` | 建议 | 判断 Iceberg v1/v2/v3 等兼容能力 |

这些字段属于 Catalog 的 metadata-of-metadata，不要求表格式层新增字段。

**情况 B：Unity/Polaris 当前表行直接扩展，侵入较高。**

如果不建独立 version store，而是在现有表实体表上直接加 branch 维度，则至少需要：

```text
table_active_state(
  catalog_id,
  schema_id,
  table_name,
  ref_id,
  content_id,
  value_id,
  metadata_location,
  entity_version,
  ...
)
```

并把原来 `(schema_id, table_name)` 的唯一约束改成 `(schema_id, table_name, ref_id)`。这会让所有 lookup/list/rename/drop 权限逻辑都变复杂，也容易污染主流 catalog 的“当前状态”模型。因此更推荐单独建 version store，再由 read path 按 ref 解析。

**情况 C：Delta Catalog-Managed Tables，协议侵入较高。**

Delta CMT 不是只加 catalog 表字段。官方文档要求启用 `delta.feature.catalogManaged`，升级 reader/writer protocol，并禁止不经 catalog 的 path-based access。它适合构建“catalog 协调多表事务”，但如果目标是 Git-like，还需要在 Unity Catalog/其他 managing catalog 上继续增加 ref/commit/history 层。

### 2.4 四种实现架构

这些架构表面都能表达 “branch -> catalog state”，但它们的原子边界、迁移风险和与现有引擎的兼容方式差别很大。判断一个方案是否成立，不能只看是否有 `refs/objs`，还要看以下五个问题：

| 判断维度 | 必须回答的问题 |
|---|---|
| 权威写入口 | 所有会改变表 metadata pointer 的写入，是否都经过同一个 Git-like 层？ |
| 原子边界 | 一次 commit / merge 更新多张表时，最终 CAS 是 ref 级、entity batch 级，还是多次单表 CAS？ |
| 默认分支语义 | 不带 branch 的传统客户端读写的是 `main`，还是绕过版本层直接写底层 catalog？ |
| 对象生命周期 | 历史 branch/tag 引用的 table metadata、manifest、data files 是否会被 GC 正确保留？ |
| 引擎兼容 | Spark/Trino/Flink/PyIceberg 是否能通过现有 REST Catalog 参数表达 ref，还是需要专用扩展？ |

#### 2.4.1 方案 A：Integrated version store

Integrated 方案是在 Unity / Polaris 的 catalog 服务内部加入版本层。对外仍是一个 catalog；对内把“当前表实体”改成“某个 ref 上的 catalog view”。

```text
client
  -> Unity / Polaris Git-like Catalog
       -> refs / commits / content-values / indexes
       -> existing entity store / privilege store / credential vending
       -> object storage metadata.json / data files
```

最小改造点：

| 模块 | 改造内容 |
|---|---|
| Lookup/list | 所有 `loadTable/listTables/loadNamespace` 增加 ref 上下文；默认 ref 为 `main` |
| Commit | 原来的单表 `metadata_location` CAS 改成生成 `ContentValue + CommitObj`，最后 CAS `ref.head` |
| Multi-table transaction | 可复用 Polaris `writeEntities()` / Iceberg REST `/transactions/commit` 的 all-or-nothing 能力，但最终应落成一个 catalog commit |
| Rename/drop | 不能只改当前 entity row；必须记录为某个 ref 上的 key-level op |
| Authz | 权限要区分 catalog object 权限与 branch 权限，例如 `write table` 不等价于 `merge to main` |
| GC | GC root 从“当前表集合”扩展为“所有 live ref/tag + retention policy 覆盖的 commit” |

Integrated 的优势是语义最干净：权限、审计、GC、credential vending 都在同一个控制面中。它也最接近 Nessie。代价是改造深，所有读写路径都必须 ref-aware。对 Unity/Polaris 这类已经有较完整权限和实体模型的 catalog，风险集中在 `list/rename/drop` 和权限继承：这些操作原本只面向当前 catalog tree，一旦引入 branch，就必须回答“branch 上删除 namespace 是否影响 main”“rename 后权限跟 name 还是跟 content id 走”等问题。

建议的落地方式不是直接把原表改成 `(table_name, ref_id)` 多版本行，而是保留现有 `uc_tables` / Polaris entity 作为 `main` 的物化视图或兼容层，另建 version store 作为权威状态。这样传统客户端仍能读 main，Git-like 客户端读 ref；但写路径必须尽快收敛到 version store，否则会出现 main 物化视图和 version store 不一致。

#### 2.4.2 方案 B：Sidecar overlay

Sidecar 方案是在主流 catalog 之外新增 Git-like 服务。它不改 Unity/Polaris 内核，而是把底层 catalog 当成一个“main 分支存储后端”或“metadata pointer provider”。

```text
client
  -> Git-like sidecar
       -> refs / commits / content-values / indexes
       -> Unity / Polaris current catalog
       -> object storage
```

这个方案的关键不是能不能存 `metadata of metadata of metadata`，而是 sidecar 是否是**权威写入口**。

| Sidecar 形态 | 是否推荐 | 原因 |
|---|---|---|
| 只读镜像 | 可用于审计/实验 | 能做历史分析，不能保证 branch 隔离和 merge 原子性 |
| 写代理 | 可行 | 所有 write/commit 经过 sidecar，底层 catalog 只保存 main 或物化状态 |
| 双写同步 | 高风险 | sidecar 和 catalog 任一侧写成功另一侧失败，就需要恢复协议 |
| 异步 CDC 同步 | 不适合强 Git-like | 能做 lineage/history，不适合 WAP merge 这种强一致发布 |

Sidecar 的主要失败模式：

- **绕写**：某些引擎直接连 Unity/Polaris，绕过 sidecar 写 main，sidecar 的 `main` HEAD 立即失真。
- **双写中断**：sidecar 已更新 ref，但底层 catalog main 物化失败；或底层 catalog 已更新，sidecar commit 失败。
- **权限分裂**：Unity/Polaris 判断用户可写表，但 sidecar 判断用户不能 merge main；如果没有统一 policy，审计会混乱。
- **GC 错删**：底层 catalog 只知道 main，不知道 sidecar branch/tag 仍引用旧 metadata。

因此 sidecar 只有两种稳妥用法：第一，成为所有引擎连接的唯一 REST endpoint；第二，只做非权威的审计/可视化，不承诺 Git-like 隔离发布。若目标是生产级 Git-like，sidecar 必须代理 Iceberg REST、Delta Catalog API、namespace、view、credential vending、drop/rename 等完整面。

#### 2.4.3 方案 C：REST proxy / branch gateway

REST proxy 是 sidecar 的一个具体形态：它拦截 Iceberg REST Catalog 或 Delta Catalog Managed API，为不同 branch 返回不同 `metadata_location`。

```text
Spark / Trino / Flink
  -> branch-aware REST endpoint
       -> resolve ref from catalog property / header / URI prefix
       -> read/write version store
       -> optionally sync main to Unity/Polaris
```

它的优势是对引擎最透明，尤其适合 Iceberg。Iceberg REST 本来就把 table commit 表达成 `requirements + updates`，并且已有 `/transactions/commit` 多表原子提交接口。Polaris 已经在 spec 中暴露这个 endpoint，源码也有 `TransactionWorkspaceMetaStoreManager` 暂存多表变更后原子提交的实现路径。这说明“REST 层提交协调”是主流方向，可以作为 Git-like 的入口。

但 REST proxy 仍有几个硬问题：

| 问题 | 说明 |
|---|---|
| ref 表达方式不标准 | Iceberg REST spec 的 `prefix` 是 catalog prefix，不是 branch 语义；不同引擎对 header/catalog property 的支持不一 |
| list/namespace 语义 | `listTables(ns)` 必须返回该 ref 上的表集合，而不是底层 catalog 当前集合 |
| rename/drop 原子性 | rename/drop 必须成为 ref 上的 commit op，而不是直接改底层 catalog |
| credentials | 不同 branch 可能暴露不同 table locations，credential vending 也必须 ref-aware |
| 缓存失效 | 引擎和 catalog client 可能缓存 table metadata；merge 后如何刷新需要明确约束 |
| Delta CMT 限制 | Delta CMT 要求客户端经 managing catalog 访问，不能直接 path-based access；proxy 必须成为该 managing catalog 或其强一致前置层 |

REST proxy 适合作为迁移入口，但不适合作为“薄转发层”。它最终仍需要 version store、权限、GC 和恢复协议。

#### 2.4.4 方案 D：Hybrid transaction-first

还有一个不完全像 Nessie 的路线：先不做长期 branch，而是基于主流 catalog 的多表事务能力实现 “transaction-first Git-like subset”。

```text
阶段 1：多表 atomic publish
  staging writes -> validate -> /transactions/commit all tables

阶段 2：给每次 transaction 生成 catalog commit log
  commit_id -> changed tables -> old/new metadata_location

阶段 3：在 commit log 上增加 tag / revert / branch
```

这条路线利用 Iceberg REST `/transactions/commit` 或 Polaris `writeEntities()` 先解决最核心的跨表 all-or-nothing，再逐步增加 log、tag、revert、branch。它不像 Nessie 一开始就有完整 commit graph，但对 Unity/Polaris 这种主流 catalog 更容易落地。

缺点是后补 branch 会遇到结构性限制：如果历史 commit log 只记录 “main 从旧值到新值”，没有为每个 ref 维护独立 HEAD 和 index，后续做 branch/merge 时仍要补建 version store。因此 Hybrid 更适合作为 P0/P1，不是最终形态。

#### 2.4.5 四种方案对比

| 架构 | 原子性 | 改造深度 | 绕写风险 | 引擎兼容 | 适合阶段 |
|---|---|---|---|---|---|
| Integrated version store | 最强，ref CAS / catalog commit | 高 | 低 | 需要 ref-aware API | 最终形态 |
| Sidecar write proxy | 强，取决于是否唯一入口 | 中 | 高，除非封死直连 | 中 | 渐进迁移 |
| REST branch gateway | 强，若覆盖完整 REST 面 | 中高 | 中 | 较好，尤其 Iceberg | P1/P2 |
| Hybrid transaction-first | 多表事务强，Git-like 弱 | 中 | 低到中 | 好 | P0/P1 |

对 Unity/Polaris 的现实建议：

1. **先实现 transaction-first 的多表 atomic publish**：复用 Iceberg REST `/transactions/commit`、Polaris `writeEntities()` 或 Unity Delta CMT 这类能力，解决最痛的跨表一致发布。
2. **同时设计独立 version store，不要把 branch 维度硬塞进现有 table row 主键**：否则 rename/list/drop/authz 会快速失控。
3. **把 main 作为兼容物化视图**：传统客户端读 main；Git-like 客户端通过 ref-aware endpoint 读写 branch。
4. **在 merge main 之前做强制门禁**：branch 保护、数据质量、schema contract、权限审批，应先于复杂 semantic merge。
5. **最后再做自动冲突解决**：auto resolve 依赖表格式语义解析，不能成为第一阶段的基础假设。

#### 2.4.6 对表结构字段侵入的最终判断

如果采用 Integrated / REST gateway，底层 Iceberg 表 metadata JSON 可以保持不变；Catalog 只需要在 version store 中新增 content value 摘要。对 Unity/Polaris 原有 table/entity 表，建议只增加少量兼容字段或物化字段：

| 字段 | 目的 | 是否侵入核心语义 |
|---|---|---|
| `content_id` / `logical_table_id` | rename 后识别同一逻辑对象 | 低，可与现有 `table_id` 对齐 |
| `main_head_commit_id` | 让当前表行知道来自哪个 catalog commit | 中，便于审计和恢复 |
| `current_metadata_location` | 已有或等价已有字段 | 低 |
| `last_catalog_commit_id` | 展示/审计 | 低 |
| `ref_id` | 若直接在表行上多版本化才需要 | 高，不建议作为主路线 |

真正必要的结构应放在独立 version store 中，而不是让现有 `tables` 表承担 commit graph 的职责。

### 3.3 Release notes 暴露的近期工程重心

从 recent releases 和本地 `site/docs/releases.md` 看，Nessie 近期不是在大改 Git-like 原语，而是在补“可作为主流 catalog 使用”的工程面：

| 主题 | 例子 | 含义 |

| Iceberg REST 能力补齐 | release notes 中出现 “time-travel and branch/tag selection for Iceberg REST in all cases”、Trino config-helper endpoint | 让标准 Iceberg REST 客户端也能使用 Nessie 的版本能力 |

| 对象存储与凭证 | S3/GCS/ADLS 配置、credential vending、secret 管理、request signing | Nessie Catalog 不只是 metadata store，还要安全发放数据访问凭证 |
| Merge 体验 | 旧 release notes 出现 detailed merge/transplant result、force/drop、external conflict resolution、content-aware merge API preparation | Nessie 已经有冲突处理扩展点，但仍偏“外部提供 resolved content” |

这支持一个判断：Nessie 的基础 Git-like 模型已经相对稳定，近期 roadmap 更偏 catalog 产品化、引擎互通和运维能力，而不是重新发明 refs/commits。

### 3.4 源码层暴露的设计约束

**约束一：stateless server + CAS，不做分布式共识。**

`versioned/storage/README.md` 明确说 Nessie server 必须保持 stateless，服务端之间不通信，也没有 distributed consensus。这是 Nessie 高吞吐和易部署的基础，但也意味着同一 branch 的高并发写入只能靠 OCC/CAS/retry，而不是 leader/lock 串行化。

源码已有 `CommitRetry`，按 retry 次数和 timeout 做指数退避。README 也描述了两个进程持续写同一 branch 时，大 commit 可能因时间更长而反复超时；新 storage model 通过 object cache 和 idempotent object writes 提高了上限，但 README 也承认问题不是 100% solvable，除非引入 coordinated commit-target-lease mechanism。

**约束二：merge 冲突粒度仍是 ContentKey 级。**

`BaseCommitHelper` 的 merge/transplant 冲突处理围绕 `ContentKey`、`CommitOp`、`MergeBehavior` 运行。它能处理 `NORMAL`、`DROP`、`FORCE`，也能接受 `resolvedContent`；但内核没有自动解析 Iceberg metadata 并合并 schema/manifest 的逻辑。第 4 章提出的 semantic merge，本质上就是利用这里的 `resolvedContent` 扩展点，把外部生成的合法 content value 注入进去。

**约束三：delete/unchanged 校验仍有模型缺口。**

`CommitImpl` 中存在明确 TODO：对 Delete/Unchanged 做更严格处理，需要 model/API 支持 expected value / expected content。这说明 Put 的 expected-content 校验更成熟，Delete 类操作的冲突语义仍有补强空间。

**约束四：merge 不是 Git 普通双父提交。**

第 2 篇已经复核：当前 merge 是 squashed target-side commit，transplant 保留 individual commits；`secondaryParents` 可记录来源，但主链仍以 target 父提交为主。这个选择降低了 index/读路径复杂度，但与 Git DAG 的语义不完全相同。

**约束五：GC 必须理解版本引用和表格式引用两层图。**

Nessie GC 官方文档有独立 mark/sweep、deferred deletion、identified live contents repository 等章节，说明 GC 已是复杂子系统。社区 issue #11273 还报告 dropped tables 的 metadata/data 清理问题。这类问题的根源是：Nessie 管 catalog refs，Iceberg metadata 再管 manifest/data files；GC 必须跨两层引用图计算 live set。

### 3.5 社区/官方已暴露的问题清单

| 问题 | 类型 | 证据 | 工程影响 | 可行优化 |
|---|---|---|---|---|
| 工具层事务能力未完全暴露 | 官方限制 | Transactions 文档明确说 tools still need work | 用户很难直接用 Spark/Trino 写出完整 serializable multi-table transaction | 增强 Spark SQL extension、REST client、Trino/Flink connector |
| 高并发同 branch 写入 timeout | 社区问题 + 源码约束 | issue #10423 报 merge timeout；storage README 描述同 ref commit retry timeout | WAP/CI 大量并发 merge main 时尾延迟高 | branch-level lease、队列化 merge、commit-target routing、preflight merge cache |
| Trino Iceberg REST 限制 | 官方限制 | 最新 Trino 文档说当前只支持 S3；OAuth endpoint 配置能力缺失，需要手工 token | Trino 生产接入需要额外配置和安全治理 | credential vending 文档/模板、等待 Trino REST OAuth 能力完善 |
| Auto conflict resolution 不足 | 设计限制 | `MergeBehavior` 支持外部 resolved content，但没有内置 semantic merge | 兼容 schema 变更、append+compaction 等场景仍可能人工处理 | 表格式 semantic merge planner |

| GC/drop table 边界 | 社区问题 | issue #11273 | 历史分支、drop table、metadata 文件清理之间容易错漏 | tombstone root、drop table live-set summary、GC dry-run 报告 |
| 多租户与原子边界冲突 | 架构限制 | 单 repo/ref CAS 最适合最大原子边界；企业 catalog 还需要租户、quota、delegated admin | 大平台可能不希望一个 repo 覆盖全部原子边界 | repo 分层、catalog group、跨 repo transaction 只做显式协调 |
| Git 语义差异 | 设计选择 | merge squash、transplant individual、`secondaryParents` | 熟悉 Git 的用户会误解 merge history | UI/文档明确区分 data merge 与 Git merge |

### 3.6 Roadmap 推断：短中长期

**短期：把 Iceberg REST Catalog 做稳。**

优先级最高的是引擎兼容、credential vending、object store、auth、Trino/Spark/Flink/PyIceberg 体验。原因很直接：如果主流引擎不能稳定通过标准 REST Catalog 使用 Nessie，Git-like 能力只能停留在少数专用客户端中。

**中期：补全事务工具链与运维闭环。**

Nessie 已有 cross-table transaction primitives，但工具层未充分暴露。中期应围绕：

- SQL/API 形式的 `START TRANSACTION ... COMMIT` 或等价客户端上下文。
- dry-run merge / transaction validation。
- branch protection 与 required checks。
- GC dry-run、deferred delete、drop table recovery。
- observability：commit retry、merge conflict、GC live-set、credential vending metrics。

**中长期：处理高冲突和语义冲突。**

高冲突 branch 可以走两条路线：一是保持 stateless，用 routing/lease/queue 降低 CAS retry；二是引入官方文档提到的 pessimistic locking，让 Nessie server 持有事务状态。后者会改变 Nessie 的简洁部署模型，需要 timeout、deadlock detection、cancellation protocol。

语义冲突则需要表格式参与。Nessie 当前扩展点允许外部 resolved content；下一步可以把常见 safe merge 规则产品化，例如 schema add-only merge、property map merge、append-only snapshot merge。这里应保持保守：只自动合并表格式库能验证正确的变更，行级业务冲突仍应交给计算引擎或业务规则。

### 3.7 对 Nessie 当前形态的工程评价

Nessie 已经解决了最难的基础原语：immutable content objects、refs pointer CAS、commit log、catalog-wide index、merge/transplant replay、diff/revert 基础能力。它的问题不再是“能不能实现 Git-like”，而是“如何把 Git-like 变得更懂数据、更快、更容易被主流引擎采用”。

换句话说，下一阶段竞争点大概率是：

- 与 Iceberg REST / Delta CMT / Polaris / Unity 的互操作。
- 高并发 branch 写入和 merge 的尾延迟。
- GC、权限、审计、血缘、数据质量检查等平台能力。
- 对同一表内兼容变更的自动/半自动 conflict resolution。
- 把 Git-like 操作包装成 Data PR、release、rollback、CI/CD，而不是只暴露底层 API。

## 4. 除 Nessie 双逻辑表迁移/外套之外，还能做哪些创新？

### 4.1 语义感知 conflict resolution

当前 Nessie 的默认冲突判断停在 ContentKey 级：同一表的 `ContentValueObj` 变了，就需要人工决策或外部 resolved content。可以向下解析 Iceberg/Delta metadata，增加几类可自动合并的规则：

| 冲突类型 | 可自动解决条件 | 可能策略 |
|---|---|---|
| append-only 数据提交 | 两边新增 snapshot 均只 append，且分区/data file 无业务冲突 | 构造新的 Iceberg metadata，包含双方 manifest/data files |
| 独立 schema add-column | 两边都只添加新列，field id 不冲突，类型兼容 | 合并 schema，生成新 schema id |
| properties 合并 | 两边修改不同 property key | map union；同 key 不同值仍冲突 |
| sort/order/spec 非重叠修改 | 一边改 sort order，一边 append 数据，且旧读写兼容 | 应用双方 metadata update |
| compaction vs append | compaction 只重写旧文件，append 新文件，Iceberg validation 通过 | 类似 Iceberg 内部 rewrite/append 并发规则 |

这类能力不应由 Catalog 盲目改 Parquet 行数据，而是作为“metadata semantic merge driver”。Catalog 可以调用表格式库或专门的 merge planner，最后仍以一个新的合法 table metadata JSON 作为 resolved content。

### 4.2 自动 resolve 的安全边界

建议把自动 resolve 分成三档：

| 档位 | 行为 | 适用 |
|---|---|---|
| `AUTO_SAFE` | 只自动合并表格式规范可证明无冲突的变更 | append-only、不同 property key、add-only schema |
| `AUTO_WITH_POLICY` | 需要数据 contract/owner policy 授权 | schema rename、type widening、partition spec 演进 |
| `MANUAL` | 必须人工或上层业务生成 resolved content | delete/update 同行、同 property 冲突、破坏性 schema 变更 |

这样可以避免把“AI 猜一个合并结果”混入核心事务路径。LLM 可以参与解释和建议，但最终进入 commit 的 resolved content 应由规则引擎/表格式库验证。

### 4.3 易用性：把 Git workflow 变成 Data workflow

比起底层结构，用户真正感受到的是工作流：

- **Pull Request for Data**：branch diff、受影响表、schema/data quality summary、样本对比、血缘影响范围、审批记录。
- **Branch protection**：main 禁止直接写；merge 必须通过 Great Expectations/Deequ/dbt tests；生产 tag 不可变。
- **Data CI**：每次 branch commit 自动跑 profiling、freshness、null ratio、schema drift 检测。
- **Release tag**：为月报、模型训练集、监管报送创建不可变 release tag，并绑定 retention。
- **一键 rollback / revert plan**：回滚前自动展示受影响表、下游血缘、需要清理/保留的文件。

这些能力不是 refs/objs 自然带来的，但它们决定 Git-like Catalog 是否能从“内核正确”变成“团队愿意用”。

### 4.4 性能：热点 branch 与大 catalog 的优化

Nessie 新 storage model 已经通过 content-addressed objects、object cache、incremental/reference index、striped index 降低读写成本。进一步创新可以在以下方向：

- **branch-local lease / soft leader**：对同一 branch 的写请求尽量路由到同一 server，减少 CAS retry。Nessie storage README 也提到 coordinated commit targets 的可能性。
- **merge preflight cache**：对 source/target/common ancestor 的 diff 预计算并缓存，dry-run merge 和真实 merge 复用。
- **materialized ref view**：为高频 branch 维护可查询的 materialized `ContentKey -> value` view，降低 list 和 prefix lookup 成本。
- **diff index**：按 namespace/table 维护 commit touched-key bitmap，快速回答“这两个 ref 之间哪些表变了”。
- **large commit chunking**：一个 catalog commit 修改上万表时，把操作分片存储，但 ref pointer 仍一次 CAS。

### 4.5 GC 与文件生命周期创新

Git-like Catalog 的 GC 难点是：Catalog 的历史 ref 会保留 metadata pointer，而表格式 metadata 又引用 data files。仅扫描当前 main 会误删历史 tag/branch 仍需要的文件；仅保守保留又会造成对象存储膨胀。

可考虑：

- 以 `ref/tag retention` 作为 GC root，先算 catalog live content，再交给表格式 live files 扫描。
- merge/revert/drop table 时记录 tombstone 与 drop metadata root，专门覆盖 dropped table 的 GC 场景。
- 对每次 commit 生成 lightweight file-reachability summary，例如 metadata file 列表、manifest list 摘要、统计 bloom。
- GC dry-run 报告纳入 Data PR：merge 前显示新增可回收/需保留文件规模。

### 4.6 与主流 Catalog 的渐进式落地方案

如果目标是 Unity/Polaris 这类主流 catalog，建议分阶段：

| 阶段 | 能力 | 侵入度 |
|---|---|---|
| P0 | 只支持 read-only tag：为 catalog 当前状态打快照，支持按 tag 读 | 低 |
| P1 | 支持 branch + isolated writes，但 merge 只允许 fast-forward | 中 |
| P2 | 支持 catalog-wide commit、diff、revert、squash merge 和表级冲突检测 | 中高 |
| P3 | 支持 semantic merge、branch protection、data PR、GC roots | 高 |
| P4 | 与 Delta CMT / Iceberg REST transactions / external engines 深度互通 | 高 |

工程上不要一开始就追求完整 Git。先做 “branch + WAP + fast-forward publish + audit log”，就能覆盖大量数据发布场景。

## 5. 最小可运行 Demo：验证有限场景的 semantic auto resolve

本章目标不是把 Nessie 改造成完整 semantic merge 引擎，而是验证一个更小、可闭环的命题：

> Nessie 当前在 catalog/version-store 层把 Iceberg table content 当作 opaque value；但外部 resolver 可以通过 Nessie 保存的 `metadataLocation` 读取 Iceberg metadata JSON，对安全可判定的表结构变更生成一个新的 Iceberg metadata 文件，再通过 Nessie 已有的 `MergeKeyBehavior.resolvedContent` 完成一次带 resolved content 的 merge。

### 5.1 Demo 范围和安全边界

建议先只支持一个非常窄的场景：

- 表格式只选 Iceberg。
- 冲突对象只允许同一张表 `T`。
- 两个分支都只做 schema-only 的 `ADD COLUMN`。
- 不允许数据写入、delete file、manifest rewrite、partition spec 变更、sort order 变更、table property 变更、rename/drop/type widening。
- 新增列之间不能同名，不能有类型冲突。
- 如果两个分支分配了相同 Iceberg field id，只允许在“没有任何数据文件引用新增字段”的前提下重新分配 field id。

这个边界很重要。Iceberg 的 schema identity 依赖 field id，不只是列名。两个分支都从同一个 base schema 增加列时，常见情况是两边都拿到相同的 next field id。对纯 schema metadata 来说，可以在最终 resolved metadata 里给其中一侧新增字段重新分配新 id；但如果任一分支已经写入数据文件，这些 field id 可能已经进入数据/manifest 语义，demo 必须拒绝自动合并。

### 5.2 需要拉取和运行的组件

最小 demo 可以分两档。

| 档位 | 组件 | 是否需要数据库 | 用途 |
|---|---|---|---|
| P0：最小临时验证 | Nessie server in-memory、MinIO、Spark + Iceberg runtime 或 PyIceberg、semantic-merge-driver | 不需要 | 验证冲突、读取 metadata、生成 resolved content、调用 Nessie merge |
| P1：接近生产形态 | Nessie server + JDBC/PostgreSQL、MinIO、Spark + Iceberg runtime、semantic-merge-driver | 需要 PostgreSQL | 验证 version store 持久化、重启恢复、并发/重试、审计记录 |

本地已有 Nessie 源码时，可以复用 `nessie-src/docker` 下的 compose 示例。最小验证建议优先用 in-memory Nessie 降低变量；一旦 resolver 逻辑跑通，再切到 PostgreSQL/JDBC 后端确认 persistence 行为。

需要拉取或准备的最小清单：

- Nessie server：使用官方镜像，或从本地 `nessie-src` 构建。
- MinIO：使用官方镜像，创建一个 warehouse bucket。
- Spark + Iceberg runtime：使用本地 Spark 发行版并加载 Iceberg runtime jar，或使用预置 Iceberg/Spark 的测试镜像。
- semantic-merge-driver：新建一个很小的 Java/Maven 或 Gradle 工程，依赖 Nessie client/model、Iceberg core、Iceberg AWS 或 Hadoop FileIO。
- PostgreSQL：仅 P1 需要，用于替换 in-memory version store。

推荐组件职责：

- Nessie server：提供 branch、commit、merge、contents API，以及 Iceberg REST catalog 接入点。
- MinIO：承载 Iceberg warehouse，包括 metadata JSON、manifest、data files。
- Spark SQL 或 PyIceberg：制造真实 Iceberg 表和真实 `ALTER TABLE ADD COLUMN` metadata。
- semantic-merge-driver：独立 Java 小程序或服务。Java 更合适，因为可以同时使用 Nessie Java client、Nessie model 和 Iceberg `TableMetadataParser`。
- PostgreSQL：P1 才需要，用于 Nessie JDBC version store 的持久化验证。

拓扑如下：

```text
Spark SQL / PyIceberg
  -> Nessie Iceberg REST Catalog
  -> MinIO warehouse

semantic-merge-driver
  -> Nessie REST / Java API
  -> Iceberg FileIO
  -> MinIO metadata JSON

Nessie server
  -> in-memory version store 或 PostgreSQL/JDBC version store
```

### 5.3 Demo 流程

基础流程：

1. 在 `main` 创建 Iceberg 表 `db.T`，初始 schema 为 `id bigint`，记录 `baseHash` 和 `baseMetadataLocation`。
2. 从 `main@baseHash` 创建两个分支 `a`、`b`。
3. 在分支 `a` 执行 `ALTER TABLE db.T ADD COLUMN col_a string`。
4. 在分支 `b` 执行 `ALTER TABLE db.T ADD COLUMN col_b string`。
5. 正常 merge `a -> main`，应成功，此时 `main` 的表 schema 是 `id, col_a`。
6. 正常 merge `b -> main`，预期在 `db.T` 的 content value 上冲突，因为 source 和 target 都修改了同一个 `ContentKey`。
7. 运行 semantic-merge-driver，针对 `db.T` 读取 base、source、target 三份 Iceberg metadata，判断是否满足安全规则。
8. resolver 写出一份新的 metadata JSON，schema 为 `id, col_a, col_b`，并构造新的 Nessie `IcebergTable` content value。
9. resolver 再次调用 Nessie merge `b -> main`，使用 squash merge 形态，并携带 per-key `MergeKeyBehavior`：`expectedTargetContent` 是当前 `main` 上的 `db.T` content，`resolvedContent` 是 resolver 新生成的 `IcebergTable`。
10. 验证 `main` 上读取 `db.T` 可以看到两列，commit log 中存在 merge commit，且 MinIO 中新增了 resolver 写出的 metadata JSON。

验收标准：

- 不带 resolver 时，`b -> main` 必须稳定复现冲突。
- 带 resolver 时，merge 成功且最终 schema 同时包含 `col_a` 和 `col_b`。
- 任一分支如果同时写入数据、删除列、改类型、改 partition spec、改 table property，resolver 必须拒绝自动合并。
- 如果 target 在 resolver 计算期间又前进，`expectedTargetContent` 校验必须失败，resolver 重新读取后再判断。

### 5.4 resolver 如何深入到表结构级别

Nessie core 的 version store 不理解 Iceberg schema，它只比较 content value。对 Iceberg table，这个 value 主要包括：

- `metadataLocation`
- `snapshotId`
- `schemaId`
- `specId`
- `sortOrderId`
- `contentId`

源码中的 `IcebergTable` model 也明确说明，Nessie 保存的是 Iceberg `TableMetadata` 文件位置和若干 ID 摘要。也就是说，Nessie core 看到的是 “metadata of metadata”，不是表字段列表。

要深入到 schema 级别，有三种路径：

| 路径 | 可行性 | 说明 |
|---|---|---|
| 外部 resolver 读取 `metadataLocation` | 最高 | 通过 Nessie contents API 拿到 IcebergTable，再用 Iceberg FileIO 读取 metadata JSON |
| Nessie Catalog 层内置 resolver | 中高 | Catalog 层已经有 Iceberg metadata 读写、object storage 访问、credential/signing 相关代码，适合承载语义逻辑 |
| VersionStore core 内置 resolver | 不建议 | 会让通用 version store 依赖 Iceberg/Delta/Hudi 语义，破坏格式无关边界 |

现有源码证据支持前两条路径：

- `api/model/IcebergTable.java` 保存 `metadataLocation`、`snapshotId`、`schemaId`、`specId`、`sortOrderId`。
- `versioned/tests/.../AbstractMerge.java` 已覆盖 `MergeKeyBehavior.expectedTargetContent + resolvedContent` 的 merge 行为。
- `versioned/storage/.../BaseCommitHelper.java` 实现了 `expectedTargetContent` 校验和 `resolvedContent` 替换逻辑，并限制 resolved content 用在 squashing merge 路径。
- `catalog/format/iceberg/.../TestJsonSerialization.java` 使用 Iceberg `TableMetadataParser.fromJson/toJson`。
- `gc/gc-iceberg/.../IcebergContentToFiles.java` 使用 `TableMetadataParser.read(io, metadataLocation)`，并继续解析 snapshot、manifest 和 data/delete files。
- `gc` 的集成测试包含 Nessie + Spark + Iceberg + MinIO 的 full round trip。

因此答案是：Nessie core 目前不会自动深入表结构；但 Nessie 仓库里已经存在访问 Iceberg metadata 和对象存储文件的工具链。最小 demo 不需要改 core，直接做外部 resolver 最稳。

### 5.5 resolver 的核心算法

输入：

- `sourceRef = b`
- `targetRef = main`
- `baseHash`
- `contentKey = db.T`
- `warehouse/object-store credentials`

处理步骤：

1. 用 Nessie API 读取 `db.T` 在 `baseHash`、`sourceRef`、`targetRef` 上的 `IcebergTable` content。
2. 用 Iceberg `FileIO` 加载三份 metadata JSON。MinIO/S3 用 `S3FileIO`；本地文件可用 `HadoopFileIO`。
3. 校验三份 metadata 的 table uuid/location 一致。
4. 校验 source 相对 base 只有新增列集合 `S_add`，target 相对 base 只有新增列集合 `T_add`。
5. 校验 `S_add` 与 `T_add` 列名不相交，类型合法，且没有 nested field 的不安全改动。
6. 校验 current snapshot、manifest list、partition spec、sort order、properties 未发生非 schema 改动。
7. 生成 resolved schema：`base_columns + target_added_columns + source_added_columns`。顺序可以固定为 target 在前、source 在后，保证确定性。
8. 处理 field id：如果新增字段 id 冲突，且确认没有数据文件引用这些新增字段，则给 source 侧冲突字段分配新的 field id，并更新 `last-column-id`。
9. 写出新的 Iceberg table metadata JSON。生产实现应尽量使用 Iceberg Java API 或兼容 Iceberg metadata writer；POC 可以先用 Iceberg `TableMetadataParser` 验证序列化结果，但不建议长期手写 JSON。
10. 构造 Nessie `resolvedContent`：`IcebergTable.of(newMetadataLocation, snapshotId, newSchemaId, specId, sortOrderId, contentId)`。
11. 调用 Nessie merge，并为 `db.T` 设置 `MergeKeyBehavior.of(key, NORMAL, expectedTargetContent, resolvedContent)`。

伪代码：

```java
IcebergTable base = getTable("main", baseHash, key);
IcebergTable source = getTable("b", sourceHash, key);
IcebergTable target = getTable("main", targetHash, key);

TableMetadata bm = TableMetadataParser.read(fileIO, base.getMetadataLocation());
TableMetadata sm = TableMetadataParser.read(fileIO, source.getMetadataLocation());
TableMetadata tm = TableMetadataParser.read(fileIO, target.getMetadataLocation());

ResolvedSchema resolved = resolveAdditiveSchemaOnly(bm, sm, tm);
String newMetadataLocation = writeResolvedMetadata(tm, resolved);

IcebergTable resolvedContent = IcebergTable.of(
    newMetadataLocation,
    target.getSnapshotId(),
    resolved.schemaId(),
    target.getSpecId(),
    target.getSortOrderId(),
    target.getId());

mergeBranch(
    "b",
    "main",
    MergeKeyBehavior.of(key, MergeBehavior.NORMAL, target, resolvedContent));
```

关键点是 `expectedTargetContent = target`。这相当于 CAS：resolver 只对它刚刚检查过的 target 状态负责。如果 `main` 在 resolver 期间又变了，Nessie merge 会失败，resolver 必须重新计算。

### 5.6 是否需要访问数据文件级别

对本 demo 的安全场景，原则上不需要读 data file 内容，但需要能证明没有数据层语义被影响。最低限度需要读取 metadata/snapshot/manifest 信息：

- 如果两边只是 schema metadata 更新，没有新增 snapshot 或 manifest，则可以不读 data file。
- 如果存在新增 snapshot、manifest 或 data/delete files，demo 阶段直接拒绝。
- 如果以后要支持更复杂场景，例如两个分支都 append 数据但 schema add 不冲突，需要读 manifest 和 data file schema/metrics，复杂度会明显上升。

Nessie 现有代码里有可复用方向：

- `gc-iceberg` 的 `IcebergContentToFiles` 已经能从 Iceberg content reference 出发读取 table metadata、snapshot、manifest，并枚举 data/delete files。
- `gc-iceberg-files` 封装了 Iceberg `S3FileIO`、`ResolvingFileIO` 和对象存储 listing。
- Catalog REST 服务里有针对 Iceberg metadata location、object IO、S3 signing/credential vending 的处理。

但这些能力当前服务的是 catalog/GC/import 等流程，不是 merge resolver。生产实现更合理的位置是 Catalog 层新增 `SemanticMergeService`，复用 FileIO 和 table-format parser，再调用 version store 的 `resolvedContent` merge primitive。

### 5.7 可行性判断和后续扩展

可行性结论：针对“两个分支分别给同一 Iceberg 表增加不同列，且没有数据写入”的场景，auto resolve 是可行的。原因是冲突发生在 Nessie content value 层，但真正的语义冲突判断可以通过 `metadataLocation` 下钻到 Iceberg metadata 完成；Nessie 已经提供了把 resolved content 交回 merge 的机制。

主要风险：

- Iceberg field id 冲突不能只按列名合并，必须处理 id 分配。
- 不能把 schema-only 结论扩展到已写数据的分支。
- 不能绕过 object-store 权限和 catalog credential vending。
- 新 metadata JSON 必须满足 Iceberg spec，否则后续引擎可能无法读取。
- resolver 是一个额外 writer，需要和 Nessie target hash 做 CAS，避免读旧写新。

下一阶段可以逐步扩展：

- 支持多个互不相关表的 additive schema merge。
- 支持 nested struct 追加字段，但拒绝 list/map 内部不安全改动。
- 支持 Data PR 中展示 schema diff 和自动合并建议。
- 支持 conflict policy：某些 namespace/table 允许 auto resolve，其他表必须人工审批。
- 将 resolver 结果写入 audit event，记录 base/source/target metadata location、规则命中情况和拒绝原因。

## 6. 对四个问题的直接回答

### 6.1 是否存在其他层级的多表版本控制？

有，但要区分“多表事务”和“多表版本控制”。

- Iceberg/Paimon 是单表 branch。
- Delta/Hudi 是单表 log/time travel/savepoint。
- Iceberg REST `/transactions/commit` 和 Delta CMT 是多表原子提交/协调，但不是完整 Git-like。
- lakeFS 是对象层 Git-like，可覆盖多表文件集合，但不天然理解表格式语义。
- Nessie/Bauplan 这类 Catalog/Data Branch 才接近 catalog-wide Git-like。

因此，目前开源主流里“表格式级别的多表版本控制”还没有成为事实标准；更现实的方向是 catalog/transaction manager 层。

### 6.2 Unity/Polaris 要实现 Git-like 至少加什么？

至少加一套 version store：`refs + commits + content values + indexes + commit ops + branch policies + GC roots`。表结构层面，Iceberg 不必改 table metadata JSON；catalog 中的 content value 要保存 `metadata_location` 和若干摘要字段。Unity/Polaris 现有表实体可以继续表示 main/current，也可以逐步改造成 ref-aware lookup，但不建议只在原表行上加 `branch_id` 解决问题，因为这会扩散到权限、rename、drop、list、credential vending 和 GC 的所有路径。

### 6.3 Nessie roadmap 与已知不足是什么？

Roadmap：Iceberg REST Catalog 化、新 storage model、Spark/Flink/Trino 等引擎接入、Java/Quarkus/认证/对象存储生产化、多表事务 primitive 与未来 pessimistic locking。

不足：冲突粒度偏粗、没有内置 semantic auto merge、merge/commit 热点可能 timeout、GC/drop table 边界复杂、delete validation 仍有 TODO、merge 形态是 squash 而非完整 Git DAG、工具对 transaction primitive 的暴露仍不足。

### 6.4 除双逻辑表迁移/外套之外的创新是什么？

最值得做的是“让 Git-like 懂数据”：

- 自动/半自动 semantic merge。
- Data PR、branch protection、quality gate。
- dependency-aware 多表发布。
- 版本化 lineage 和影响分析。
- 高性能 diff/cache/materialized ref view。
- 安全 GC 和 dropped table recovery。
- 与 Iceberg REST transactions、Delta CMT、Polaris/Unity 权限模型互通。
