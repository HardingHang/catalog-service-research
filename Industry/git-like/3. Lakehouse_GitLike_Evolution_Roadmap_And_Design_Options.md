# Lakehouse Git-like 演进、主流 Catalog 改造与创新方案讨论

> 调研日期：2026-05-18。本文独立讨论 Lakehouse Git-like 的层级演进、Unity Catalog / Apache Polaris 等主流 Catalog 的改造路径、Nessie roadmap 与已知不足，以及 metadata-of-metadata 之外的创新方向。

---

## 1. Lakehouse Git-like 的层级演进

本章判断：目前 Lakehouse 领域确实存在多个层级的版本化方案，但主流开源生态中尚未形成“表格式级别的多表 Git-like 版本控制”事实标准。Iceberg、Paimon 等表格式已经具备单表 branch/tag；Iceberg REST、Lakekeeper、Polaris、Unity/Delta Catalog-Managed Tables 正在强化 Catalog 级事务协调；真正接近跨表 Git-like 的能力仍主要位于 Catalog、对象存储版本层或 Pipeline/Data Product 控制面。

### 1.1 按版本边界划分的能力谱系

讨论 Git-like 之前，需要先区分三类概念：

- **单表版本控制**：版本边界是一张表，典型能力是 snapshot、time travel、branch/tag、savepoint。
- **多表事务协调**：版本边界是一次跨表提交，要求 all-or-nothing，但不必然存在长期 branch、merge、diff、revert。
- **多表版本控制**：版本边界是一个 catalog/repository 的一致快照，要求 branch、commit log、merge、tag、diff、revert、审计和 GC 共同成立。

| 层级 | 代表技术 | 版本边界 | 是否接近 Git-like | 跨表能力 | 关键判断 |
|---|---|---|---|---|---|
| 表格式层 | Iceberg branch/tag、Paimon branch | 单表 snapshot lineage | 部分接近 | 否 | 适合单表 WAP、审计、回滚；不能表达“一次提交修改多张表” |
| 表事务日志层 | Delta transaction log、Hudi timeline/savepoint | 单表 commit timeline | 不接近 | 否 | 强在单表 ACID/time travel；跨表一致性依赖外部协调 |
| Catalog 事务协调层 | Iceberg REST `/transactions/commit`、Lakekeeper、Polaris、Gravitino REST、Delta CMT / Unity Catalog managed tables | 多表提交边界 | 不是完整 Git-like | 是 | 解决多表原子提交，但不天然提供长期 branch/merge/diff/revert |
| Catalog Git-like 层 | Nessie、Bauplan data branches | catalog/repository 快照 | 是 | 是 | 最接近 Git-like：branch、commit、merge、tag、log |
| 对象存储版本层 | lakeFS | repository 内对象路径集合 | 是 | 与文件集合一致 | 格式无关；默认不理解 Iceberg/Delta 的表格式语义 |
| Pipeline / Data Product 层 | Bauplan、LakeVilla 类事务管理研究 | pipeline run 或长事务 | 部分接近 | 是 | 把版本控制与作业发布、数据契约、恢复机制结合 |

### 1.2 表格式层：Iceberg 与 Paimon 的单表 branch

Iceberg 官方文档将 branch/tag 定义为表 snapshot 的命名引用。Branch 指向某条 snapshot lineage 的 head，tag 指向特定 snapshot。典型用法是 audit branch：写入先进入 audit branch，经数据质量校验后再 `fastForward` 到 main。这个能力对单表 WAP、审计保留、单表回滚非常有价值。

但是 Iceberg branch 的边界仍然是单表。`sales.orders` 与 `sales.customers` 即使命名为相同的 `audit` branch，也不是同一个版本树，不能天然表达“订单表、客户表、指标视图在同一次 catalog commit 中发布”。

Paimon 也提供单表 branch。其文档强调 branch 可用于 streaming 场景的数据纠错和验证，支持从 tag 创建 branch、读写 `t$branch_branch1`，并 fast-forward 回 main。Paimon 的能力同样限定在单表范围内。

因此，表格式层 branch 是重要基础能力，但不是 catalog-wide Git-like。它可以减少 Catalog 层的一部分诉求，例如单表 WAP 和单表回滚，但替代不了跨表一致发布、跨表审计日志和跨表 revert。

### 1.3 表事务日志层：Delta 与 Hudi 的单表时间线

Delta Lake 的核心版本能力来自 `_delta_log`，提供单表 ACID、time travel、rollback、change data feed 等能力。Hudi 的 timeline/savepoint 也面向单表 commit 和恢复场景。

这类方案的强项是表内事务和数据文件管理，弱项是跨表协调。多个 Delta/Hudi 表之间没有共享 commit 对象，也没有统一 branch head。若一个 pipeline 同时更新事实表、维表和汇总表，传统做法通常依赖调度系统、补偿逻辑或业务约定来避免部分可见。

Delta Catalog-Managed Tables 改变了这一趋势。Delta 4.x 引入 `catalogManaged` reader-writer table feature，由 managing catalog 协调提交原子性，并要求 Delta client 通过 catalog 发现和访问表，不再支持直接 path-based access。Unity Catalog 0.4.x 的 managed tables 也体现了相同方向：Catalog 逐步成为表状态、提交校验、权限治理和多表事务的协调点。

### 1.4 Catalog 事务协调层：多表原子提交正在标准化

Iceberg REST Catalog OpenAPI 已包含 `POST /v1/{prefix}/transactions/commit`，用于原子提交多个表的更新。Iceberg 官方 roadmap 也将 multi-table transaction support 列为社区工作方向。

该方向已经被多个 Catalog 实现采用：

- **Polaris**：定位为 Iceberg REST Catalog，Catalog 的基本职责包括保存表名到当前 metadata file 的指针，并原子更新该指针。Polaris 1.4.x 文档强调集中、安全地对 REST-compatible 引擎提供读写访问。
- **Lakekeeper**：实现 Iceberg REST Catalog，明确支持 `transactions/commit`、credential vending、remote signing 与多租户管理，但不提供 Nessie 式 Git-like branch。
- **Gravitino Iceberg REST Server**：支持 Iceberg REST API 1.10 的多数 namespace/table/view 接口，但文档列出 multi table transaction 尚未实现，说明该能力正在成为 REST Catalog 实现之间的重要分水岭。
- **Unity Catalog managed tables / Delta CMT**：将 Delta 表的提交协调上移到 Catalog，使 Catalog 能够校验提交内容、协调多表事务、统一权限和审计。

这些能力说明 Lakehouse 行业正在把“提交协调权”从对象存储和文件系统原语上移到 Catalog。但多表事务仍不等价于 Git-like。它解决的是“这一次提交是否 all-or-nothing”，不自动提供“长期分支如何演进、如何 merge、如何 diff、如何 tag、如何基于历史安全 GC”。

### 1.5 Catalog Git-like 层：Nessie 与 Bauplan

Nessie 的版本边界是 catalog branch 的 HEAD。一个 branch HEAD 下可以同时包含多张 Iceberg 表、视图和 namespace 的一致状态。每次 commit 都是 catalog-wide 的 key-level 变更集合，merge/transplant 在 ContentKey 层处理冲突。这是当前开源生态中最接近 Git-like Catalog 的实现。

Bauplan 则更强调 data branch 与 pipeline run 的结合。其文档将 data branch 描述为隔离开发环境，用户可以在 branch 中导入数据、运行 pipeline、验证结果，再原子发布到 main。相关论文也强调 typed table contracts、Git-like data versioning 和 transactional runs 的组合。这说明 Git-like 在数据平台中不只是 Catalog API 问题，也可能成为 Data Product 发布模型的一部分。

### 1.6 对象存储版本层：lakeFS 的格式无关版本控制

lakeFS 在对象存储之上提供 repository、branch、commit、tag、merge。其 branch 是指向 commit 的 pointer，创建 branch 是 zero-copy；commit 是 repository 全部对象内容的不可变 checkpoint；merge 生成以目标和来源为父的提交。

lakeFS 的优势是格式无关，Parquet、JSON、模型文件、图片或任意对象都可以纳入同一版本空间。代价是它默认看到的是对象路径集合，而不是表格式中的 schema、snapshot、manifest、delete files 等语义。若以 lakeFS 承载 Iceberg/Delta 版本控制，仍需要保证表 metadata 与数据文件引用在对象层版本之间保持一致，否则容易出现“文件集合可回滚，但表格式语义不一致”的风险。

### 1.7 本章小结

目前可以形成以下判断：

- 表格式层的 branch/tag 解决单表版本控制，不解决多表版本树。
- Iceberg REST、Delta CMT、Polaris、Lakekeeper、Unity Catalog managed tables 代表 Catalog 事务协调路线，是主流演进方向。
- Nessie/Bauplan 更接近完整 Git-like，但它们不是简单的表字段扩展，而是引入了 catalog/repository 级版本边界。
- 对自研 Catalog 而言，务实路径通常是先实现多表事务与 audit log，再决定是否进入完整 Git-like branch/merge。

## 2. 基于 Unity / Polaris 等主流 Catalog 实现 Git-like 的设计

本章判断：在 Unity Catalog、Apache Polaris 等主流 Catalog 中实现 Git-like，核心不是给每张表增加几个字段，而是引入一套 catalog-wide version store、ref-aware read/write API、branch 权限、merge/diff/revert 语义和跨版本 GC 机制。对 Iceberg 可保持表格式低侵入；对 Delta Catalog-Managed Tables 则必须接受协议级侵入和 Catalog 权威访问入口。

### 2.1 主流 Catalog 的当前模型

**Unity Catalog OSS** 的 `TableInfo` 主要表示当前表实体，包括 `name`、`catalog_name`、`schema_name`、`table_type`、`data_source_format`、`columns`、`storage_location`、`properties`、`owner`、`table_id` 等。服务端持久化模型也围绕当前 catalog tree 展开。Unity Catalog 0.4.x 引入 managed tables 后，Catalog 对 Delta 表的读写协调能力显著增强，但它仍不是 catalog-wide Git-like commit graph。

**Apache Polaris** 的定位是 Iceberg REST Catalog。Polaris Catalog 的核心职责是保存表名到当前 metadata file 的指针，并通过原子操作更新该指针。它已经具备权限、credential vending、存储配置和 REST-compatible 多引擎接入能力，但当前公开模型仍以当前 catalog tree 为中心，而不是每个 ref 拥有独立 catalog snapshot。

这意味着 Unity/Polaris 已经具备 Git-like 的部分前置条件，例如 table identity、metadata pointer、OCC、批量提交、权限与凭证控制。但 Git-like 需要额外回答以下问题：

| 问题 | 当前 Catalog 通常已有 | Git-like 需要新增 |
|---|---|---|
| 表当前状态 | 表名到 metadata pointer | ref 到一组 content value 的映射 |
| 写入并发 | 单表或批量 OCC | ref HEAD CAS 与 commit log |
| 历史 | 表级历史或事务日志 | catalog-wide commit history |
| 隔离环境 | schema/catalog 级环境隔离 | branch/tag 级逻辑隔离 |
| 发布 | 单次表提交或多表事务 | branch merge、revert、policy gate |
| 文件生命周期 | 当前表 GC | 所有 live ref/tag/history 的 reachability |

### 2.2 最小新增结构

若采用 Nessie-like 的 Catalog 内置版本层，即在 Catalog 内部维护 `refs`、`commits`、`content_values` 和索引，至少需要以下结构。

| 结构 | 作用 | 关键字段 |
|---|---|---|
| `catalog_refs` | branch/tag 的命名入口 | `catalog_id`、`ref_name`、`ref_type`、`head_commit_id`、`created_at`、`owner`、`policy`、`deleted` |
| `catalog_commits` | catalog-wide commit 链 | `commit_id`、`parent_commit_id`、`secondary_parent_ids`、`author`、`timestamp`、`message`、`index_id`、`operation_summary` |
| `catalog_content_values` | 某个 catalog object 在某版本上的 on-reference state | `value_id`、`content_id`、`content_type`、`metadata_location`、`snapshot_id`、`schema_id`、`spec_id`、`sort_order_id`、`table_uuid`、`serialized_payload` |
| `catalog_commit_ops` | commit 中的 key 级变更 | `commit_id`、`content_key`、`op_type`、`expected_value_id`、`new_value_id`、`payload_type` |
| `catalog_commit_indexes` | 从 HEAD 快速解析完整 catalog view | full index、incremental index、stripe index |
| `branch_policies` | branch/tag 权限与保护规则 | write/merge/delete 权限、required checks、tag immutability |
| `gc_roots` / reachability index | 防止误删仍被历史引用的 metadata/data files | `ref_name`、`commit_id`、`content_value_id`、retention policy |

抽象读路径如下：

```text
ref_name = main
  -> catalog_refs.head_commit_id = c102
  -> catalog_commits.index_id
  -> lookup(ContentKey("sales.orders"))
  -> catalog_content_values(value_id=cv43)
  -> metadata_location = s3://.../orders/metadata/v43.metadata.json
```

抽象写路径如下：

```text
1. read target ref HEAD
2. resolve HEAD index and expected content values
3. write new table-format metadata to object storage
4. create new content values, commit object and index objects
5. CAS update catalog_refs.head_commit_id from old HEAD to new HEAD
```

### 2.3 对表格式和 Catalog 表结构的侵入性

#### 2.3.1 Iceberg：表格式低侵入，Catalog 指针成为权威状态

对 Iceberg 表，不需要修改 Iceberg table metadata JSON。Iceberg 的核心提交模型本来就是生成新的 metadata JSON，再由 Catalog 原子替换当前 `metadata_location`。Git-like Catalog 只需把“当前 metadata pointer”从单一 Catalog 行扩展为“每个 ref 上的 content value”，并把 ref HEAD 的 CAS 作为最终提交边界。

Iceberg REST OpenAPI 已包含 `POST /v1/{prefix}/transactions/commit`，请求体由多张表的 requirements 与 updates 组成，用于原子提交多表更新。这说明 Iceberg 社区正在把多表一致性放到 Catalog 协调层，而不是要求表格式文件直接保存 catalog-wide branch 状态。

为了提升 diff、merge、OCC 和 UI 展示能力，建议在 content value 中冗余保存以下字段：

| 字段 | 必要性 | 说明 |
|---|---|---|
| `metadata_location` | 必须 | 当前 ref 上该表的 Iceberg metadata JSON |
| `content_id` / `table_uuid` | 强烈建议 | 识别 rename 前后是否同一逻辑表 |
| `snapshot_id` | 建议 | 快速展示和校验，不必每次解析 JSON |
| `schema_id`、`spec_id`、`sort_order_id` | 建议 | 支持 schema/spec/order 级 diff 与部分自动冲突判断 |
| `location` | 建议 | 支持存储策略、权限、GC 和安全校验 |
| `format_version` | 建议 | 判断 Iceberg v1/v2/v3 等兼容能力 |
| `last_sequence_number` | 建议 | 辅助判断 append、rewrite、delete 等操作边界 |
| `metadata_etag` / `metadata_fingerprint` | 建议 | 支持缓存失效、幂等写入和快速一致性校验 |

这些字段属于 Catalog 的 metadata-of-metadata，不要求 Iceberg 表格式新增字段。

需要注意，Iceberg 的表级 branch/tag 与 Catalog Git-like branch 不是同一概念。表级 branch 存在于单张表 metadata 中，Catalog branch 是跨 namespace/table/view 的一致视图。如果 REST/API 代理入口用 URI prefix、header 或 catalog property 承载 branch，需要同步处理 `listTables`、`loadTable`、`commitTable`、`renameTable`、`dropTable`、view、credential vending、ETag 与客户端缓存，否则不同接口可能解析到不同 ref。

#### 2.3.2 Delta Catalog-Managed Tables：协议侵入更深，绕写控制更严格

Delta CMT 不是简单的 Catalog 字段扩展。官方文档要求启用 `delta.feature.catalogManaged`，升级 reader/writer protocol，并禁止不经 managing catalog 的 path-based access。Delta clients 必须通过 Catalog 发现和访问表，以保证 Catalog 能协调提交、校验内容并维持一致性。

Delta CMT 的关键变化是把 Delta 的提交发布从纯文件系统 `_delta_log` 协调，改为由 managing catalog 参与原子性控制。Catalog 因此可以获得多表事务、统一权限、审计、credential vending 和集中优化的基础，但代价是客户端、协议特性和运维入口都必须支持 catalog-managed 模型。Unity Catalog managed tables 与 Databricks 文档也强调：managed tables 的读写、存储和优化由 Unity Catalog 管理，path-based access 会绕过权限控制并可能造成一致性问题。

因此，若在 Unity Catalog 上实现 Git-like，Delta CMT 提供的是强有力的提交协调基础，但不是完整 Git-like。还需要继续增加 ref、commit、branch policy、merge、diff、revert、GC roots 和 branch-aware API。对外部引擎而言，最低要求是支持 Unity REST API 或 Delta CMT 协议；仅能按路径访问 Delta log 的旧客户端不应写入 Git-like 管理的表。

#### 2.3.3 Unity / Polaris 表实体：不建议把 `ref_id` 直接并入现有表行

一种看似简单的实现是把现有表行改为多版本行：

```text
table_active_state(
  catalog_id,
  schema_id,
  table_name,
  ref_id,
  content_id,
  value_id,
  metadata_location,
  entity_version,
  ...
)
```

这会把原来 `(schema_id, table_name)` 的唯一约束扩展为 `(schema_id, table_name, ref_id)`。问题在于，lookup、list、rename、drop、权限继承、credential vending、GC 都会被 ref 维度污染。长期看，更合理的方式是保留当前表实体作为 main 的物化视图或兼容层，另建 version store 作为权威状态。

具体风险包括：

- **唯一性语义被削弱**：同名表在不同 ref 上可以指向不同 content value，但它们是否仍是同一逻辑表，需要 `content_id` 或 table UUID 维持身份，而不是依赖 `(schema, name, ref)`。
- **权限模型变复杂**：Unity/Polaris 的权限通常绑定 catalog、namespace、table、view 等实体。若每个 ref 生成一组表行，需要决定权限复制、继承、撤销和审计归属，容易出现 ref 内权限与 main 权限不一致。
- **rename/drop 语义不稳定**：Git-like rename 应该是 content key 的历史变更，而不是简单改多行名称。drop 还需要 tombstone、retention、restore 和 GC root。
- **缓存与凭证难以隔离**：Iceberg REST 的 `loadTable` 可能返回 credentials、config、ETag 和 metadata。若同一表名在不同 ref 上返回不同结果，客户端缓存必须把 ref 纳入 cache key。
- **外部同步成本增加**：Polaris external catalog、Unity foreign/external tables、Snowflake/Dremio 等集成通常假设一个当前表状态。多 ref 表行会放大同步冲突。

#### 2.3.4 最小侵入模型：主表实体兼容，version store 权威

建议把现有 Catalog 表实体定位为兼容视图，而不是 Git-like 的事实源：

| 对象 | 是否改造 | 设计建议 |
|---|---|---|
| `tables` / `views` 现有实体 | 低侵入 | 保留 main 的可见状态，服务旧客户端和管理 API |
| `refs` / `commits` / `content_values` | 新增 | 保存 catalog-wide 版本历史，成为 ref-aware API 的权威状态 |
| 权限对象 | 中等侵入 | 默认继承 namespace/table 权限，另加 branch policy、merge policy、tag immutability |
| 缓存对象 | 中等侵入 | cache key 必须包含 ref/hash、content id、metadata fingerprint |
| GC/retention 对象 | 高侵入 | 引入 ref/tag retention、drop tombstone、resolved metadata root 和 dry-run 报告 |

这个模型允许主流 Catalog 先维持既有 API 稳定，再逐步暴露能识别分支、tag 或 commit hash 的 API 入口。它也避免把 Git-like 语义硬编码进每个表格式的 metadata 文件。

### 2.4 四种实现架构

以下四类名称是本文按“版本数据放在哪里、谁是写入权威、如何接入引擎”归纳的设计形态，不是行业固定术语或某个项目的官方命名。因此本节改用中文描述性名称，避免把分析标签误读为事实标准。

| 架构 | 版本数据位置 | 原子性 | 改造深度 | 绕写风险 | 适合阶段 | 核心风险 |
|---|---|---|---|---|---|---|
| Catalog 内置版本层 | Unity/Polaris 等 Catalog 内部 | 最强，由分支 HEAD 条件更新和 catalog commit 保证 | 高 | 低 | 最终形态或自研 Catalog | 改造范围覆盖读写、权限、缓存、GC |
| Catalog 外置版本层 | 主流 Catalog 外部的 Nessie-like 版本服务 | 取决于外置服务是否是唯一写入口 | 中到高 | 高，除非封闭直写 | 渐进迁移或兼容旧 Catalog | 外置状态与主 Catalog 物化状态可能不一致 |
| REST/API 代理转换层 | 引擎和 Catalog 之间的协议入口 | 强，前提是完整覆盖读写接口 | 中高 | 中 | Iceberg REST 优先阶段 | 分支选择、凭证、缓存和接口覆盖容易不一致 |
| 先做多表事务，再扩展版本能力 | Catalog 事务日志与多表提交记录 | 多表事务强，长期分支弱 | 中 | 低到中 | P0/P1 | 后补长期 branch 仍需重建版本存储 |

#### 2.4.1 Catalog 内置版本层

该方案是在 Unity/Polaris 的 Catalog 服务内部加入版本层。对外仍是一个 Catalog；对内把“当前表实体”改成“某个 ref 上的 catalog view”。这里的 ref-aware API 指所有读写接口都能显式识别分支、tag 或 commit hash，而不是只读取默认 main 状态。

```text
client
  -> Git-like Catalog service
       -> refs / commits / content-values / indexes
       -> existing entity store / privilege store / credential vending
       -> object storage metadata files / data files
```

该方案语义最完整，权限、审计、GC、credential vending 都在同一控制面中。主要成本是所有读写路径必须识别分支，尤其是 `listTables`、`renameTable`、`dropTable`、namespace 删除、权限继承和缓存失效。

该方案适合新建 Catalog 或可控私有 Catalog。若直接改造 Unity/Polaris，需要至少补齐三类内部接口：第一，`resolve(ref, content_key)` 与 `commit(ref, expected_head, ops)`；第二，按分支执行的权限校验与审计事件；第三，GC root 计算与 object store 文件生命周期管理。否则即使 refs/commits 表存在，也无法保证所有 Catalog 行为都遵循同一 ref 视图。

#### 2.4.2 Catalog 外置版本层：在主流 Catalog 外套 Nessie-like 版本服务

该方案对应“metadata of metadata of metadata”的设想。层次关系可以拆成三层：

| 层级 | 管理对象 | 例子 |
|---|---|---|
| 表格式 metadata | 数据文件、manifest、snapshot、schema | Iceberg `metadata.json` |
| 主流 Catalog metadata | 表名到当前 metadata 文件的指针、权限、位置、凭证策略 | Unity/Polaris 中的 table row 和 `metadata_location` |
| 外置版本 metadata | 不同 ref 上的 Catalog content value、commit、index、merge 记录 | Nessie-like 的 `refs`、`commits`、`content_values` |

因此，外置版本层不是简单记录“主 Catalog 当前表行的历史”。若主 Catalog 只有一份可变的当前表行，外置服务必须自己保存每个 ref 上的 `ContentKey -> content value`，包括 `metadata_location`、content id、schema/spec 摘要、删除 tombstone 和 commit index。否则，一旦主 Catalog 的 main 行被覆盖，历史分支就无法可靠恢复。

典型结构如下：

```text
Spark / Trino / Flink
  -> 外置 Git-like Catalog 服务
       -> refs / commits / content-values / indexes
       -> 主流 Catalog：只物化 main 或提供权限、凭证、对象注册
       -> object storage：Iceberg metadata.json / manifest / data files
```

这个方案的关键不是“能否再套一层元数据”，而是“谁是权威写入口”：

- 若所有引擎只能通过外置服务写入，则外置服务可以成为 Git-like 的权威状态，主流 Catalog 只是 main 分支的物化视图或权限/凭证提供者。
- 若引擎仍可直接写 Unity/Polaris，则外置服务保存的 branch HEAD 会失真。此时它只能提供审计、历史可视化或迁移辅助，不能承诺强隔离写入、merge 和 revert。
- 若采用外置服务与主流 Catalog 双写，需要 outbox、重试、补偿和对账机制，处理“外置 commit 成功但主 Catalog 物化失败”或“主 Catalog 物化成功但外置 commit 失败”的不一致。

进一步细分，Catalog 外置版本层有三种形态：

| 形态 | 权威状态 | 适用场景 | 主要限制 |
|---|---|---|---|
| 只读历史层 | 主 Catalog | 历史可视化、diff、审计 | 不能提供 isolated write 和 merge |
| 写入代理层 | 外置版本服务 | 引擎接入点可完全收口 | 必须禁止直连主 Catalog 写入 |
| 主从物化层 | 外置版本服务为权威，主 Catalog 只物化 main | 兼容旧客户端 | 需要处理物化失败、补偿和回放 |

如果选择该方案，设计重点应从“如何套一层 metadata-of-metadata-of-metadata”转向“如何收敛写入口、如何处理物化一致性、如何证明底层 Catalog 没有被绕写”。这是它与 Catalog 内置版本层的主要差异。

#### 2.4.3 REST/API 代理转换层：在协议入口解析分支

该方案是在引擎和主流 Catalog 之间放置一个能识别分支的 REST/API 入口。它拦截 Iceberg REST Catalog 或 Delta Catalog Managed API，为不同 branch 返回不同 `metadata_location`，并把写入提交到版本存储。

```text
Spark / Trino / Flink / PyIceberg
  -> 能识别分支的 REST/API 入口
       -> 从 URI、header 或配置中解析 ref
       -> 读写版本存储
       -> 必要时把 main 物化到 Unity/Polaris
```

它对引擎最透明，尤其适合 Iceberg。但 Iceberg REST spec 的 `prefix` 本身是 catalog prefix，不是 branch 标准语义。不同引擎对 header、catalog property、URI rewrite 的支持也不一致。若代理入口不能完整覆盖 namespace、table、view、rename、drop、credential vending、transactions/commit 和 cache invalidation，就容易出现行为不一致。

分支选择可以有四种方式：

| 方式 | 示例 | 优点 | 问题 |
|---|---|---|---|
| URI 路径 | `/v1/prod/branches/dev/...` | 直观，便于路由 | 偏离 Iceberg `prefix` 的原始语义 |
| Catalog 配置项 | `ref=dev` | 配置简单 | 不同引擎对动态切换支持不一致 |
| HTTP header | `X-Catalog-Ref: dev` | 不污染表名 | 代理、缓存、审计链路必须透传 |
| Namespace 编码 | `dev.sales.orders` | 兼容性最好 | namespace 与 branch 语义混杂 |

无论采用哪种方式，缓存与凭证都必须显式包含 ref。Iceberg REST `loadTable` 返回的 credentials/config/metadata 与 ETag 如果只按 table identifier 缓存，就可能把 target branch 的 metadata 暴露给 source branch。OAuth token endpoint 在 Iceberg REST 规范中也已标记为 deprecated-for-removal，长期应通过标准 OAuth endpoint 与 token exchange 处理用户身份，而不是在代理入口中自定义弱认证。

#### 2.4.4 先做多表事务，再扩展版本能力

该路线不先做长期 branch，而是先利用 Iceberg REST `/transactions/commit`、Polaris batch entity write、Unity/Delta CMT 等能力，实现多表 atomic publish 与 catalog commit log。

```text
阶段 1：多表 atomic publish
  staging writes -> validate -> commit all tables

阶段 2：给每次 transaction 生成 catalog commit log
  commit_id -> changed tables -> old/new metadata_location

阶段 3：在 commit log 上逐步增加 tag / revert / branch
```

该方案更容易落地，但后补 branch 会遇到结构性限制。如果历史只记录 main 从旧值到新值，没有为每个 ref 维护独立 HEAD 和 index，后续仍要补建版本存储。因此它更适合作为 P0/P1，不是最终形态。

对主流组件应采用更细的判断：

| 组件 | 事务基础 | 对 Git-like 的含义 |
|---|---|---|
| Iceberg REST | 规范包含 `/transactions/commit` | 可作为多表 atomic publish 入口，但不定义 branch/merge |
| Delta CMT / Unity Catalog managed tables | Catalog 参与提交协调，并禁止普通路径绕写 | 适合先做 governed publish，再扩展能识别分支的 API |
| Apache Polaris | 以 Iceberg REST Catalog、内部/外部 catalog、权限与存储配置为核心 | 适合增强 internal catalog 的版本层；external catalog 多为同步/只读语义 |
| Lakekeeper | Rust Iceberg REST Catalog，强调 vended credentials、remote signing、治理集成 | 可作为 REST/API 代理或“先做多表事务、再扩展版本能力”的参考 |
| Gravitino Iceberg REST service | 文档列出多项 REST 能力，但明确 multi table transaction 尚未实现 | 适合作为 catalog-of-catalogs 与治理入口参考，不应假设其已提供多表事务 |

#### 2.4.5 架构选择建议

若研发目标是自研 Catalog 并长期承载 Git-like 能力，Catalog 内置版本层最符合语义完整性。若目标是接入已有 Unity/Polaris 生态，短期应优先选择“先做多表事务，再扩展版本能力”或“REST/API 代理转换层”，先把写入口和权限闭环做稳定，再逐步把 ref、commit、diff、merge、GC roots 做成独立权威层。

在主流 Catalog 外套 Nessie-like 版本服务是可行方案，但不能只理解为“多加一层 metadata 表”。它必须回答三个问题：第一，外置版本层是否保存完整的 per-ref content value；第二，是否能禁止所有客户端绕过外置服务写主 Catalog；第三，main 物化到主 Catalog 失败时如何补偿。如果这三个问题无法解决，该方案应定位为审计、可视化或迁移过渡层，而不是强一致 Git-like Catalog。

### 2.5 对 Unity/Polaris 的落地建议

1. 先实现多表事务优先的 atomic publish，优先解决跨表一致发布。
2. 同步设计独立 version store，不把 branch 维度硬塞进现有 table row 主键。
3. 将 main 作为兼容物化视图，传统客户端读 main，Git-like 客户端通过能识别分支的 API 入口读写 branch。
4. 在 merge main 前引入 branch protection、required checks、schema/data contract 和权限审批。
5. 在基础事务、权限、GC、审计稳定后，再引入 semantic auto resolve。

## 3. Nessie Roadmap、已知问题与不足

本章判断：Nessie 的公开演进重点正在从 Git-like 内核转向 Iceberg REST Catalog 化、引擎互通和生产运维能力。Nessie 已经具备 refs、commits、content values、catalog-wide index、merge/transplant 等基础原语；当前更突出的不足在工具层事务暴露、ContentKey 级冲突粒度、语义合并、热点 ref 性能、GC/drop table 边界和主流引擎接入细节。

### 3.1 证据口径

Project Nessie 公开站点没有单独稳定的“Roadmap 2026”页面。本文将 roadmap 拆成四类证据：

| 证据类型 | 可信度 | 用法 |
|---|---|---|
| 官方 docs 明确写出的能力/限制 | 高 | 作为当前事实或官方方向 |
| release notes 连续出现的主题 | 中高 | 判断近期工程重心 |
| 源码 README / TODO / 实现结构 | 中 | 判断技术约束和潜在演进 |
| GitHub issue | 中 | 说明真实用户遇到的问题，但不等于官方承诺 |

下面的“方向”按工程判断表述，不将推断写成官方承诺。

### 3.2 官方文档可确认的方向

| 方向 | 证据 | 判断 |
|---|---|---|
| Iceberg REST Catalog 化 | Nessie 0.107.5 下载页说明主 Nessie server 同时服务 Iceberg REST API 和 Nessie native REST API；Iceberg REST guide 提供迁移方式 | Nessie 正在把 Git-like 能力包进标准 Iceberg REST Catalog 体验 |
| 标准引擎接入 | 最新 Trino with Iceberg REST 文档说明已经验证 S3/MinIO，并提供 starter configuration | 旧源码 README 中的 “Trino coming soon” 已不是最新口径 |
| 跨表事务 primitive | Transactions 文档说明 Nessie 可通过 branch merge 或 single commit 实现 cross-table transactions，底层能力已存在，但工具仍需暴露 | 内核能力先于 Spark/Trino/Flink 等工具层体验 |
| 隔离级别 | Transactions 文档描述 Read Committed、Repeated Read、Serializable 三类 optimistic 模型，并说明未来 likely add pessimistic locking | 高冲突 workload 下，长期可能需要服务端事务状态 |

| GC 与运维 | GC 文档包含 mark/sweep、deferred deletion、live content set、future enhancements 等内容 | 版本历史与对象存储生命周期仍是生产重点 |

### 3.3 近期工程重心

从 recent releases、latest docs 和公开源码结构看，Nessie 近期不是在重写 Git-like 原语，而是在补齐主流 Catalog 使用所需的工程面：

| 主题 | 例子 | 含义 |
|---|---|---|
| Iceberg REST 能力 | Iceberg REST migration、branch/tag selection、metadata-location 一致性 | 降低专有 NessieCatalog 依赖 |
| 引擎兼容 | Spark SQL 4.0 extension、Trino with Iceberg REST、PyIceberg 相关配置 | 提升标准客户端可用性 |
| 对象存储与凭证 | S3/GCS/ADLS、credential vending、request signing、secret manager | Catalog 需要承担安全数据访问入口 |
| 运行时与部署 | Java 17、Quarkus、Helm、server admin tool | 生产部署和升级能力增强 |
| 运维工具 | GC、export/import、admin tool、configuration reference | 从开发工具走向平台组件 |

这支持一个判断：Nessie 的基础 Git-like 模型已经相对稳定，近期 roadmap 更偏 Catalog 产品化、引擎互通和运维能力，而不是重新设计 refs/commits。

### 3.4 设计约束与源码暴露的问题

#### 3.4.1 Stateless server + CAS：水平扩展与热点 ref 冲突并存

Nessie storage 设计强调 stateless server。多个服务端实例之间不通过分布式共识协议通信，写入通过对象写入和 reference pointer CAS 完成。这有利于水平扩展，但也意味着同一 branch 的高并发写入主要依赖 OCC/CAS/retry，而不是集中式锁。

Nessie configuration 暴露了 `commit-retries`、`commit-timeout-millis`、retry 初始 sleep、最大 sleep 等参数，说明并发写入失败并不是异常路径，而是 optimistic model 的正常组成。默认 `commit-timeout-millis` 为 5000ms；在同一 target branch 上大量 CI/WAP 分支同时 merge 时，大 commit 更容易因构建 index、写对象和 CAS 时间更长而被后续 HEAD 前进打断。

这类问题不应只通过调大 timeout 处理。更合理的产品能力包括 branch-level lease、merge queue、commit-target routing、preflight conflict check 和对 main branch 的写入限流。否则 Git-like Catalog 在小规模测试中表现正常，但在生产主分支集中发布时出现尾延迟和间歇失败。

#### 3.4.2 Index / content value 模型：读性能依赖索引分段与缓存

Nessie version store 通过 immutable objects、commit object、content values、incremental index、reference index 等结构支持 catalog-wide lookup。该模型避免每次读取都从根提交回放完整历史，但会引入 index object 大小、分段、缓存命中率和后端存储 row/item size 限制。

配置中存在 `max-serialized-index-size`、`max-incremental-index-size`、`max-reference-stripes-per-commit`、`parents-per-commit` 等参数，说明大 catalog 和大 commit 需要显式控制索引对象大小。对自研 Catalog 的启示是：不要只设计 `commits` 和 `commit_ops` 两张表，还需要设计可查询 index、prefix lookup、namespace listing、diff index 和冷热 ref 缓存；否则 Git-like 功能会在表数量增长后退化为历史回放。

#### 3.4.3 冲突粒度仍是 ContentKey 级

Nessie merge/transplant 冲突处理围绕 `ContentKey`、`CommitOp`、`MergeBehavior` 和 content value 运行。它支持 `NORMAL`、`DROP`、`FORCE`，也支持外部提供 `resolvedContent`。但 version store core 不会自动解析 Iceberg metadata JSON，也不会判断两个 schema add-column 是否语义兼容。

官方 Transactions 文档也把锁和状态描述为 table granularity：如果表级发生冲突，Nessie 会拒绝操作，或委托底层表格式进一步处理。因此，Nessie 已经提供 semantic merge 的插入口，但没有内置表格式语义合并引擎。

这也是 Catalog Git-like 与普通 Git 的重要差异：代码文件可以按行或 AST merge，湖仓表的正确合并需要同时理解 schema id、field id、snapshot lineage、manifest rewrite、delete files、partition spec、sort order 和 table properties。ContentKey 级冲突只是定位冲突对象，不足以判断是否可以自动解决。

#### 3.4.4 Delete / Unchanged 校验与事务隔离 primitive 仍需工具化

源码中存在对 Delete/Unchanged 更严格 expected value / expected content 模型的 TODO。这说明 Put 类操作的 expected-content 校验更成熟，而 Delete、Unchanged 在 API 表达和冲突校验上仍有补强空间。

Nessie 的 Serializable optimistic transaction 依赖 `Unchanged` 操作记录读集合：提交时要求读过的表仍处于相同状态，否则拒绝写入。这个 primitive 对多表事务很关键，但官方文档也说明工具层仍需增强，才能让 Spark、Trino、Flink 等用户自然使用这些隔离能力。自研 Catalog 若要对外宣称 serializable multi-table transaction，不能只支持多表 Put，还必须支持 read-set validation、expected target content、幂等提交和失败重试语义。

#### 3.4.5 Merge 语义与 Git 不完全一致

Nessie 官方 About 文档明确说明：Nessie commit 只有一个 parent；merge 操作不是生成普通 Git 双父 merge commit，而是把 source branch 的变化 replay 到 target branch 最新提交之上。`transplant` 保留 individual commits；merge 可通过额外元数据记录来源，但主链仍以 target 父提交为主。

这种设计降低了 index 与读路径复杂度，也更适合“main 永远指向最新数据状态”的 Catalog 语义。但它不等同于 Git 的历史模型。产品文档和 UI 应避免直接照搬 Git merge graph，否则用户会误解 merge-base、revert、cherry-pick、squash、audit lineage 的含义。

#### 3.4.6 GC 需要跨两层引用图

Nessie GC 需要先理解 catalog refs/commits/content values，再理解 Iceberg metadata、snapshot、manifest、data/delete files。社区 issue #11273 报告了 dropped tables 场景下 metadata/data 没有被清理的问题。这类问题的根源是：Catalog 控制 metadata pointer，表格式 metadata 再控制文件引用，GC 必须跨两层图计算 live set。

Nessie GC 文档将流程拆为 identify/live-content-set 与 expire/delete，并讨论 deferred deletion、unreferenced contents、Iceberg-specific enhancements 等方向。对自研方案而言，GC 不能只扫描当前 main 的 metadata location；它必须以 ref/tag retention、commit retention、drop tombstone、resolved metadata root 和表格式文件引用共同构成 live set。否则会在两个方向出错：要么误删历史 branch/tag 仍需的数据，要么无法清理 drop table 后完全不可达的存储路径。

#### 3.4.7 引擎接入与 REST 规范差异

Nessie 同时提供 Iceberg REST API 与 Nessie native REST API。Iceberg REST 降低了 Spark、Trino、Flink、PyIceberg 等客户端的接入门槛，但 branch/tag、merge、transplant、resolvedContent 等 Git-like 能力并不是 Iceberg REST 的通用语义。Trino with Iceberg REST、Spark extension、PyIceberg 配置等需要分别验证。

Iceberg REST OpenAPI 中还包含 endpoint discovery、idempotency key、ETag、credential vending、OAuth endpoint deprecation 等细节。Git-like Catalog 如果通过 REST/API 代理入口承载 branch，必须逐项处理这些协议细节，而不能只重写 `metadata_location`。否则会出现读写路径一致但权限、缓存、token、rename/drop 或 transaction endpoint 不一致的问题。

### 3.5 已知问题与优化方向

| 问题 | 类型 | 影响 | 可行优化 |
|---|---|---|---|
| 工具层事务能力未完全暴露 | 官方限制 | 用户难以直接用 SQL/引擎 API 写出完整 serializable multi-table transaction | 增强 Spark SQL extension、REST client、Trino/Flink connector |
| 高并发同 branch 写入 timeout | 社区 issue + 架构约束 | WAP/CI 大量并发 merge main 时尾延迟高 | branch-level lease、merge queue、commit-target routing、preflight merge cache |
| Trino Iceberg REST 限制 | 官方限制 | 当前 Trino 文档强调 S3/MinIO 验证、OAuth endpoint 配置缺口 | 提供更完整模板，等待 Trino REST OAuth 能力完善 |
| 无内置 semantic auto merge | 设计限制 | 兼容 schema 变更、append+compaction 等场景仍需人工或外部 resolver | Catalog 层 semantic merge service |
| Delete 校验不足 | 源码 TODO | 删除/不变操作 OCC 粒度不如 Put 严格 | API 增加 expected content，补强 delete validation |
| GC/drop table 边界复杂 | 社区 issue | 历史分支、drop table、metadata 文件清理之间容易错漏 | tombstone root、drop metadata root、GC dry-run 报告 |
| Git 语义误解 | 设计差异 | 用户可能误解 merge history 与 Git 完全一致 | UI/文档明确区分 data merge 与 Git merge |

### 3.6 Roadmap 推断

**短期：把 Iceberg REST Catalog 做稳。**  
优先级最高的是主流引擎兼容、credential vending、object store、auth、Trino/Spark/Flink/PyIceberg 体验。原因是如果标准引擎不能稳定通过 REST Catalog 使用 Nessie，Git-like 能力只能停留在少数专用客户端中。

**中期：补全事务工具链与运维闭环。**  
Nessie 已有 cross-table transaction primitives，但工具层仍需增强。合理方向包括 transaction-aware SQL/API、dry-run merge、branch protection、required checks、GC dry-run、deferred delete、drop table recovery、commit retry/merge conflict/GC 指标。

**中长期：处理高冲突和语义冲突。**  
高冲突 branch 可通过 routing/lease/queue 减少 CAS retry，也可能引入官方文档提到的 pessimistic locking。语义冲突则需要表格式参与：只自动合并表格式库能验证正确的变更，例如 add-only schema merge、不同 property key 合并、append-only snapshot merge。破坏性 schema 变更、业务行级冲突仍应交给人工或业务规则。

## 4. 创新与增强方向

本章判断：类似 Nessie 的 metadata-of-metadata 结构是实现 Git-like 的必要条件，但不是充分条件。真正形成产品差异的方向首先在工作流、治理、性能、GC 和主流 Catalog 互通；语义合并应作为受控增强能力后置建设，并且只能自动提交由规则引擎和表格式库验证过的结果。

### 4.1 创新方向总览

把 Nessie 式双逻辑表结构迁移到主流 Catalog 或叠加在 Catalog 外层，只能得到 refs、commits、content values 和基础 merge primitive。若要形成可落地产品，需要继续补齐以下能力：

| 方向 | 目标 | 关键设计 |
|---|---|---|
| 协作工作流 | 将 branch/merge 转化为数据发布流程 | Data PR、required checks、审批、审计、release tag |
| 发布治理 | 保证多表变更按依赖关系一致发布 | dependency graph、contract validation、回滚计划 |
| 性能与规模 | 支撑大 catalog、高频 main、长历史 | materialized ref view、diff index、merge queue、branch lease |
| 文件生命周期 | 避免历史分支误删或 drop table 泄漏 | ref/tag retention、tombstone、GC dry-run、reachability summary |
| 语义合并 | 降低安全场景下的人工冲突成本 | 表格式插件、resolved content、规则验证、policy gating |
| 治理互通 | 与 Unity/Polaris 权限和凭证模型一致 | branch policy、token/credential scope、审计事件对齐 |

### 4.2 Data PR 与工作流增强

底层 refs/commits 只能保证版本原语成立，不能保证团队愿意使用。更重要的是把 Git-like 包装为数据团队可操作的流程。

| 能力 | 设计要点 |
|---|---|
| Data PR | 展示 branch diff、受影响表、schema diff、数据质量摘要、样本对比、血缘影响、审批记录 |
| Branch protection | main 禁止直接写；merge 必须通过 required checks；生产 tag 不可变 |
| Quality gate | 集成 Great Expectations、Deequ、dbt tests、freshness、null ratio、schema drift 检查 |
| Release tag | 为月报、模型训练集、监管报送创建不可变 tag，并绑定 retention |
| Revert plan | 回滚前展示受影响表、下游依赖、需要保留或可清理的文件 |
| Dependency-aware publish | 按血缘和数据契约判断多表发布顺序与最小影响范围 |

这些能力不是 `refs/objs` 自然带来的，但它们决定 Git-like Catalog 是否能从“内核正确”转为“平台可用”。

Data PR 的最小信息集建议包括：

- **变更范围**：新增/删除/重命名的 namespace、table、view，以及每张表的新旧 metadata location。
- **表格式 diff**：schema、partition spec、sort order、snapshot lineage、table properties、row-level delete/update 摘要。
- **质量结果**：行数、空值率、唯一性、freshness、数据契约、dbt/Deequ/Great Expectations 结果。
- **权限影响**：新增对象的 owner、继承权限、branch-specific policy、外部共享范围。
- **发布决策**：fast-forward、squash、rebase/replay、manual resolved content、rollback plan。

### 4.3 依赖感知多表发布与可回滚计划

多表 Git-like 的核心价值不只是一次提交修改多张表，而是让一组有关联的数据产品以可审查、可回滚、可复现的方式发布。建议在 commit/PR 层维护 `dependency_manifest`：

| 字段 | 说明 |
|---|---|
| `changed_contents` | 本次修改的表、视图、函数、模型或数据产品 |
| `read_dependencies` | 构建时读取的上游表和具体 ref/hash |
| `contract_checks` | schema contract、semantic type、freshness、SLO 检查结果 |
| `publish_order` | 对下游可见性有要求时的提交/物化顺序 |
| `rollback_plan` | revert 时需要恢复的 content value、tag、外部物化对象和文件保留策略 |

该能力可以与 Iceberg REST `/transactions/commit` 或 Delta CMT 的多表原子提交结合：事务保证 all-or-nothing，dependency manifest 负责解释“为什么这些表必须一起发布、发布后影响哪些下游、回滚是否安全”。这一区分能避免把多表事务误解为完整数据发布治理。

### 4.4 性能与可扩展性增强

大 catalog 和高频 main branch 会带来读写热点。可考虑以下优化：

- **branch-local lease / soft leader**：对同一 branch 的写请求尽量路由到同一 server，减少 CAS retry。
- **merge queue**：对生产 main 的 merge 请求排队，避免大量 CI 分支同时抢占 HEAD。
- **merge preflight cache**：缓存 source/target/common ancestor 的 diff，dry-run merge 和真实 merge 复用。
- **materialized ref view**：为高频 ref 维护可查询的 `ContentKey -> value` 物化视图，降低 list 和 prefix lookup 成本。
- **diff index**：按 namespace/table 维护 touched-key bitmap，快速回答两个 ref 之间哪些对象变化。
- **large commit chunking**：一个 catalog commit 修改大量对象时，将操作分片存储，但 ref pointer 仍一次 CAS。
- **commit graph cache**：缓存 common ancestor、recent head、merge-base 与 branch protection 判断结果。
- **server-side planning integration**：若实现 Iceberg REST scan planning endpoint，可在 Catalog 侧复用权限、credential vending 与 metadata cache，降低客户端反复加载 metadata 的成本。

性能设计应避免破坏一致性边界。materialized ref view、diff index、preflight cache 都只能作为派生结构；权威提交仍应以 ref HEAD CAS 和 commit object 为准。若派生结构更新失败，应支持从 commit log 重放修复。

### 4.5 GC 与文件生命周期增强

Git-like Catalog 的 GC 难点在于双层引用图：Catalog 历史 ref 保留 metadata pointer，表格式 metadata 又引用 snapshot、manifest、data/delete files。仅扫描当前 main 会误删历史 tag/branch 仍需的文件；过度保守则会造成对象存储膨胀。

建议设计：

- 以 `ref/tag retention` 作为 GC root，先计算 catalog live content，再交给表格式 live files 扫描。
- merge、revert、drop table 时记录 tombstone 与 drop metadata root，覆盖 dropped table 的文件清理场景。
- 对每次 commit 生成 lightweight file-reachability summary，例如 metadata file 列表、manifest list 摘要、文件统计 bloom。
- GC dry-run 报告纳入 Data PR：merge 前展示新增可回收文件、需保留文件和预计存储影响。
- 对生产 tag、监管 tag、模型训练集 tag 设置不可变 retention policy，避免自动 GC 破坏可复现性。

还需要区分四类删除语义：

| 删除类型 | 语义 | GC 处理 |
|---|---|---|
| branch 删除 | 删除 ref 名称，不等于删除历史文件 | 仍按 commit retention 保留一段时间 |
| table drop | 当前 ref 不再可见表 | 记录 tombstone 与旧 metadata root，等待 retention |
| snapshot expire | 表格式内部清理旧 snapshot | 需确认没有其他 catalog ref 指向该 metadata lineage |
| storage orphan cleanup | 删除未被任何 live set 引用的物理文件 | 必须经过 dry-run、审计和延迟删除 |

### 4.6 Semantic merge 与有限安全自动解决

#### 4.6.1 问题边界和分层架构

以一个受限场景说明语义合并价值：两个分支从同一个 base 分出，分别对同一张 Iceberg 表执行 schema-only `ADD COLUMN`。普通 ContentKey 级 merge 会发现同一张表的 content value 在 source 和 target 都发生变化，因此返回冲突。外部 resolver 可以读取 base/source/target 三份 Iceberg metadata，验证两侧均为安全的 additive schema change，生成新的合法 Iceberg metadata，并通过 `resolvedContent` 完成合并。

这个场景说明，version-store core 不应直接理解 Iceberg schema；它只需要提供冲突定位、expected target content 和 resolved content 校验入口。Catalog semantic service 则可以基于 `metadataLocation` 下钻到表格式语义。

建议分为三层：

| 层级 | 职责 | 说明 |
|---|---|---|
| VersionStore core | refs、commits、content values、merge primitive、`resolvedContent` 校验 | 保持格式无关，不解析 Iceberg/Delta/Hudi |
| Catalog semantic service | 读取 table-format metadata，判断能否安全合并，生成 resolved content | 可按表格式插件化 |
| Policy / Workflow layer | 决定哪些表、namespace、分支允许自动合并，记录审计和审批 | 与 Data PR、branch protection 结合 |

#### 4.6.2 Additive schema auto merge 的安全边界

建议先支持极窄的安全场景：

- 表格式仅支持 Iceberg。
- 冲突对象仅限同一张表。
- 两个分支都只做 schema-only `ADD COLUMN`。
- 不允许数据写入、delete file、manifest rewrite、partition spec 变更、sort order 变更、table property 变更、rename、drop、type widening。
- 新增列之间不能同名，类型必须兼容。
- 如果两个分支分配了相同 Iceberg field id，只允许在确认没有任何数据文件引用新增字段的前提下重新分配 field id。

Iceberg 的 schema identity 依赖 field id，不只是列名。两个分支从同一个 base schema 增加列时，可能都拿到相同的 next field id。对纯 schema metadata 变更，可以在最终 resolved metadata 中给其中一侧新增字段重新分配新 id；但如果任一分支已经写入数据文件，这些 field id 可能已进入数据/manifest 语义，自动合并必须拒绝。

#### 4.6.3 Resolver 的核心流程

推荐流程如下：

1. 读取目标 `ContentKey` 在 base、source、target 三个版本上的 table content。
2. 使用表格式库加载三份 metadata，例如 Iceberg `FileIO` 与 `TableMetadataParser`。
3. 校验三份 metadata 的 table uuid、location、format version 一致。
4. 计算 source 相对 base 的变更集合与 target 相对 base 的变更集合。
5. 只允许两边都是 add-only schema change，拒绝 snapshot、manifest、partition spec、sort order、property 等非 schema 变更。
6. 校验新增列名称、类型、field id，不满足安全条件则返回人工冲突。
7. 生成新的 metadata JSON，包含 target 与 source 双方新增字段，并保证 field id 合法。
8. 构造新的 content value，携带新的 metadata location、schema id、snapshot id、spec id、sort order id 和 content id。
9. 调用 merge，并为该 key 设置 `expectedTargetContent` 与 `resolvedContent`。
10. 若 target 在 resolver 计算期间前进，expected 校验失败，resolver 必须重新读取并重新判断。

伪代码只保留设计层含义：

```java
TableContent base = getTable(baseHash, key);
TableContent source = getTable(sourceHash, key);
TableContent target = getTable(targetHash, key);

TableMetadata bm = readMetadata(base.metadataLocation());
TableMetadata sm = readMetadata(source.metadataLocation());
TableMetadata tm = readMetadata(target.metadataLocation());

ResolvedMetadata resolved = resolveAdditiveSchemaOnly(bm, sm, tm);
TableContent resolvedContent = toCatalogContent(resolved);

mergeBranch(sourceRef, targetRef, key, expectedTargetContent = target, resolvedContent);
```

#### 4.6.4 自动合并策略分级与 LLM 边界

建议把自动 resolve 分为三档，避免把不可证明正确的结果写入核心事务路径。

| 档位 | 行为 | 适用场景 |
|---|---|---|
| `AUTO_SAFE` | 只自动合并表格式规范可证明无冲突的变更 | add-only schema、不同 property key、无重叠 append |
| `AUTO_WITH_POLICY` | 需要数据 contract、owner policy 或 branch policy 授权 | type widening、nested struct add、partition spec 演进 |
| `MANUAL` | 必须人工或业务系统生成 resolved content | delete/update 同行、同 property 冲突、破坏性 schema 变更、rename/drop |

LLM 可以用于解释冲突、生成审查摘要、建议合并策略，但进入 commit 的 resolved content 必须由规则引擎或表格式库验证。Catalog 不应让非确定性推断直接决定表 metadata。

### 4.7 与主流 Catalog 的渐进式路线

如果目标是 Unity/Polaris 这类主流 Catalog，建议分阶段落地：

| 阶段 | 能力 | 侵入度 |
|---|---|---|
| P0 | read-only tag：为当前 catalog 状态打快照，支持按 tag 读 | 低 |
| P1 | branch + isolated writes，merge 只允许 fast-forward | 中 |
| P2 | catalog-wide commit、diff、revert、squash merge 和表级冲突检测 | 中高 |
| P3 | semantic merge、branch protection、Data PR、GC roots | 高 |
| P4 | 与 Delta CMT、Iceberg REST transactions、Unity/Polaris 权限模型深度互通 | 高 |

工程上不应一开始追求完整 Git。先实现 branch、WAP、fast-forward publish 和 audit log，就能覆盖大量数据发布场景，并为后续 semantic merge 和 Data PR 打基础。
