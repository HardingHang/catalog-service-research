## 2. 测试范围

本报告评估 clustering-only，不显式创建 `BTREE`、`IVF`、全文索引或向量索引。查询收益来自聚簇布局、Lance fragment/page min-max 统计裁剪，以及顺序读局部性。

报告中的 `p50` 表示多次执行延迟的中位数，即 50% 的查询耗时不超过该值。本文主要用 `p50` 观察典型查询表现；尾延迟需要单独看 `p95/p99`。

报告中的 `bytes_read` 表示查询实际读取的数据量，用于观察裁剪效果和读放大。它不是按返回行数线性变化，而是受 fragment/page、列投影和统计裁剪粒度影响；因此一些查询会出现相同的读取档位，例如 `30.6 MiB`。这个值不是全局最小读取量，本次结果中点查/混合条件也出现了 `21-24 MiB` 的更小读取量。

本报告中的 `2D`、`3D`、`4D` 表示参与聚簇和查询评估的标量维度数量：

- `2D`：使用 `lat`、`lng` 两列。
- `3D`：使用 `lat`、`lng`、`category_id` 三列。
- `4D`：使用 `lat`、`lng`、`category_id`、`timestamp` 四列。

数据分布如下：

| 分布 | 生成方式 | 测试含义 |
|:---|:---|:---|
| `uniform` | `lat ~ Uniform(-90, 90)`，`lng ~ Uniform(-180, 180)` | 无明显热点的基础场景，用于观察算法在均匀空间上的布局和裁剪能力。 |
| `gaussian` | `lat ~ Normal(0, 20)`，`lng ~ Normal(0, 40)` | 数据集中在中心区域，用于观察局部聚集分布下的裁剪效果和算法稳定性。 |
| `skewed` | `lat = Zipf(2.0) % 180 - 90`，`lng = Zipf(2.0) % 360 - 180` | 强热点倾斜场景，用于观察算法在热点块、非均匀密度下的退化风险。 |

算法组如下：

| 组 | 含义 |
|:---|:---|
| `A-R` | 不聚簇重写布局 |
| `B-H` | Hilbert 聚簇 |
| `B-Z` | ZOrder 聚簇，`bits = 16` |
| `B-X` | XMCK 默认参数 |
| `B-XM` | XMCK 中等粒度参数 |
| `B-XT` | XMCK 更细粒度参数 |
| `B-O` | OTree 默认参数，批量 OTree-like layout |

`A-R` 不是新的聚簇算法，而是把未聚簇数据重写成 20 个 fragment/data file，和各聚簇组的文件数量一致。它用于隔离“文件数量不同”本身带来的影响，是本文比较聚簇算法收益的 baseline。原始单文件无聚簇组不再纳入算法对比。

本文中的 `B-O` 是 OTree-like 批量布局：递归切分 cube、把记录分配到 leaf cube、cube 内排序并重写数据。它不同于完整 OTree/Qbeast OTree：当前没有持久化 cube 索引协议、revision/payload/maxWeight 等增量维护机制，也没有在查询解析阶段根据 filter 直接定位 cube；因此本报告评估的是 OTree 物理布局收益，不是完整 OTree 查询裁剪体系的上限。

查询场景如下：

| 场景 | 含义 |
|:---|:---|
| `S1_2D_Range` | `lat/lng` 二维范围查询 |
| `S2_1D_Range` | `lat` 一维范围查询 |
| `S3_Point_Query` | `lat/lng` 点查询 |
| `S4_Full_Scan` | 全表聚合扫描 |
| `S5_Mixed_Condition` | `lat range + lng point` 混合条件 |

## 4. 总体结论

- **聚簇对真实命中的范围查询收益明确。** `S1` 的二维选择率按每轴 `sqrt(selectivity)` 生成，`uniform/gaussian` 的 `Rows` 接近标称选择率；`S3/S5` 使用真实存在的点值，避免把空结果误判为裁剪收益。

- **`S1/S2` 仍是判断算法收益的主依据。** 在 `uniform/gaussian` 的 `S1 10%` 中，最佳聚簇组相对 `A-R` 约 **7.1×-9.5×** 加速；`S2 10%` 中最佳组相对 `A-R` 约 **9.8×-10.8×**。`S1 50%` 收益约 **5.8×-7.3×**，选择率升高后仍有收益，但算法差距收敛。

- **Hilbert/ZOrder 在二维范围主路径上更稳，XMCK 在单列范围和构建成本上更强。** `gaussian/2d S1 10%` 中 `B-H/B-Z` 约 22.5ms，明显优于默认 `B-X` 的 45.4ms；`S2 10%` 中 `B-X/B-XM` 通常最快。XMCK 平均构建耗时约 **11.4s**，低于 Hilbert 的 **14.2s** 和 ZOrder 的 **13.3s**。

- **OTree 默认参数有明确正收益，但当前更像保守布局而不是二维范围最优布局。** `B-O` 在 `S2 10%` 单列范围中通常接近最快组，`uniform/2d` 为 19.84ms、`uniform/3d` 为 21.10ms、`uniform/4d` 为 20.17ms；但在 `S1 10%` 二维范围中通常落后于最佳 Hilbert/ZOrder/XMCK 约 **1.2×-1.6×**。主要原因是当前 OTree 只做物理重写，不做查询解析或 cube 级裁剪，收益依赖 Lance 现有 fragment/page min-max 统计。

- **`skewed` 是热点压力场景，不是普通低选择率场景。** Zipf 数据大量集中在 `lat=-89,lng=-179` 附近，`S1 0.1%/1%` 实际返回约 **37 万行**，`S2 0.1%/10%` 返回约 **61 万行**。聚簇仍有收益，但不能和 `uniform/gaussian` 的选择率直接横向比较。

- **`S3/S5` 主要用于验证非空点值路径。** 在 `uniform/gaussian` 下通常只返回 1 行，适合确认点值裁剪和非空查询，不适合作为算法主排序依据。

按查询场景看：

| 场景 | 结论 |
|:---|:---|
| `S1_2D_Range` | 主路径。`uniform/gaussian` 的行数接近标称选择率，`10%` 收益最清晰。 |
| `S2_1D_Range` | 单列范围查询收益稳定，`XMCK` 系列通常最好。 |
| `S3_Point_Query` | 使用真实存在的点值；连续分布下只返回 1 行，不适合主排序。 |
| `S4_Full_Scan` | 用于确认全表扫描表现；不作为聚簇裁剪收益的主判断依据。 |
| `S5_Mixed_Condition` | 使用真实存在的点值；连续分布下主要是微命中点查，作为辅助观察。 |

## 5. 主要结果

本节按分布和维度分表。`Rows` 是平均返回行数，用于确认查询是否真实命中。耗时表为 p50，单位 `ms`；读取字节表单位为 `MiB`。所有主结果表均列出 `A-R/B-H/B-Z/B-X/B-XM/B-XT/B-O`。

### 5.1 均匀分布

`uniform` 覆盖 `2D/3D/4D`。整体看，`S1/S2` 的聚簇收益稳定；维度升高后 `S1` 的最佳算法会变化，但 `S2` 仍偏向 XMCK 系列。

分析结论：

- `S1 10%` 最佳为 `B-H`，p50 从 `A-R` 的 203.20ms 降到 20.61ms；`B-O` 为 30.68ms。

## 8. 结果解释

范围查询收益主要来自物理布局让 fragment/page min-max 更容易裁剪，并提升顺序读局部性。`Rows` 可以确认 `uniform/gaussian S1` 的返回行数接近标称选择率，因此 `S1` 适合作为主路径判断依据。

`Hilbert` 和 `ZOrder` 在二维范围查询上整体更稳，尤其是 `gaussian/2d` 这类中心聚集分布。`XMCK` 的优势更多体现在较低构建成本、单列范围查询，以及均匀高维场景下的可调参数。

`OTree` 当前结果符合第一版实现预期：它已经通过 tree/cube 布局带来明显裁剪和局部性收益，但没有查询侧 cube pruning，因此二维范围查询还不能体现完整 OTree 体系的上限。`B-O` 对 `A-R` 的收益是明确的：`S1 10%` 在五个矩阵中有 **4.23×-7.83×** 加速，`S2 10%` 有 **5.05×-10.71×** 加速。它在单列范围上的表现接近 XMCK，说明物理布局本身有效；在二维范围和高维布局上落后，主要是默认 leaf 粒度偏粗和查询规划未使用 OTree 元数据。

`S2` 明显好于 `S1` 的相对排名。单列范围查询只沿一个维度形成带状区域，当前 OTree 的物理局部性和 page/fragment min-max 更容易生效；二维矩形查询会同时跨多个 leaf cube，且没有 cube 级查询裁剪，读放大更明显。若目标是提升二维范围查询，下一步应验证两类改动：一是调小 `target_rows_per_cube/min_rows_per_split` 形成更细 leaf；二是引入查询侧 cube 命中计算，让 OTree 元数据真正参与过滤。

`skewed` 的结果需要单独解释：它不是“0.1% 只返回 1000 行”的场景，而是热点数据导致同一个点/窗口命中大量重复坐标。这个结果说明默认参数对极端热点仍不够鲁棒，后续需要考虑更适合热点数据的分桶或自适应策略。

## 9. 建议

建议保留现有默认算法策略，不把 `XMCK` 设为默认。理由是 `Hilbert/ZOrder` 在二维范围查询主路径上仍更稳，而 `XMCK` 对参数和数据分布更敏感。

建议对外暴露或文档推荐 `XMCK` 的定位为：需要更低聚簇构建成本、主要查询包含单列范围或高维聚簇列、并且用户愿意基于 workload 调整参数的场景。

建议暂不把 `OTree` 定位为二维范围查询的默认算法。当前默认参数可以作为实验组保留：它构建成本接近 XMCK，单列范围收益强，但二维范围要继续补 tuned 参数组和查询侧 cube pruning 后再判断。

后续优先补充两类验证：`gaussian/skewed 3D/4D` 完整矩阵，以及更多查询窗口位置，例如中心窗口、低分位窗口、高分位窗口和热点窗口。

## 10. 局限性

- 本报告不包含显式 `BTREE`、`IVF` 或全文索引，不能推导聚簇与索引组合后的收益。
- 本报告只覆盖正式主矩阵，未覆盖 `gaussian/skewed 3D/4D`。
- 结果来自 WSL2 单机环境，受 CPU、磁盘、OS page cache 和后台负载影响，不能直接等价于生产环境。
- per-group cold-cache 依赖 `sudo drop_caches`，只能控制 OS page cache，不能完全隔离所有硬件和运行时缓存。
- `S3` 和 `S5` 已保证真实命中，但在连续分布下返回行数很少，因此主要用于辅助观察，不作为主排序依据。
- `skewed` 数据的标称选择率和实际返回行数差异很大，解释时必须同时看 `Rows`。
- `OTree` 第一版未实现查询解析、filter 改写或 cube 级裁剪，因此本报告只能评估 OTree 物理布局收益，不能代表完整 OTree 查询规划能力。
- 本报告以 `p50` 作为主要排序依据，同时参考 `bytes_read`；如果目标是 tail latency SLA，需要单独提高 `p95/p99` 的权重。
